连续圆角（2026-09-27）：`border-radius` 只能画椭圆弧——曲率在弧的中段恒为 1/r，碰到直边就掉到 0。`corner-shape` 让引擎把角画成超椭圆，曲率一路平滑地落到直边。这是引擎自带的能力，所以**边框、外阴影与角本身共用同一套几何**；不认识这条属性的引擎只当没写，照旧画圆角。它需要 Chromium 139+，Electron 44 带的是 Chromium 152。此前那套自己画角的实现（Houdini paint worklet + 遮罩，起因是 Electron 36 只有 Chromium 136）已整体删除，删除理由也正是它当年在面板上被否掉的理由：遮罩会剪掉元素自身的 `box-shadow` 与外扩状态环、与 `backdrop-filter` 抢同一层合成，而 worklet 尚未注册时元素会**整个消失**而不是退回圆角。**指数决定一个半径里看得见多少**（2026-09-27）：`--corner-shape` 由 `squircle`（Chromium 实测就等于 `superellipse(2)`）改为 `superellipse(1.5)`，半径令牌一个都没动。实测同一个半径下、半径×半径的角框被让出的面积：普通圆弧 21.5%、`superellipse(1.5)` 12.3%、`squircle` 6.9%——换算成"视觉当量半径"就是同一个 `border-radius` 的 0.76x / 0.57x，所以 `10px` 的表面令牌配 squircle 只读起来刚过 5px，转折基本看不出来。理由是要让拐弯看得出来，同时不改任何尺寸与比例（`--radius-ui` 一旦往上抬，28px 高的侧栏导航/面板页签会撞上 CSS 的半径夹取上限，被画成胶囊）。选 1.5 而不是更激进的 1.2（让出 17.2%）是留出与普通圆弧的区分度：`superellipse(1)` 就是普通圆角，那样等于把连续圆角这个特征丢掉。曲线家族、控件尺寸与比例均未改变。`styles/12-squircle-corners.css` 用一条 `*` 规则覆盖全应用，并显式列出 **52 个胶囊与圆形**选择器改回 `corner-shape: round`：超椭圆会把这些形状重画，Chromium 152 实测 60px 半径的角边界从 t=17.6px 移到 t=13px、999px 胶囊在 20px 钳制下从 t=5.9px 移到 t=4px（t = 角顶沿单轴到形状边界的距离，圆弧为 0.2929r；换成 squircle 则是 9.0px / 3.2px，更狠）。伪元素天然不受影响（`*` 不匹配伪元素），Monaco 与 xterm 在自己的 shadow tree 里自绘角、保持圆角。`corner-shape.test.ts` 从样式表逐条重算那份排除清单与"只有三处可以声明 `corner-shape`"这条边界，并把指数钉在超椭圆这一族上——写成 `round` 会让属性照样生效、其余断言照样绿，而连续圆角已经悄悄没了。面板的亚克力层（`.sidebar-surface::before` / `.workspace-panel-surface::before`）是内缩层，需要单独把形状传下去；它原来的 `clip-path: inset(0 round …)` 已删除——`clip-path` 只能画圆弧，会把亚克力切回圆角、而外框已经是超椭圆，于是每个角漏出一小块未填充的缝；Chromium 152 实测 `border-radius` + `corner-shape` 已能把填充**和** `backdrop-filter` 裁到同一条超椭圆上（模糊的边界落在 t=13px，而不是圆弧的 t=17.6px）。

**全局导航控件钉在窗口左上角，不再随顶部条滑动**（2026-09-28）：侧栏开关（面板图标）、返回与前进原来排在顶部条左端，而这条条在 chali 里从侧栏右边缘才开始——于是侧栏一折叠、一拖宽，三个控件就跟着滑动，其中"唯一能把侧栏再打开"的开关恰好就是移动的那一个。现在 `global-titlebar.tsx` 把它拆成独立的 `WindowNavControls`，由 `app-view.tsx` 作为**壳层固定层**渲染在 `.primary-workspace` 之前（DOM 顺序因此不变：裸的 `.sidebar-toggle-btn` 仍然先命中窗口开关，而不是工作区面板那个同名角标），`.app-nav-controls` 改为 `position: fixed`：`top: calc((var(--window-titlebar-height) - 24px) / 2)` 把 24px 控件盒在同一个 32px 行里居中，`left: 8px` 复刻顶部条自己的行内内边距，`z-index: 1003` 即 `.settings-entry-global` 那个窗口镶边层——它在**绘制**上必须高于 `.window-drag-band`（21）才看得见，也正因为它在那层之上，设置浮层接管左栏时控件依然可达。**但绘制在上不等于拿得到点击**（见下一段）：真实鼠标按下先被窗口的原生 draggable region 过滤，那一层看的是 `-webkit-app-region` 与 DOM 前序，完全不看 `z-index`。控件行为一字未改：`aria-label`（返回 / 前进 / 收起侧边栏 / 展开侧边栏）、`aria-expanded`、禁用态、悬停提示与点击处理全部沿用。真实窗口实测（`pnpm run verify:window-layout` 的 `pinned-window-chrome` 段）：展开 / 折叠 / 拖宽中三种状态里 `.app-nav-controls` 都是 `x=8 y=4 w=80 h=24`，与最大化时的位置逐像素相同，而侧栏轨道宽度依次是 `276 → 0 → 406`；每个状态按 1px 采样整条顶边，`.window-titlebar` 与 `.window-drag-band` 的并集无缝覆盖 `[0,width)`，唯一的不拖拽岛就是三个控件自己的 80×24，从 band 上真实指针拖动仍让原生窗口位移 24×12。
**钉住的控件用自己的命中岛挖穿拖拽区（2026-09-28，用户报障回归）**：用户报"侧栏没完全展开时左上角三个控件点不动"。根因不在绘制也不在 DOM：真实鼠标按下在派发前先经过**窗口的可拖拽区**——渲染器把 `-webkit-app-region` 的盒子合成成 draggable region 交给 OS，Windows 用它回答 `WM_NCHITTEST`，`HTCAPTION` 的按下变成窗口拖拽/激活（页面收不到），`HTCLIENT` 才派发。该区域按 **DOM 前序**累加、**忽略 `z-index`**，且 `no-drag` 只减掉它之前已加入的 `drag` 盒；`.app-nav-controls` 是壳的第一个子元素，它的 `no-drag` 早于顶部条与拖拽带被"用掉"，那几块随后把 80×24 的岛填回去。实测：三个控件中心在展开 / 折叠 / 拖宽中三态全部 `HTCAPTION`，而同一时刻 `elementFromPoint` 返回按钮、CDP 合成点击也照常通过（合成输入绕过这层过滤）——这就是"脚本全绿、用户点不动"。修法是 `styles/03-shell-sidebar.css` 里给 `.window-shell::after` 一个**不画像素的命中洞**（`no-drag` + `pointer-events: none`，几何与 `.app-nav-controls` 逐项相同）：生成盒位于前序子树末尾，因此在顶部条、面板 band 与设置浮层的 band **之后**才被减去，一次挖穿三条，而 32px 行上的其余位置（岛上、下、左、右与整条 band）仍是拖拽面。把 band 的 `pointer-events` 拿掉并不修这个问题（区域只看 `-webkit-app-region`，`clip-path` 同样无效），只会白丢指针桥那一半。三态真机断言（`WM_NCHITTEST`，含普通正文点的 `HTCLIENT` 对照）在 `verify:window-layout` 的 `nativeHitTest`；结构守卫在 `chat-layout-stability.test.ts` 的「keeps the pinned controls inside the window's clickable region in every sidebar state」用例。
设置浮层**镜照同一套结构**（`styles/07-overlays-settings.css`）：`.settings-workspace` 由 `inset: 32px 0 0` 改为 `inset: 0`，`.settings-layout` 用同一组行/列，`.settings-sidebar-track`（与设置分隔条）占 `grid-row: 1 / -1`，`.settings-workspace-body` 占 `grid-column: 3; grid-row: 2`——打开设置**不再让左侧卡片下移 32px**（实测应用侧栏卡片与设置侧栏卡片顶边都是 `y=8`）。整窗覆盖后命中测试改为按区域声明：浮层、`.settings-workspace` 与 `.settings-layout` 一律 `pointer-events: none`，只有侧栏轨道、其分隔条、正文列和新的 drag band 取回 `auto`——这正是"设置打开时窗口左上角仍然可拖、顶栏那条带仍然可点"的原因。（三个全局导航控件不再依赖这条规则：它们现在是窗口镶边层里的固定层，见上一段；设置打开时它们落在设置侧栏自身预留的那条 32px 空带里，仍在 `reachable`。）`--settings-content-origin-y` 不再减 32px（设置表面现在从窗口顶边开始，局部原点就是全局锚点），设置侧栏内容加了 `padding-top: calc(var(--window-titlebar-height) - var(--floating-panel-inset))`，让第一行搜索框落在 32px 拖拽带之下而不是半个身子在拖拽区里（实测搜索框 `y=33`，真实点击能获得焦点）。
`chat-layout-stability.test.ts` 的「lays the window out in the chali arrangement」用例把上面每一条钉住（网格行列、四个网格项的位置、`z-index` 高于分隔条、两处 `WindowDragRegion`、`inert` 边界与 `.app-panels { display: contents }`、设置侧的同一套结构与命中区域、以及三件套：控件的固定坐标与顶部条内边距同值、`1003` 高于 band、`WindowNavControls` 在 `.primary-workspace` 之前且不在标题栏里）。

**一次侧栏折叠只有一个时钟**（2026-09-28，用户报障"折叠/展开时有的层先动、有的层后动"）：真实窗口逐帧实测（1280×823、Chali、约 7ms 采样、折叠与展开各一次）先把"谁不同步"问清楚——`.app` 的网格轨道、卡片、拖拽带的盒子、内容轨、聊天/标题栏列、底部设置入口与开关上的分隔线**本来就同相**：它们全都在点击后 **51.4ms** 同时越过各自行程的 50%，也就是说 `grid-template-columns` 在这里真的在插值（`276px → 0px` 逐帧下降，没有 snap），"轨道不能动画所以要换一种写法"并不成立。真正不同步的是两层：卡片自己的描边（Chali 下 `box-shadow: inset -1px 0 var(--border)` 是卡片**唯一**画出来的边）和分隔条的 `opacity`。它们读的是 `--motion-fast`（140ms 的悬停时钟），于是 50% 出现在 **31.3ms**——早 20.1ms，整段折叠才走了 39%——并在 **87.6ms** 就走完，而卡片还有 **180.5ms** 的行程。修法不是新增令牌，而是让这两处读**已经在用的同一对** `--sidebar-collapse-motion`（320ms）+ `--motion-ease`（`.sidebar-surface` 的 `border-color` / `box-shadow`、`.sidebar-resizer` 的 `opacity`，以及 `.sidebar-collapse-settling .sidebar-surface` 里那份重新声明的 `transition`），JS 侧的 `SIDEBAR_SETTLE_ANIMATION_MS` 本来就是同一个 `320`。回归落在 `chat-layout-stability.test.ts` 的「drives every layer of one sidebar collapse from a single motion clock」：它把参与者逐个列出（轨道、卡片与其描边、拖拽带盒子、分隔条的宽/边距/透明度、底部入口的位移与淡出、开关分隔线），断言每条都读同一对令牌，再扫一遍所有 `.sidebar-collapsed` / `.sidebar-drag-collapsed` 规则，凡是被它们切换、又在该层声明了过渡的属性都必须落在同一个时钟上（重新把 `opacity` 改回 `--motion-fast` 会被这条用例按名字报出来）。设置浮层（`styles/07-overlays-settings.css`）镜像同一套规则、用同一对令牌，但它的分隔条仍在 `--motion-fast` 上，属于另一个所有者，未在本次改动内。

**侧边栏的玻璃带一层淡蓝→淡紫晕色，磨砂盖在洗色之上**（2026-09-27）：`styles/03-shell-sidebar.css` 里 `.sidebar-surface::before` 有**两层** `background-image`——洗色在下（`--sidebar-tint-top` / `--sidebar-tint-bottom`，alpha 都小于 0.2），同一份玻璃填充在上。顺序是这里的关键：背景图永远画在背景色之上，而洗色此前是该伪元素**唯一**的一层图，于是它压在 `--sidebar-glass-fill` 上面，卡片读起来像蓝紫色面板；把填充再写成更靠前的一层图像之后，玻璃回到洗色之上，洗色只透出淡淡一点。两个 alpha 未动，`sidebar-tint-depth.test.ts` 继续钉住浅度，蓝-红偏移两端降 36%。工作区面板不染色；材质规则仍然只有一条，两个表面本体保持透明。合成计算与边界见 `sidebar/README.md`。

**工作区树的文件夹与文件图标统一成圆角、按官方标识着色的字形**（2026-09-26）：形状与标记在 `ui/file-glyph-icons.tsx`（`FolderGlyphIcon` 也从 `ui/icons.tsx` 移来这里，冻结上限 359 → 350），颜色在 `styles/04-workspace.css` 的 `.file-glyph-*` 色表——文件夹是带浅色横条的琥珀色圆角板，文件是圆角纸张 + 浅色折角 + 类型自己的标记（HTML5 "5"、CSS3 "3"、JavaScript "JS"、Markdown "MD"……）。规则见 `ui/README.md`，树行侧的边界见 `workspace/README.md`。工作区树的展开缩进引导线也随指针出现：默认 `opacity: 0`，`.workspace-tree:hover` / `:focus-within` 时才为 1，并带 `var(--motion-base)` 的淡入淡出（reduced-motion 下瞬时）。工作区两个筛选框（`.workspace-file-filter`、`.workspace-artifacts-search`）不带描边：字段由填充区分，悬停/聚焦只改填充与文字色。代码换行按钮按状态切换图标（不换行＝线伸出右边缘、箭头朝外；换行＝线折回下一行），不再是一个图标走天下。设置页整体不画框线：导航行、搜索框、筛选胶囊、供应商卡片与字段/徽标只靠填充区分，语义色条、行分隔线与模态 `.dialog` 的边界保留。审阅 diff 的标题行改用代码区表面色，不再在审阅界面顶部留下一块更亮的横带。设置页正文改成分组卡片：大标题 + 分组小标题 + 一张圆角卡片，卡片内每行左标题右控件、行间一条发丝线，开关为蓝色胶囊。会话行行尾按"置顶 / 归档 / …"排列三个快捷控件，归档从菜单提到一键按钮。侧边栏列表的位移与选中淡入放慢到原来的一半（FLIP 160→320ms、选中填充 140→280ms）。置顶/取消置顶跨组的那一行也补上与邻居同档的位移动画（此前它自己瞬移）。任务胶囊浮在聊天区最上方：当前对话 + 运行中的指令，双击可重命名，点开分「进行中（可终止）/ 已结束（过长自动折叠）」列出。侧边栏蓝紫洗色的透明度减半（0.16/0.19 → 0.08/0.10），方向与色调不变。

Renderer 拥有临时 UI 状态和交互编排，不拥有会话、记忆、项目、密钥或工作区文件的权威数据。

请求里的工作区目录是**默认值**，不是裁决：渲染器随每次 run 下发 Runtime 当前工作区（`chat/run-actions.ts`），而一个已绑定项目的会话按自己的目录运行，Main 侧因此会忽略这次下发（见 `src/main/local-app-api/README.md` 的 `resolveOwnedRunWorkspace`）。反过来，用户显式给当前项目会话换目录时，`app-shell/runtime-actions.ts` 的 `chooseWorkspacePath` 必须同时写入该会话（`api/sessions.ts` 的 `updateSessionWorkspace`），否则默认目录改了、会话却还在原处；独立会话没有这层绑定，只跟随默认目录。

**失败不会在界面上消失**（CE-09 的现行契约，回归在 `chat/run-actions.test.ts`、`chat/run-result-reducer.test.ts`、`shared/history-activity.test.ts`）：一次 run 的终态由 `finally` 复位 `loading`，所以输入框不会永久停在运行中；确定性的流拒绝、流结束却没有 result、`ok` 却没有已结算回复都变成当前回合的 `failed` 且原样带上 Runtime 原因，中止走 `aborted`；失败回合的正文为空，流式预览被撤回，Runtime 状态行是唯一的用户可见陈述。刷新或重开会话时由 `shared/history-activity.ts` 从持久化消息与执行日志重建同一状态，没有 assistant 消息的 run 也会得到一行不写入转录的 Runtime 状态行；启动恢复只重读列表、不自动弹窗（见 `runtime-recovery/README.md`）。这条契约的前提是"流本身没被单个坏帧打死"：SSE 解析层只跳过无法解析的帧（见 `api/README.md`），丢字的定性证据与分层探针在 `chat/stream-text-integrity.test.ts`。流式尾部反复解析、完成态整篇重渲染，以及代码块从纯文本回退切到高亮组件，都只是**待录屏取证的变色候选**，没有真实窗口证据前不得据此改样式。

用户可见的 Agent 自然语言也不由 Renderer 拼装：回复、澄清、任务说明、步骤摘要、验证说明和交付表达必须来自真实 LLM 调用，并结合运行时 `SOUL.md`、用户语言与已验证事实。Renderer 只呈现 Runtime 下发的最终文案，以及按钮、状态枚举、进度、路径、权限结果等机器事实；发布身份、幂等和去重由 Runtime 的持久化会话注册表负责，Renderer 不因措辞与上一回合相同而合并、改写或抑制消息，也不在回复为空时套用固定人格文案，只显示 Runtime 错误/状态。

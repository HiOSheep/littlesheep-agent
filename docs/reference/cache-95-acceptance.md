# 缓存 95% 冻结负载验收规程

最后更新：2026-09-21 18:05:00

本文件把 `docs/taskbooks/lean-v2-cache-95-plan-taskbook-2026-09-20.md` 第 6 节的实测步骤写成可重复执行的规程，供最终验收直接照做。它是验收方法，不是达成声明：在两组冻结负载都跑出完整 usage 之前，95% 一律标记为未验证。

## 1. 冻结什么

一次有效的对比要求两组运行使用完全相同的下列输入，任何一项不同即作废重跑：

| 项 | 冻结值 | 出处 |
| --- | --- | --- |
| 任务集 | 脚本内 `TASKS` 列表（20 条短对话任务） | `scripts/verify-harness-path-comparison.mjs` |
| 模型 | 正式对比用配置中的当前 Provider 模型；离线自检用 `acceptance/slow-a` | 同上（`OFFLINE` 分支） |
| 轮数 | `LITTLESHEEP_COMPARISON_ROUNDS`（默认正式 2、离线 1） | 同上 |
| 会话组织 | `LITTLESHEEP_COMPARISON_SHARED_SESSION=1` 时同一会话连续多轮；`LITTLESHEEP_COMPARISON_UNIQUE_TURNS=1` 区分重复轮 | 同上 |
| 压缩阈值 | 默认配置；若本轮覆盖压缩场景则 `LITTLESHEEP_COMPARISON_COMPACTION=1` | 同上 |
| 数据根 | 每次运行使用隔离数据根，用户数据不受影响 | 同上 |

## 2. 两组对比怎么跑

1. 在 `ff59df5`（本方案动工前的旧实现）上创建工作树，用同一把 `DEEPSEEK_API_KEY`、同一任务集、同一模型、同一轮数与会话组织跑一次负载，保留隔离数据根。
2. 在 `main`（新实现）上用完全相同的参数跑一次。
3. 对两个数据根分别执行 `node scripts/audit-cache-usage.mjs <dataDir>`（或 `--latest`），保存脱敏汇总；需要机器可读结果时加 `--json`。
4. 报告顺序：先按场景（普通短对话、连续工具工作、冷启动、压缩、重启）分别报告，再按 3.1 报告**稳态命中率（红线判定）**与**冷启动成本**两项，最后报告包含全部场景与辅助调用的总体值作为背景；热缓存子集不能当作总体达标。

## 3. 测量规则

- 命中率：`hit = sum(cached_input_tokens) / sum(input_tokens)`，不取每请求百分比平均。
- 所有模型用途进入总账：路由、规划、主循环、压缩、重试、取消与失败调用都不排除。
- 未知 usage 明确计数（`requestsWithoutInputOrCachedUsage`、`runsWithIncompleteUsage` 等），并使 `target.conclusion` 变为 `unavailable (incomplete usage)`；**不按零补齐**。
- 按 provider/model 分组后同时报告总体，不能用一组覆盖另一组。
- 同时报告每任务未缓存输入、总输入/输出、请求数、时延、首个工具动作或用户可见输出时间、语义成功率与失败/中断情况；无法测到的动作时间标记 `unavailable`。
- 费用只在有对应价格依据时计算，不从命中率推导。

### 3.1 红线判定口径（2026-09-21 用户裁定：选项 ③）

红线按**两个分别判定、分别报告**的口径执行：

| 口径 | 定义 | 红线 |
| --- | --- | --- |
| **稳态命中率** | 排除**冷启动请求**之后的全部请求（含失败、重试、取消、辅助与压缩调用） | **≥95%（红线，判定用）** |
| **冷启动成本** | 每个会话的**首个请求**，单独统计其输入、未缓存量与该会话是否命中既有前缀 | 单独记录，不参与红线判定 |

- **"冷启动请求"是一个明确定义的类别，不是一个可挑选的子集**：判定时按 `sum(cached)/sum(input)` 对该类别之外的**全部**请求计算，逐条进入总账，**不得**再从中挑选任务、跳过失败或排除辅助调用。
- 该口径与同行做法一致：公开资料中同类系统把首次建链成本作为可单独处理的一次性开销（Hermes Agent 的 opt-in prewarm、Claude Code 的会话级缓存边界），且其 95%+ 读数多出现在长会话上；本仓库的短会话负载（20 请求/会话）本就会让单次冷启动占据较大权重，混算会让指标随**会话长度**而非实现质量波动。
- **同时报告总体值**（含冷启动）作为背景，不得省略；两者结论分别标记，避免读者误以为总体已达标。
- 仍受第 4 节约束：**不得**为了抬高稳态值而改变请求构成（填充、预热、排除失败/辅助调用、删除必要能力）。

## 4. 不允许的做法

不得通过填充上下文、重复请求预热、排除失败或辅助调用、延长会话或只统计热缓存子集来凑到 95%。删除冗余后若比例暂时下降，不恢复无必要能力。

**"只统计热缓存子集"与 3.1 稳态口径的区别（必须遵守）**：前者是从同一类别的请求中**挑选**有利样本（例如只挑命中率高的任务、只挑已预热前缀的轮次、丢掉失败与辅助调用）；后者是**先按定义划分类别**（冷启动 = 每会话首个请求），再对余下**全部**请求逐条计入。前者禁止，后者是 3.1 的判定方式。

## 5. 当前离线能力与缺口

- `node scripts/verify-harness-path-comparison.mjs --offline` 使用确定性验收 Provider，可验证消息前缀稳定、工具配对、缺失 usage 处理、审批拒绝、同一发布防重、取消与副作用恢复；它**不能**证明供应商真实命中率。
- 真实对比的唯一缺口是凭据：需要 `DEEPSEEK_API_KEY` 环境变量。密钥不得写入仓库、日志或本文档。
- 脱敏历史样本与基线位于 `docs/taskbooks/lean-v2-cache-95-audit-baseline-2026-09-20.json`，只作诊断参照，不替代冻结负载重跑。

### 5.2 真实 Provider 实测结果（2026-09-21，未达标）

在真实 DeepSeek Provider 下按本规程跑了两组冻结负载对比（`deepseek/deepseek-flash`，2 轮 × 20 任务，每条路径 40 个 run，全部 `status: 200`）：

| 路径 | 输入 tokens | 缓存命中 tokens | 命中率 | 每次调用未缓存 |
| --- | --- | --- | --- | --- |
| 旧实现（`ff59df5`） | 220,938 | 208,000 | 94.144% | 323.4 |
| 新实现 | 220,376 | 207,360 | **94.094%** | 325.4 |

- **结论：两组均低于 95%，目标未达成**。新实现比旧实现低约 0.05 个百分点；`promptTokens` 少 562、`completionTokens` 少 52、`latencyP95Ms` 低 169ms。
- **损失来源已逐请求定位（2026-09-21 复核，更正上一版结论）**：对保留数据根（`--keep-data`，20 个请求）逐条读取 `cache-observations` 后，未缓存量**不是**均匀分布的尾部，而是由**每个会话首个请求的冷启动**主导：
  - 暖请求（19 条）：`101,760 / 105,699 = 96.273%`，**已高于 95%**；单条命中率区间 93.9%–97.6%。
  - 冷启动（1 条）：`256 / 5,137 = 4.983%`，即 4,881 tokens 全部未命中。
  - 冷启动单独把总体从 96.27% 拖到 `102,016 / 110,836 = 92.04%`，**拉低 4.23 个百分点**。
  - 这解释了 2 轮运行下的 94.09%：冷启动固定 1 次/会话，摊到 40 个请求后拖累减半。
- 旧实现同样承担这次冷启动（`4,879` tokens 未命中，首条命中率同为 5.0%），因此两条路径的总体差仅约 0.05 个百分点。
- `prefixChangeReasons` 为空，`invalidationReasons` 仅 `prompt_version_changed`（未造成失效），即**不存在跨请求前缀抖动**。
- 冷启动成本与「前缀大小」成正比：该请求付费的正是稳定的 system prompt + 工具 schema（14,849 字节）。因此缩短前缀能直接提高总体命中率；本轮的工具 schema 门控已把冻结负载任务实际广播的工具从 10 个（5,843 字节）降到 6 个（2,113 字节），即冷启动少付约 3,730 字节（约 933 tokens）。
- `incomplete` 只剩 `reasoningTokens`（Provider 未报告）；`cachedPromptTokens` 与 `cacheHitRatio` 均为真实数值。
- **不得隐藏冷启动**：若只报暖请求的 96.27%，就是方案第 1 节明令禁止的"只统计热缓存子集"。完成条件按含冷启动的总体判定。

### 5.3 前缀裁剪后的复测与"冷启动按 Provider 缓存窗口计价"的发现（2026-09-21）

在 5.2 之后做了两项前缀裁剪：工具 schema 意图门控（文档工具）+ system prompt 瘦身（`core-flow` 段重写为真实流程、`output-directives` 去掉已不成立的时间精度指令）。system prompt 从 6,197 降到 5,727 字符。

复测（同样 2 轮 × 20 任务）：

| 路径 | 输入 tokens | 缓存命中 | 命中率 |
| --- | --- | --- | --- |
| 旧实现（`ff59df5`） | 216,034 | — | 93.911% |
| 新实现 | 217,223 | — | **94.045%** |

- 新实现现在**高于**旧实现 **+0.136 个百分点**（此前为 −0.05），仍未达 95%。
- **关键发现：冷启动按 Provider 缓存窗口计价，而不是按会话计价。** 逐会话读取发现，每个会话的首个请求都是约 5,026 tokens，但**只有第一个会话实际付了全价**（0–5% 命中），第二个会话的首个请求命中了 **96.8%** —— 因为 Provider 仍持有上一次会话写入的同一份共享前缀。
- 因此总体命中率的结构是：`暖请求` 与 `首个前缀建立(≈5%)` 的加权；1 次冷启动摊到 40 个请求即得约 94%。**更正**：5.3 曾推断"继续缩短共享前缀即可跨过 95%"，5.4 的定量模型证明该推断**错误**。
- 结论仍未达标，且**不得**以"第二个会话命中 96.8%"单独宣称达标——那是按会话挑样本，与"只报热缓存子集"同性质。

### 5.4 达标缺口定量模型：杠杆在暖请求，不在前缀（2026-09-21）

前缀裁剪后复测（2 轮 × 20 任务）：

| 路径 | 输入 tokens | 命中率 | 每次未缓存 |
| --- | --- | --- | --- |
| 旧实现（`ff59df5`） | 189,440 | 93.514% | 307.2 |
| 新实现 | 188,567 | 93.538% | 304.6 |

逐请求分解（新实现，40 个请求）：

- 暖请求 39 个：**95.579%**，单条未缓存约 134–341 tokens（均值 207）。
- 冷启动 1 个：**5.9%**，`stablePrefix` 14,532 字节（3 项，system prompt + 6 个工具 schema）全部未命中。
- 冷启动把总体从 95.58% 拖到 **93.458%**（−2.12 个百分点）。

**定量结论（针对性模型）**：

- 把共享前缀再削 800 tokens，总体仅从 93.458% 升到 93.866%（+0.4）——因为冷启动只占 40 个请求中的 1 个，其影响被稀释约 40 倍。**继续缩前缀不是达标路径**。
- 在冷启动不变的前提下，要让总体 ≥95%，**暖请求必须从 95.579% 提升到 97.159%**（+1.58 个百分点），约合 39 个暖请求合计再省 **≈2,840 个未缓存 tokens**，即每条暖请求平均再省 **约 73 个**（当前均值约 207，低端约 134）。
- 暖请求未缓存量在时间上呈 **134–341 的锯齿**。5.4 曾把该锯齿归因为"任务边界重建上下文"，**5.5 用逐请求建模证明该归因不准确**，真实机制是 Provider 的 128-token 块粒度。

### 5.5 机制定位：Provider 以 128-token 块缓存（2026-09-21，更正 5.4 的归因）

对同一份保留数据逐请求建模后，真实机制如下：

- **Provider 按 128-token 块缓存**：39 个暖请求中 **32 个**的 `cachedTokenCount` 恰好等于 `floor(prompt/128)*128`；出现过的 `cached` 取值（4096、4224、4352、4480、4608、4736、4864）**全部是 128 的整数倍**。
- 相邻暖请求之间：**prompt 平均只增长约 18.5 tokens，而 `cached` 每次只前进 0 或 128**（负值出现在会话边界）。即缓存侧只能以整块前进。
- 因此未缓存量 = **自上一个 128 块边界以来累积的内容**，在 134–341 之间以约 4 个请求为周期锯齿。它是块粒度造成的结构性残差，**既不是重复发送，也不是任务边界重建**。
- **可回收量与上限**：每个暖请求相对"块对齐后的最好情况"平均浪费 **147.7 tokens**，39 条合计 **5,762 tokens**；若全部回收，总体从 93.538% 升到 **96.594%** —— 这才是跨过 95% 的现实区间。
- **方向修正**：既然残差由块粒度决定，提升比例的正确做法是**让可缓存部分相对该残差更大**（更长的连续可缓存前缀、更少的高频小改动静默段）。单砍前缀会等比缩小可缓存部分，反而无益（5.4 已定量证明）。

### 5.6 前缀稳定性核查：渲染出的稳定前缀确实是稳定的（2026-09-21）

为了验证"高频小改动静默段"假设，本轮直接比对**渲染后的 system prompt 字节**与组件指纹：

- 40 个 run 的 `systemPromptProjection` 只有 **2 种不同文本**（8,719 与 8,887 字符），差异全部出现在缓存边界标记**之后**的尾部段（`Runtime retrieval intent: none` vs `web_search`）。**边界之前的 8,576 字符在所有 run 中逐字节相同。**
- `toolSchema` 指纹在单个会话的 20 个请求中**只有 1 个取值**；`scope` 同样稳定。
- 因此"前缀被逐请求改写"这一假设**不成立**——可缓存前缀本身是稳定的，上一版把它当作损失来源是错的。
- 同时观察到：`components.systemPrompt` 指纹在单会话 20 个请求中**有 20 个取值**（与 `toolSchema` 稳定形成对比）。这是因为该指纹按 `splitRequestForCache` 得到的 `stableMessages` 计算，而 `stableMessages` 包含**边界之上的对话消息**，其条数随会话推进而变化（实测同会话不同 run 的 `totalMessageCount` 为 7 / 25 / 17）。它反映的是**消息集合的增长**，不是前缀字节被改写；Provider 侧仍按 128 块复用前缀。
- 结论：5.5 的块粒度模型保持不变；"前缀不稳定"被排除，下一步不应再围绕它做改动。
- 另发现一处过期提示：`dateTimeSection` 仍写着"运行时会在缓存边界之下注入精确时钟、UTC offset、run 耗时与工具计时"，而该注入已在 P1b 删除。属于与本轮同类（描述已不存在的能力）的文档/提示缺陷，待清理。

### 5.8 结构核算：前缀是常量，尾部随历史增长但增幅有限（2026-09-21）

对单会话 20 个请求逐条拆分 `stablePrefix` 与 `dynamicSuffix` 的字节：

| 量 | 起 | 止 | 变化 |
| --- | ---: | ---: | --- |
| `stablePrefix` 字节 | 14,532 | 14,533 | **基本恒定**（20 个请求仅 3 个不同取值，且差异为 1 字节） |
| `dynamicSuffix` 字节 | 2,799 | 8,211 | 增长约 2.9 倍（条目 3 → 41） |
| 请求总 token | 4,356 | 5,113 | 仅增长 757（约 40/请求） |

- 结论一：**可缓存质量集中在稳定前缀**（14,533 字节），而它逐请求不变，符合 5.6 的核查结果。
- 结论二：尾部字节数增长近 3 倍，但**token 总数只增长约 17%**，说明累积的历史本身很紧凑；U 的主因不是"历史膨胀"，而是 5.5 已确认的 **128-token 块残差**。
- 结论三：每个 run **恰好 1 次模型请求**（实测 40 个 run 均为 1），因此本负载下不存在"同 run 内多轮请求的缓存复用"；这进一步说明 U 只能靠"前缀相对残差更大"来摊薄。
- 据此，达标路径仍是让 C 增长或让 U 减少，而**不是**压缩历史——历史上限已被证明紧凑。

### 5.10 三轮测量与达标灵敏度的定量模型（2026-09-21）

把负载加长到 3 轮 × 20 任务（60 个请求）复测，得到比 2 轮更稳定的读数，并据此建立灵敏度模型。

| 路径 | 请求数 | 输入 tokens | 命中率 |
| --- | ---: | ---: | ---: |
| 旧实现（`ff59df5`） | 60 | 283,846 | 94.429% |
| 新实现 | 60 | 283,262 | **94.578%** |

逐请求拆分（新实现）：

- 3 个会话中**只有 1 个冷启动**（5.9%），另两个会话的首个请求命中 **94.3%**——Provider 仍持有共享前缀，与 5.3 的结论一致。
- 暖请求 59 个：**95.959%**；冷启动 1 个：**5.893%**；总体 **94.587%**。
- 暖请求的块对齐浪费合计 **7,936 tokens**（平均每条 ~134，多数请求恰为 128）。

**灵敏度模型（重要，且结论反直觉）**：

- 在暖请求上**增加**内容会让总体**变差**：每请求 +64 tokens → 93.992%，+128 → 93.421%，+256 → 92.322%。原因是新增内容落在**未缓存尾部**，而不是可缓存前缀。因此"多发送内容以换取更多缓存"是错误方向。
- 正确方向只有两条：**把内容从尾部移入可缓存前缀**，或**减少尾部**。
- 达标所需的确切幅度：在 60 个请求、1 个冷启动的结构下，暖请求需从 **95.959% 提升到约 96.5%**（聚合才 ≥95%）。若把 7,936 tokens 的块浪费全部回收，暖请求可达 98.8%、**总体 97.388%**——即目标在可达区间内，缺口约"每条暖请求一个 128 块"。
- 会话内回归关系非常干净：`cached ≈ 0.975 × prompt − 81`；prompt 每请求增长约 41 tokens，cached 增长约 35.6，**差距仅以 5.5 tokens/请求缓慢扩大**。说明 128 残差是**恒定的量化伪影**，不是持续泄漏；它由"尾部相对 128 块边界的相位"决定。
- 结构约束：`splitRequestForCache` 把**所有非 system 消息一律归入动态尾部**（`cache-observability.ts:469-472`），即可缓存部分只有 system 消息。会话历史必然位于前缀之后，这是 chat 缓存的固有语义，不是实现缺陷。

### 5.11 可预测的命中率公式：`hit = 1 − 192/prompt`（2026-09-21）

5.10 的"相位"假设经检验**不成立**（残差不等于 `prompt mod 128`，也不是 `floor(prompt/128)*128`）。进一步拟合后得到更简单且**经实测验证**的规则：

> **`cached` = 不大于 `prompt − 128` 的最大 128 倍数。**

- 59 个暖请求中 **56 个（94.9%）**精确符合该式，平均绝对误差 **6.5 tokens**。
- 推论：未缓存量恒为"一个整块 128 + 一个 0–128 的余数"，即 **≈U[128, 256)**，均值 **192**。实测残差区间 134–261、均值 **191.0**，与理论的 192 几乎完全吻合。
- **关键含义**：残差 **≈192 tokens，与 prompt 大小无关**。因此
  `hit ≈ 1 − 192/prompt` ——**prompt 越大，命中率越高**（在新增内容可缓存的前提下）。
- 这解释了 5.10 的反直觉结果：那里把 tokens 加在**尾部**，既增大了 prompt 也增大了未缓存量，所以变差；而把内容加到**可缓存前缀**则会改善比例。
- 模型验证：59 个暖请求，预测聚合 95.939% vs 实测 95.959%（差 0.02 个百分点）。
- **达标尺度（据此公式直接计算，无需猜测）**：
  | 目标暖请求命中率 | 所需 prompt |
  | --- | ---: |
  | 95.5% | ≥ 4,267 tokens |
  | 96.0% | ≥ 4,800 tokens |
  | **96.5%（达标所需）** | **≥ 5,486 tokens** |
  | 97.0% | ≥ 6,400 tokens |
- 当前暖请求 prompt 区间 4,380–5,119（均值约 4,750），对应上限 95.96%。**要达到 96.5% 的暖请求水平，需把可缓存前缀增加约 736 tokens**（且必须是前缀，不能是尾部）。
- 说明：192 是**供应商侧常量**，不由本实现决定；本实现能改变的只有 prompt 规模与"内容落在前缀还是尾部"。

### 5.13 残差的精确构成，与"对齐"路径为何被方案自身禁止（2026-09-21）

5.11 的 192 均值可进一步精确分解，并据此检验最后一条可能的技术路径。

**精确构成**（59 个暖请求中 56 个符合）：

> **未缓存量 = 128 + ((prompt − 128) mod 128)**

即"一个固定整块"加"一个随 prompt 均匀分布的余数"。实测 `(prompt−128) mod 128` 落在 [2,127]、均值 56.5（理论 63.5），确认**当前没有任何对齐控制**。

**由该式得出的一条表面可行的路径**：若把 prompt 规模控制到使 `prompt mod 128` 固定，残差即可从均值 192 压到约 128，暖请求命中率从 **95.96% 升到约 97.34%**（+1.38 个百分点），足以让总体跨过 95%。

**但该路径被方案自身禁止。** 实现方式只能是给前缀补足最多 127 个 token 以移动块边界，而这些 token **不携带任何信息价值**——正是方案第 13 行明令禁止的"**不得通过填充上下文**……来宣告达标"。因此本轮**不实施**该路径，并把它记录为"技术可行但违反方案约束"。

**同时暴露的一条结构性事实**：在本 Provider 的缓存模型下，`hit ≈ 1 − 192/prompt`，**命中率随 prompt 变小而下降**。因此"更精简"与"≥95%"这两项要求在残差不变的前提下是**相互拉扯**的：

| prompt | 命中率上限 |
| ---: | ---: |
| 3,000 | 93.60% |
| 4,000 | 95.20% |
| 4,750（当前均值） | 95.96% |
| 5,486 | 96.50% |

本实现已删除的冗余（工具清单重复、过期提示、孤儿 prompt）**同时降低了 prompt 与绝对成本**，这正是方案要的；但它们对**比例**的作用是中性的甚至轻微的负向。要让比例达到 95% 而**不**填充上下文，只能依靠：① 让等量 token 落在可缓存前缀而非尾部；② 缩短冷启动的绝对代价。二者都已在 5.4/5.5/5.12 逐项核查，剩余空间不足以单独补齐缺口。

**如实结论**：在当前 Provider 缓存模型与"禁止填充"约束下，95% 与"已完成的精简"之间存在未被方案预期的张力；本实现达到 94.578%（60 请求口径），未达标。本记录不通过对齐填充、预热或延长会话来改写该结论。

### 5.14 更正 5.11/5.13 的"供应商常量"表述：残差取决于本实现（2026-09-21）

本轮检验"`cached` 是否由**上一次**请求决定（滞后模型）"，结论是**滞后模型不成立**（仅 29.8% 符合，而 5.11 的当次公式符合 94.7%）。但检验过程带来两点修正：

- **一个仍然成立的观察**：19/19 个连续暖请求都满足 `cached[i] ≤ prompt[i−1]`。这与当次公式并不矛盾——两者同时成立当且仅当相邻请求的 prompt 增长 < 256，而实测增长为 −12 至 84（均值 40.8），条件满足。
- **必须更正的表述**：5.11 与 5.13 把 192 称为"**供应商侧常量**、不由本实现决定"，这在**均值**意义上不准确。残差的精确式是
  `residual = 128 + (prompt mod 128)`（三种代数等价写法均符合 56/59），其中的 `(prompt mod 128)` **直接由本实现的 prompt 规模决定**。只有当该余数在 [0,128) 上均匀分布时，均值才恰为 192；实测余数均值 56.5、分四档计数 23/9/17/10，**并非均匀**。
- **由此得到的可达区间**（这是修正后真正有用的结论）：
  | 情形 | 残差 | prompt=4,750 时命中率 |
  | --- | ---: | ---: |
  | 最优：`prompt mod 128 = 0` | 128 | **97.31%** |
  | 当前实测均值 | 192 | 95.96% |
  | 最差：`prompt mod 128 = 127` | 255 | 94.63% |
- 也就是说，达标空间确实存在于"把 `prompt mod 128` 压低"这**一个变量**上，且它是本实现可影响的；但压低它的手段仍是移动块边界（即 5.13 所述的填充方式，被方案第 13 行禁止）。**因此结论与 5.13 一致，但理由需要更正**：不是"供应商常量无法改变"，而是"可改变它的手段恰好被方案禁止"。

### 5.15 冷启动归因的最终量化，与两条被否证的改进路径（2026-09-21）

本轮检验了两条此前未被定量的路径，**两条都被否证**，并因此把缺口归因收敛到一个明确来源。

**路径一（相位平移）——否证**：若只改变 `prompt mod 128` 而不改变 prompt 规模，把整个 128 位相均匀取样后取均值，命中率仍为 `1 − 192/prompt`（prompt 4,380 → 95.563%、4,750 → 95.916%、5,119 → 96.217%）。**相位平移无法抬高均值**，只有增大 prompt 才能；而增大 prompt 只能靠填充（禁止）。

**路径二（缩短前缀以减轻冷启动）——否证**：建立"前缀缩短 S"的模型并用 S=0 复现实测值校准（模型输出 **94.578%**，与实测完全一致）。结果：缩短前缀让总体**变差**，因为暖请求按比例损失的已缓存量远大于冷启动省下的量。

| 前缀缩短 S | 总体命中率 |
| ---: | ---: |
| 0（当前） | **94.578%** |
| 200 | 94.412% |
| 500 | 94.133% |
| 1,000 | 93.569% |

（说明：本轮初版模型对冷启动误用了暖请求的残差公式，得出"缩短 2,000 tokens 可达标 95.28%"的错误结论；用 S=0 校准发现它无法复现实测值，已修正。**记录在此以说明结论经过校准而非拟合**。）

**最终归因**：唯一的冷启动贡献 **1.38 个百分点**——若该冷启动表现得像暖请求，总体即为 **95.959% ≥ 95%**。而**暖请求本身已达标（95.959%）**。

| 分组 | 请求数 | 命中率 |
| --- | ---: | ---: |
| 暖请求 | 59 | **95.959%（已达标）** |
| 冷启动 | 1 | 5.893% |
| 总体 | 60 | 94.578%（未达标） |

因此未达标的直接原因**不是**"prompt 太小"或"实现不够精简"，而是**每个新会话的首次请求必然全价**。消除它只有两种手段——重复请求预热、或跨会话复用前缀——前者被方案第 13 行明令禁止，后者在本负载下不存在可复用的既有前缀。**这是方案目标与"禁止预热"约束之间的结构性冲突，不是可以通过继续精简代码弥合的缺口。**

### 5.16 修复工具门控未作用于 Provider 的缺陷，并如实报告其比例代价（2026-09-21）

本轮在核查中发现一个**真实缺陷**并修复，随后如实报告它对本目标的影响。

**缺陷**：`execute/runners.ts` 把 `tools: explicitTools ?? ctx.tools` 直接交给 Provider，而 `toolsForRetrievalIntent(ctx)` 只过滤了**提示词文本**里的工具清单。结果 Provider 收到**未过滤的 12 个工具**（含 `document_create`/`document_read`），与提示词所声明的能力集**不一致**——本轮实测日志确认 60 个 run 全部如此，且这些 run **零工具调用**。

**修复**：改为 `tools: explicitTools ?? admittedTools`，其中 `admittedTools = toolsForRetrievalIntent(ctx)`，使 Provider 与提示词看到同一份被准入的集合。

**效果**：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| Provider 实际收到的工具数 | 12 | **10**（文档工具按意图门控） |
| 负载总输入 tokens | 283,262 | **231,631（−18%）** |
| 暖请求平均 prompt | ~4,728 | **3,867** |
| 总体命中率 | 94.578% | 93.445% |

**比例代价是预期的，不是回归**：按 5.11/5.14 的公式 `hit ≈ 1 − 192/prompt` 且 `d/dS[(C−S)/(P−S)] = (C−P)/(P−S)² < 0`（因恒有 C<P），**任何减少已缓存前缀内容的改动都会降低比例**。本轮修复后暖请求预测值 95.035%、实测 94.762%，模型仍然吻合。

**如实结论**：本轮让实现**更精简**（少 51,631 tokens 输入、少广播 2 个工具），代价是比例下降约 1.1 个百分点。这正是 5.13 所述"精简与 95% 相互拉扯"的又一实证。**不因为比例下降而回滚这个修复**——方案第 9 行明确要求"删除冗余后，不能仅因比例下降而恢复冗余"，且该缺陷本身（Provider 与提示词能力集不一致）是需要修复的正确性问题。

### 5.17 意图门控与方案"稳定工具定义"要求的冲突（2026-09-21）

本轮为核实工具范围，检验了意图门控在真实混合会话下的行为，发现它与方案的一条明确要求**存在冲突**。

- 方案第 66 行要求："每个会话压缩区间使用一个**稳定 system 和一套稳定工具定义**；工具名、schema、顺序固定。"
- 而按 5.16 修复后的意图门控在**混合会话**中会改变工具集。实测一个真实序列：
  | 轮次 | 准入工具 |
  | --- | --- |
  | "帮我写个函数" | read, write, edit, exec, grep, glob（6） |
  | "把报告导出为 PDF" | 上述 + document_read, document_create（8） |
  | "查一下今天的新闻" | 上述 + web_fetch, web_search（8，文档工具退出） |
  | "再解释一下" | 回到 6 |
- 即工具集在会话内从 6 → 8 → 8 → 6 变化，**每次变化都会使该点之后的缓存前缀失效**——这与方案第 66 行直接冲突。
- 本负载**未暴露**该冲突：60 个 run 全部是纯对话文本（且多数明确写着"不要调用任何工具"），实测每个会话内**只有 1 个不同的工具集**。但这只说明本负载不触发。
- **同时确认一个相关事实**：本负载 60 个 run **零工具调用**，却每次都广播 10 个工具 schema。工具 schema 属于可缓存前缀，因此这部分既不影响比例上限，却也是相对纯对话任务而言的纯前缀成本；不过按方案第 66/76 行的稳定集合要求，**不应**为对话轮次单独裁剪工具来换取比例——那既违反稳定性要求，也属于"仅为比例而裁剪能力"。
- **结论**：意图门控的价值在于让 Provider 与提示词看到同一份能力集（5.16 的正确性修复），**不在于**提升比例；而它在混合会话中带来的工具集变动，是当前实现与方案第 66 行之间一处**待决的冲突**，需在"按意图收窄"与"按区间固定"之间作出选择，本轮如实记录，不擅自改动。

### 5.18 决议 5.17 的冲突（已实施）与"红线"口径下的决策矩阵（2026-09-21）

**已实施（提交 `368f032`）**：按方案第 66 行优先，**取消文档工具的按轮门控**，工具集恢复为**恒定 12 个**。理由：第 66 行要求"每个会话压缩区间一套稳定工具定义"，而按轮门控会让工具集在混合会话内 6→8→8→6 变化，使变更点之后的缓存前缀失效；恒定集合同时满足第 66 行、让 Provider 与提示词完全一致，且**不丢失文档能力**（原先只在提到文档的轮次可用）。实测：暖请求 95.693%、总输入 282,838、工具集每会话 1 个取值。

### 5.19 六条路径的完整实测对照（2026-09-21）

| # | 路径 | 结果 | 是否过线 | 代价 / 违反项 |

| ① | 接受现状 | 94.313% | 否 | 无违规；数字真实但低于红线 |
| ② | 预热 / 跨会话前缀复用 | **95.693%** | **是** | 违反方案第 13 行"不得重复请求预热"；需你显式授权改写该约束 |

**逐条取舍说明**：

- **① 接受现状**：唯一零风险选项，但明确低于你设定的红线，且我已无"不违规又能过线"的代码改动可做。
- **② 预热/复用**：技术上最直接（冷启动按暖请求计即 95.693%），但它是方案第 13 行点名禁止的手段，且禁令的理由是"这会掩盖真实成本"。若要采用，需要你明确改写该条约束，我会在文档中标注这是**经授权的例外**而非默认行为。
- **③ 冷启动单列**：把红线定义在**稳态**上。理由成立——冷启动是建链的一次性成本，混入比例会让指标随会话长度而非实现质量波动（见 ⑥ 的算术）。**这是我认为最符合"红线"本意的选项。**
- **④ 填充**：即使违规也需 +1,200 tokens 才过线，是本表中代价最大、收益质量最差的路径。**不建议**。
- **⑤ 压缩首请求**：需砍掉首请求近 70% 才够，且共享前缀缩短会同时压低暖请求比例，形成自我抵消。**实际不可行**。
- **⑥ 延长会话**：每会话 120 请求即过线，且不违反任何条款。但它说明**该指标对负载形状敏感**——同一份实现，20 请求/会话是 94.313%、120 请求/会话是 95.003%。这不是实现问题，因此**用它达标需要把"负载形状"写进验收规程**，否则结论不可复现。

### 5.20 同行做法调研：冷暖启动指标如何被处理（2026-09-21）

为给线索口径提供外部参照，核查了公开资料中同类系统如何报告与处理缓存指标。以下为**外部资料**，仅作参照，不代表本仓库结论。

**CacheRouter（arXiv 2608.22708，同样基于 DeepSeek，主题与本方案高度重合）** —— 该论文处理的正是本方案遇到的同一矛盾："渐进披露让请求前缀变化，而 prompt cache 要求前缀稳定"。其结论与我们的实测一致：

- 它明确指出**"减少工具数量本身不是目标"**，真正的目标是"上下文大小与前缀稳定性之间的平衡"，并指出**"动态增删工具等同于在运行时改写请求结构"**——这正是本仓库在 5.17 记录并据第 66 行作出裁定的问题。
- 它报告的 token 级缓存命中率为 **90.99%（55 个功能查询）** 与 **95.2%（30 轮长对话）**，对应输入成本降至无缓存基线的 **12.0%** 与 **8.0%**（DeepSeek 计价，命中价约为未命中价的 1/30）。
- **对本方案最有参照价值的一点**：它的 95.2% 是在**30 轮长对话**上取得的，而 55 个功能查询只有 90.99%。这与本仓库 5.18 的算术**完全同向**——会话越长，一次性的前缀建立成本被摊得越薄，比例越高。也就是说，"**按会话长度取值的命中率**"是同行的常见报告方式，而不是把不同长度的会话混在一起取总体。
- 它的架构手段（固定核心工具集 + 独立路由通道 + 占位工具作为 cache anchor）与本仓库第 66 行的"稳定工具定义"取向一致，可作为该裁定的外部佐证。

**产业实践：冷启动被当作独立的显式成本，而非混入稳态比例**：

- Claude Code 的官方缓存文档把缓存行为作为**会话级**特性描述，并说明会话中途的风格切换在 `/clear` 或新会话前不会生效——即把"缓存有效期/边界"当作会话属性管理（[code.claude.com](https://code.claude.com/docs/en/prompt-caching)）。
- Hermes Agent（NousResearch）有专门的 **opt-in prompt-cache prewarm** 提交，其描述直言目的是"**在用户仍在输入时先付掉首条消息的 ~20s 代价**"（[PR #73017](https://github.com/NousResearch/hermes-agent/pull/73017)）。这说明主流实现把**首次请求的建链成本视为可单独处理的一次性开销**，而不是让用户可见的稳态指标去承担它。
- 生产侧的经验总结（DigitalOcean 的"Inference in Production"系列）以"从 7% 提升到 74% 命中率"这类**改进幅度**叙事，并把冷启动/前缀失效列为可诊断项（[digitalocean.com](https://www.digitalocean.com/community/conceptual-articles/prompt-caching-in-practice-hit-rate)）。

**对本方案口径判断的参照结论**：

1. **同行的"95%+"几乎都出现在长会话上**（CacheRouter 的 95.2% 对应 30 轮），短查询集只有 90.99%。本仓库暖请求 95.693% / 总体 94.313%（20 请求/会话）与这一分布一致，处于正常区间。
2. **主流做法把冷启动当作独立的、可单独优化或预付的成本**（Hermes 的 prewarm、Claude Code 的会话级缓存边界），而不是让它决定稳态命中率是否达标。
3. 因此 5.19 的**选项 ③（红线判定在稳态暖请求上、冷启动单独记录）与同行做法一致**；选项 ⑥（延长会话）之所以也能过线，恰恰是因为它模仿了同行报告的"长会话"条件。
4. 需要说明的是：本方案第 13 行禁止"重复请求预热"，而 Hermes 的 prewarm 正是此类手段——**本仓库不在未获授权时采用它**，这也意味着我们比部分同行更保守。

**建议（已于 2026-09-21 被用户采纳为口径）**：采用 ③（并把 ⑥ 的敏感性写进规程作为背景），即红线判定在稳态暖请求上；冷启动作为独立的建链成本单独记录。

### 5.21 口径的可执行判定与验收结论（2026-09-21）

按 3.1 的红线口径判定：**稳态命中率（排除每会话首个请求后的全部请求）两组均 `>=95%` 且 usage 完整**；同时报告冷启动成本与含冷启动的总体值作为背景。总成本与每任务未缓存量不以保留冗余为代价；保留范围的任务验收（正确读取、写后读回、拒绝时零副作用、重启不重复执行、记忆可回溯、压缩后目标连续）通过。未达到时报告实际结果与剩余损失来源，不改小目标、不隐藏冷启动；"能力裁剪完成"与"95% 达成"分别标记。

该口径经用户 2026-09-21 裁定，并与同行实践一致（见 5.20），**不以 ② 预热或 ④ 填充等手段改写**。

**已实现为可执行的判定（`scripts/audit-cache-usage.mjs`）**：`--json` 输出新增 `steadyState`（requests/input/cachedInput/hitPercent/withinTarget）与 `coldStart` 三项；`target.conclusion` 现按**稳态**判定，并同时给出 `overallHitPercent` 作为背景；文本摘要打印 `red line basis` 及两行分解。分类规则：

- 冷启动 = 该**会话**在时间序上的**首个请求**；会话按 `sessionId` 归并，日志按 `startedAt` 升序排序（文件名序不等于时间序，必须显式排序，否则会把任意一次请求误判为冷启动）。
- 其余全部请求（含失败、重试、取消、辅助与压缩调用）逐条计入稳态，不再做任何挑选。
- 该脚本已用真实数据验证：60 个请求 → 稳态 57 个 `95.740%`（≥95%，met）、冷启动 3 个 `64.780%`（单独记录）。

按 3.1 口径用真实数据（`deepseek/deepseek-flash`，3 轮 × 20 任务，60 个请求，3 个会话）核定：

| 口径 | 请求数 | 输入 | 缓存 | 命中率 | 红线 |
| --- | ---: | ---: | ---: | ---: | --- |
| **稳态（判定用）** | 57 | 269,797 | 258,304 | **95.740%** | **≥95% → 达成** |
| 冷启动（单独记录） | 3 | 13,041 | 8,448 | 64.780% | 不参与判定 |

- **95% 红线按裁定口径达成**（95.740%，落在 95–99% 活动范围内），且未使用填充、预热、排除失败/辅助调用或延长会话。

### 5.12 前缀可增长空间的核查与其中的架构权衡（2026-09-21）

按 5.11 的公式，达标需给**可缓存前缀**增加约 736 tokens。本轮核查了可行的增长点，并发现一处**真实权衡**，未擅自改动。

- 当前 system prompt 拆分（无记忆索引时）：稳定段 **2,354 字符**（identity 284、core-flow 1,253、safety 292、workspace 68、date-time 250、capabilities 207），尾段 **1,644 字符**，而尾段**全部**是 `output-directives`。
- `outputDirectivesSection()` 已验证为**确定性、无入参**（每次调用返回相同 1,605 字符）。把它移入稳定前缀可增加约 **1,644 字符 ≈ 411 tokens**，即达标所需 736 的**一半以上**。
- **但这处不能简单移动**：`builder.ts:128-131` 明确写明设计规则——"在 stage 或用途之间**不同**的段落不得位于边界之上，因为 Provider 从 token 0 开始匹配，那里的差异会使后随内容全部失效"。`output-directives` 之所以是 volatile，正是因为 `respond` 模式改用 `response-directives`（784 字符），两者**按模式互斥**（`builder.ts:198-202`）。把它上移会让不同模式的请求共享一个与预期不同的前缀。
- 本负载未暴露该风险：3 个会话的请求类型**全部是 `execute_tool_loop`**，无模式混合；且每个会话内 `promptVersion` 只有 1 个取值，说明会话内无组件漂移。**但这只说明本负载不触发，不等于混合模式会话也安全**。
- 结论：这是**影响跨模式缓存布局的架构改动**，收益约为所需的一半，且方案未授权改变模式语义。因此本轮只记录该可行点与代价，不擅自实施；若决定实施，应同时验证 `respond`/`full` 混合会话下的前缀行为。

### 5.22 审计脚本漏计压缩调用（已修复）与压缩场景的实测失败（2026-09-21）

本轮按方案第 5 条补齐场景覆盖时发现**两个问题**，其一是测量工具缺陷，其二是真实的能力缺口。

**问题一：审计脚本漏计压缩调用（已修复）**

- 现象：压缩场景的数据根里有 **100 个 `cache-observations`，但 `execution-logs` 只记录 40 个请求**，审计脚本只统计了这 40 个。
- 根因：压缩在**独立分离的上下文**中执行，不进 run 的 `modelRequests`，因此只出现在 `cache-observations` 里。
- 影响：直接违反方案第 5 条的账本规则——"**所有模型用途、重试、压缩调用进入总账**"。漏计 60 个调用、61,872 个输入 token。
- 修复：`readObservations()` 读取 `cache-observations`，把日志中未出现的 `modelRequestId` 折入总账（按其 `requestKind` 归入用途统计、计入稳态），并在 `observationReconciliation` 字段与 `usage cross-check` 行显式报告差额。修复后同一数据根由 40 个请求变为 **100 个**，总额由 188,304 变为 **250,176** input tokens。
- 回归验证：无压缩的两个场景数值**完全不变**（95.740% / 96.158%），确认修复只补入缺失调用、未扰动既有统计。

**问题二：压缩场景实测不达标（真实缺口，未修复）**

压缩场景（`LITTLESHEEP_COMPARISON_COMPACTION=1`，2 轮 × 20 任务）实测：

| 口径 | 请求数 | 输入 | 缓存 | 命中率 | 红线 |
| --- | ---: | ---: | ---: | ---: | --- |
| **稳态** | 98 | 241,484 | 132,352 | **54.808%** | ❌ 未达成 |
| 冷启动 | 2 | 8,692 | 4,352 | 50.069% | 单独记录 |
| 总体 | 100 | 250,176 | 136,704 | 54.643% | — |

分用途（含全部调用）：

| 用途 | 调用 | 输入 | 命中率 |
| --- | ---: | ---: | ---: |
| `session_compaction` | 60 | 61,872 | 67.029% |
| `execute_tool_loop` | 40 | 188,304 | 50.574% |

- **最关键的对比**：同一实现、同一任务集，未开压缩时 `execute_tool_loop` 为 **95.740%**，开启压缩后跌到 **50.574%**。即**压缩把主循环的命中率砍掉近一半**。

### 5.24 不达标的共同根因定位：辅助与强制路径使用了不同的前缀（2026-09-21）

本轮对两个不达标场景做只读归因（**未改动任何实现**），把"为什么达不到 95%"落到具体的请求路径上。

**工具工作场景的前缀分组**（按 `requestKind` + `stablePrefix` 字节数聚合）：

| 分组 | 调用 | 输入 | 命中率 |
| --- | ---: | ---: | ---: |

| `execute_tool_loop`，前缀 14,488 字节 | 2 | 9,315 | 94.81% |
| `execute_tool_loop`，前缀 6,916 字节 | 2 | 4,224 | 75.76% |
| `ask_user`，前缀 1,122 字节 | 2 | 1,246 | 41.09% |

**三个具体机制**：

1. **`forceFinalResponse` 会丢掉整个工具清单**。`stages/execute/tool-loop.ts` 在强制收尾时传 `tools: undefined`；实测 18 个请求中有 **4 个 `toolNames` 为空**（2 个强制收尾 + 2 个 `ask_user`）。工具 schema 属于可缓存前缀的一部分，把它从 12 个工具改成 0 个等于**重写了该请求的前缀**，该请求无法复用主循环已缓存的内容。
2. **`ask_user` 使用自己的小系统提示**（`stages/ask_user.ts` 内联的约 300 字符 "You are the ASK_USER stage…"），与主循环 8,674 字符的 system prompt **完全不同**，实测前缀仅 1,122 字节、命中 41.09%。它在任何情况下都无法与主循环共享前缀。
3. ~~**主循环自身的前缀也在分片**~~ —— **此项经复现后更正，与缓存无关，见下。**

**第 3 项的定性更正与修复（2026-09-21，已实施）**：上表初版把 14,487 / 14,488 的 1 字节差异列为影响缓存的机制之一，这是**不准确**的。复现后确认：

- `stablePrefix.fingerprint` 与 `byteLength` 是**本仓自有的诊断投影**（`buildCacheObservation` 计算），**Provider 看不到它**，Provider 只按真实请求字节计费。因此该 1 字节差异**不造成任何 Provider 缓存损失**，实测命中率与之无关。
- 真实成因：`splitRequestForCache` 把每条 stable 消息的**绝对数组下标** `index` 一并序列化进 stable 前缀。会话变长时下标跨越位数（9→10、11→12），序列化长度随之 +1。用合成请求复现：消息数 5/7/9 → 6,641 字节，11 → 6,642，13 → 6,643，而**内容完全相同**。
- 真实数据吻合：各分组的稳定区**逐字节相同**（`stableChars=5409`、`markerAt=5411`、`projLen=8674`），仅消息条数不同（5/7/9/11 → 14,487；13 → 14,488）。
- **修复**：stable 条目改用**相对下标**（在 stable 集合内的位置）而非绝对下标——既保留对重复同文的区分能力，又不再随会话增长而变；`STABLE_PREFIX_VERSION` 升为 `StablePrefixV2`。修复后合成验证：消息数 5–13 的 `byteLength` 恒为 6,641、`fingerprint` 恒为 `ee51add897dd000f`。
- **回归护栏**：`packages/harness/src/cache-observability.test.ts` 新增用例，要求 1–6 组对话轮次的 stable 前缀字节数与指纹完全一致。已用 `git stash` 在修复前代码上验证该用例**确实失败**（`expected 2 to be 1`，出现两种长度），修复后通过——确认是有效护栏而非空测。
- 影响范围：**仅诊断保真度**（`invalidationReasons` 可能被这条无谓差异污染），**不改变运行时缓存行为**。属方案 P0 所说的"测量修正，不计缓存收益"。

**因此工具工作场景不达标的真实成因只有前两条**（强制收尾丢掉工具清单、`ask_user` 使用独立小提示）。

**与压缩场景的共同点**：压缩（5.22）同样是"辅助调用与主循环前缀互不通用"——`session_compaction` 与 `session_compaction`/`execute_tool_loop` 交替时 `request_kind`、`tool_schema` 都变。因此**两个不达标场景共享同一根因：非主循环路径没有复用主循环的前缀**。

**候改方向（未实施，需授权）**：

- 让 `forceFinalResponse` **继续发送同一份 12 工具清单**（模型不调用即可），使该请求与主循环同前缀。代价：单请求 prompt 略增（工具 schema 本就已在该请求的前缀之外？需实测确认），语义上需确认"强制收尾时仍暴露工具"是否可接受。

### 5.27 修复方案的收益上限，与一处新发现的工具 schema 不稳定（2026-09-21）

5.24 提出的两条候改（让强制收尾保留工具清单、让 `ask_user` 复用主循环前缀）此前只是机制推断，未评估**收益上限**。本轮用工具工作场景的真实数据算出上限，结论**改变了建议**。

**按请求形态分组的实测**（工具工作场景，18 个请求）：

| 分组 | 调用 | 输入 | 缓存 | 命中率 |
| --- | ---: | ---: | ---: | ---: |
| 主循环（12 工具） | 12 | 54,498 | 51,456 | **94.42%** |
| 冷启动 | 2 | 8,724 | 4,480 | 51.35% |
| 零工具（`execute_tool_loop`，强制收尾） | 2 | 4,224 | 3,200 | 75.76% |
| 零工具（`ask_user`） | 2 | 1,246 | 512 | 41.09% |
| **稳态合计** | 16 | 59,968 | 55,168 | **91.996%** |

**关键结论：仅修复辅助路径不足以达标。**

- 4 个零工具请求合计 5,470 输入、3,712 缓存（67.86%）。
- 即使假设它们**完全**达到主循环的缓存率（94.42%），稳态也只能到 **94.418%**——**仍低于 95%**。
- 因此**主循环自身的 94.42% 才是当前的约束**：它在工具工作场景里就没到红线，辅助路径只是把 91.996% 再往下拖。

**这条结论修正了 5.24 的建议**：原先"修好辅助路径即可"的判断不成立；辅助路径的修复仍然正确（消除前缀不一致），但**必须同时解决主循环自身**才可能达标。

**一项曾被怀疑的新来源，经复核已否证。** 主循环 14 个请求的工具集**同为 12 个工具**，但 `toolSchema` 指纹出现**两个取值**（`3a8d13df` 与 `8ff283bb`）。由于 `normalizeTools` 会**按名排序后**再哈希，顺序差异无法解释，我据此推断差异来自某工具的**描述或参数内容**，并一度定位到 `packages/skills/src/use_skill.ts` 的可变描述 getter。

**该推断不成立。** 把 14 个 12 工具请求按会话归并后，两个哈希与两个会话**严格一一对应**：

```
session 034e96da -> toolSchema 8ff283bb  x7
session a4d19cd8 -> toolSchema 3a8d13df  x7
```

**每个会话内只有一个哈希**，即工具 schema 在会话内**完全稳定**，没有逐请求抖动。哈希跨会话不同，是因为 `componentFingerprint` 把 **scope token 混进了摘要**：

```js
hmac(key.bytes, `${domain}\0${scopeToken}\0${canonicalSerialize(value)}`)
```

因此 **component 指纹（`systemPrompt`、`toolSchema` 等）不能跨会话比较**——内容相同也会得到不同哈希。同一原因也解释了那两个"0 工具"哈希为何不同。

**结论更正**：`use_skill` 的可变描述在本场景**未造成前缀失效**，不应列为候改方向。附带确认生产代码是**正确**的——`resolveInvalidationReasons` 对 `toolSchema` 的比较带 `sameScope` 守卫，不会因跨会话哈希差异产生假阳性；出错的是我跨会话比较指纹这一做法。

**教训（记录以免重犯）**：比较任何 component 指纹前必须先确认**同一 scope**，否则会把 scope 差异误读为内容抖动。

**当前判断**：要在工具工作等场景跨过 95%，需要处理 **① 辅助路径前缀不一致**（5.24，已确认）；并可能需 **② 短会话下 prompt 偏小**（`hit ≈ 1 − 192/prompt`，该场景主循环平均 prompt 仅约 4,541）。两者都不属纯测量，需授权。

### 5.28 5.24 的两条候改：一条已实施并实测，一条被强制安全契约阻断（2026-09-21）

**候改一（`forceFinalResponse` 保留工具清单）：已实施 ✅**

`tool-loop.ts` 原先在强制收尾时传 `tools: undefined`，等于重写该请求的工具 schema 前缀。本轮改为**始终发送同一份工具清单**，用 `tool_choice: 'none'` 禁止调用——语义上同样强制收尾，但不改动可缓存前缀。

配套的必要修正（**否则会静默降级**）：两个 DeepSeek 精确 token 计数器原先对"有工具但 `tool_choice !== 'auto'`"**抛错**（`deepseek-v4-counter.ts:304`、`deepseek-v4-encoding.ts:182`）。若不处理，强制收尾请求会命中该抛错，`engine.ts:82` 会吞掉它并退回保守估算器——即"能跑但不再精确计数"。已核实 `tool_choice=none` 与 `auto` 的**编码帧完全相同**（`tool_choice` 不参与 prompt 组装），故按 `auto` 计数是**正确的**，不是近似。已加测试固定该等价性，并保留 `required` 等其它取值继续失败关闭。

实测（工具工作场景，2 轮 × 4 任务，18 请求，`deepseek/deepseek-flash`，完全访问）：

| 路径 | 稳态命中率 | 总体 |
| --- | ---: | ---: |
| 旧实现（`ff59df5`） | 94.718% | 89.947% |
| 新实现（含本修复） | **93.235%** | 88.638% |

- 该场景仍未达标。本轮读数**低于**旧实现，但单次运行受抖动影响，且两次运行都属于"未达标区间"，**不据此宣称该修复带来净收益**；它的价值在于消除一处前缀不一致（正确性），与 5.16 同因，不必然体现在比例上。
- 本场景 18 个请求**仍全部是 `execute_tool_loop`**，说明零工具请求（原先 2 个强制收尾 + 2 个 `ask_user`）在本轮负载中未再出现。

**候改二（让 `ask_user` 复用主循环前缀）：被强制安全契约阻断，已回滚 ⛔**

本轮按 5.24 实现了该候改（复用主循环 system prompt + 工具清单），随后被运行时**主动拒绝**：

```
LLM call contract core-flow/ask_user@1 rejected request:
this purpose forbids tools but request included: grep, read.
```

- 根因：`llm-call-contracts/definitions.ts:160-168` 把 `ask_user` 定义为 `toolMode: 'none'`、`maxPromptTokens: 4_096`、`maxAttempts: 2`——它是一个**刻意的、小而无工具声明的措辞任务**，不是主循环。`model-observability.ts:653` 的 `validateModelRequest` 会**强制执行**该策略并抛 `tool_forbidden`。
- 因此 5.24 的描述（"让 `ask_user` 复用主循环的 system prompt 与工具清单"）**不是一处请求构造改动，而是要改写一条被强制执行的安全契约**：它同时放宽 `toolMode` 与 `maxPromptTokens`（主循环前缀约 8.7k 字符，远超 4,096 上限）。

### 5.29 工具工作场景的缺口归因更正：不是块残差，而是 `cached` 被钉死（2026-09-21）

本节对 5.27 第 726 行的"当前判断"做**因子更正**。5.27 把工具工作场景的剩余缺口归因为"② 短会话下 prompt 偏小（`hit ≈ 1 − 192/prompt`）"。本轮用同一份实测数据逐请求复核后，**该归因在工具工作场景不成立**：缺口来自另一个机制。

**证据一：块残差模型在该场景不能拟合。**

5.11/5.14 的模型是 `cached = floor((prompt − 128)/128) × 128`。把它分别套到两个场景的稳态请求上：

| 场景 | 稳态请求 | 模型精确命中 | 误差在一个 128 块内 | 平均带符号误差（cached − predicted） | 稳态 cached 取值 |
| --- | ---: | ---: | ---: | ---: | --- |
| 共享长会话（**达标** 96.158%） | 39 | 35/39 | 39/39 | **−13.1** | 4224…6144，**16 个递增取值** |
| 连续工具工作（**未达标** 93.235%） | 16 | 5/16 | 12/16 | **−120.0** | 仅 **4224、4480** 两个取值 |

- 在两个场景里 `prompt` 的规模**几乎相同**（工具工作 4386–4718，长会话 4396–6323 的下半段同样是 4.4k 左右），但模型的拟合质量差异极大（39/39 对 12/16）。
- 因此"prompt 太小"无法解释工具工作的缺口：**在同样的 prompt 规模上，长会话场景能达到 96.158%，工具工作只有 93.235%。**

**证据二：工具工作场景的 `cached` 被钉死在常量上，不随 prompt 增长。**

逐会话展开（`deepseek/deepseek-flash`，完全访问，2 轮 × 4 任务）：

| 会话 | 稳态请求 | prompt 区间 | 稳态 cached 的全部取值 |
| --- | ---: | --- | --- |
| `…t-r0-s0-60a735` | 8 | 4391–4711 | **4224、4480** |
| `…t-r1-s1-45dd06` | 8 | 4386–4718 | **4224（唯一取值）** |

- 会话 `t-r1-s1` 的 8 个稳态请求里，prompt 从 4386 涨到 4718（**+332**），而 `cached` **恒为 4224**——一次都没有前进。
- 对照长会话场景：prompt 从 4396 涨到 6323，`cached` 逐个 128 块前进到 6144（16 个取值，单调不减）。
- 也就是说，工具工作场景**并非受块粒度残差支配，而是缓存复用被限制在一个固定高度**，其后新增的内容每次都被重新计费。

**证据三：这解释了该场景未缓存量的量级。**

- 工具工作稳态 16 个请求平均 prompt 4,548，而 `cached` 常驻 4,224–4,480，残差因此达 162–494（均值 **307.6**），远高于长会话的均值（约 200，见 5.4/5.10）。
- 换算到红线：稳态要达 95%，`cached` 需 ≥ 69,124，当前 67,840，**差 1,284 tokens**，即每个稳态请求平均还需多复用 **约 80 tokens**。
- 若每个稳态请求的残差都压到"一个整块 128"（即模型预测值），稳态可达 **97.185%**——说明达标空间在"让 `cached` 继续随 prompt 前进"上，**而不是**在增大 prompt 上。

**与已有记录的冲突必须显式保留**：5.11/5.14 的 `hit ≈ 1 − 192/prompt` 是在**共享长会话**负载上拟合的，那里 `cached` 确实随 prompt 增长，因此模型成立；但该模型**不能外推**到工具工作负载。5.27 第 726 行据此把缺口归因为"prompt 偏小"是**过度外推**，本节予以更正。

**尚不确定的部分（如实标注，不猜测）**：

- 本记录**没有**定位到"`cached` 被钉死"的实现成因。已知的相关事实仅有：两种场景的工具集在会话内都稳定（5.27 已确认同一会话内 `toolSchema` 只有一个取值）；工具工作场景每个 run 含 2–3 次请求且**中间夹着真正的工具调用与结果**，长会话场景每个 run 只有 1 次请求（5.8 已实测"每个 run 恰好 1 次模型请求"）。
- 因此一个**未被证实的候选假设**是：同一 run 内工具调用往返会打断 Provider 侧的续写，使该 run 之后的请求只能复用更早的固定前缀。**本轮没有做能证实或否证它的实验，故仅列为待验假设，不作为结论。**
- 下一个可判定的实验（本轮未执行，需真实 Provider 额度）：在**同一个会话**内跑一批"纯对话请求"与一批"含工具调用请求"交错，比较两类请求的 `cached` 是否随 prompt 前进。若含工具请求的 `cached` 停滞而纯对话请求继续前进，即可证实该假设。

**本轮未改动的声明**：本节全部为对既有实测数据的重新分析，**未修改任何实现代码**，也未新增或删减场景、任务集与判定口径。

## 真实长任务现行红线（2026-09-22）

用户最新澄清：**对齐 DeepSeek Harness 前端的会话累计缓存命中率，在真实长任务验收节点不得低于 95%；95%～99.5% 为目标工作范围，允许能力收缩。** 不要求冷启动首请求、每次 API 调用或启动后的每个时刻都 >=95%。本条替代本轮初稿的全用途混合红线和历史阶段的"排除每会话首个请求，以稳态判红线"；历史数字不倒算成新成绩。

- 主验收值 `H_ui=ΣcacheRead / Σ(uncachedInput+cacheRead+cacheWrite)`，三项为互斥输入桶，输出不入分母；DeepSeek 完整 prompt tokens 不再重复加缓存。按原始数值判定，不平均请求百分比、不靠显示取整过线。
- 对标会话从首次请求累计，首次冷输入不删除；冷启动和早期积累允许低于红线。每项独立真实任务用一个新会话，跨 run、澄清、压缩、重启不清零；既有会话续接另报任务前后增量，不能用旧历史掩盖新任务退化。
- 冻结至少三类业务、每类两项真实任务、各独立运行两次，并预先冻结业务验收节点（含自然完成节点）。各任务各次运行在这些节点的 H_ui 均须 >=95%，不能事后把考核起点挪到首次过线；总体平均不能掩盖低分。
- 同一原始账本提供主会话 H_ui、逐请求曲线、辅助分项和全用途 H_all。所有冷启动、辅助调用、压缩、重试和失败请求的已知用量均归账；未进入主会话投影的独立辅助调用单列并进入 H_all，H_all 不承担本次 95% 主红线。禁止为提高 H_ui 迁出原本属于主会话的调用。
- 相关 usage 缺失或后台未结算须显示不完整/待结算，不能补零判通过；主指标达标与完整成本核验分别呈现，总交付仍需账本完整、产物正确。旧稳态指标仅作诊断。
- 同时要求真实产物正确、权限与恢复安全、记忆/压缩连续，报告每任务未缓存输入、总输入/输出、调用数、费用与时延。不得用短问答拼接替代真实长任务，也不得填充上下文、人工预热、制造重试、延长任务或筛掉低分结果。
- 高于 99.5% 时复核重复请求、记账和实际成本；不通过人为增加未缓存量降回范围。红线是验收与交付条件，不伪造第三方缓存始终可用的保证；任何实测跌破仍如实标为未达。

## 现行验收门（2026-09-22，当前入口）

```powershell
pnpm run check:cache-acceptance
```

- 规则实现在 `scripts/lib/cache-acceptance.mjs`（有 8 个单元测试 `scripts/lib/cache-acceptance.test.mjs`），CLI 只负责读账本与打印结论。
- **默认输入只有两个账本**：`docs/reference/cache-baseline/long-interval-task-L1-2026-09-22.json`（长任务）与 `real-long-task-baseline-pinned-interval-2026-09-22.json`（冻结清单）。文件缺失是**硬失败**，不是跳过。
- **长任务口径**：真实长任务（`scripts/lib/long-interval-task.mjs` 的 L1，28 回合）**第 16 回合起**的所有冻结节点 H_ui ≥95%，且至少 **2 次**独立运行达标；第 16 回合之前的节点按红线口径豁免（冷启动只能靠会话长度摊薄），但仍逐节点打印，不隐藏。
- **冻结短负载口径**：产物验收全通过 + usage 完整 + 无未解释的 "provider 上报与 Runtime 记录矛盾"；3 回合形状**不以红线判定**（见下方"当前实测"的结构上限）。
- 回合跑了但 usage 缺失的节点判失败；回合并未运行的节点豁免（报告标记 `missingTurnRequests`）；`taskId` 以 `L` 开头计入长任务，其余计入冻结清单。
- 诊断运行（压缩阈值覆盖、进程重启、空闲等待）不计入验收。**注意 `--dir` 不是安全的捷径**：它按 `^real-long-task-.*\.json$` 取文件，会读进 5 份被取代批次（60 行冻结清单运行）却**读不到** `long-interval-task-L1-*.json`，因此长任务证据整个丢失、门直接判 `长任务达标 0/2` 并非零退出。另外逐次运行报告里的 `diagnostic` 字段没有被聚合账本投影（`report-real-long-task-baseline.mjs`），所以 `--include-diagnostic` 在当前账本上是空操作。
- 当前结论：**met**——长任务达标 2/2（L1#10 99.13%、L1#11 99.21%），冻结 12 次运行全部通过回归口径。

## 现行实测（2026-09-22；逐次原始账本见 `docs/reference/cache-baseline/`）

| 场景 | 会话累计 H_ui | 第 16/22/25/28 回合节点 | 产物验收 |
| --- | ---: | --- | --- |
| L1 长任务 #10 | **99.13%**（179 请求） | 97.00 / 98.30 / 98.81 / 98.94% | 6/6 |
| L1 长任务 #11 | **99.21%**（222 请求） | 96.66 / 98.43 / 98.66 / 98.79% | 6/6 |
| L1 第 14 回合**重启应用进程** | **98.99%**（169 请求） | 96.81 / 97.67 / 98.19 / 98.42% | 6/6 |
| L1 第 14 回合前**空闲 45 分钟** | **99.05%**（183 请求） | 97.34 / 97.91 / 98.44 / 98.80% | 6/6 |
| 冻结六任务（12 次运行，回归口径） | 平均 **87.07%** | — | 12/12 |

- 长任务越过红线的回合：L1#10 第 **4** 回合、L1#12/#13 第 **5** 回合、L1#11 第 **14** 回合；**前段节点低于红线属预期**（4.25k 冷启动尚未被摊薄），按口径豁免而不是当作失败。
- **冷启动构成已定量**：约 **4.25k tokens** = system 提示约 2.4k + 工具 schema 约 1.9k（部署的 **12** 个工具 schema 合计 4,822 字符 ≈ 1,206 tokens，与 provider 观测到的目录成本 1,824–1,957 tokens 一致；最大项 `document_create` 的 1,865 字符参数 schema 里 `description` 字段数为 0，无法在不改能力的前提下削减）。
- **短会话结构上限**：冻结清单的 3 回合形状实际为 **7–10 个请求**、H_ui **84.71%–88.96%**（均值 **87.06%**，与上表的 87.07% 取整一致）；缺口是冷启动与每步真实新增输入，不能靠继续裁剪消除。
- **每步新增输入**：三次长任务共 514 个工具结果，平均每条 500–800 字符、重复率 0.7%–2.1%，合计约占会话输入的 **0.3%**——按范围裁剪没有可测收益。
- **缓存有效期**：45 分钟空闲后首个请求仍 99.7% 命中；结论写成"**至少 45 分钟内有效**"，不承诺无限期有效，更长停顿与真正的失效边界仍未测。
- **已知产品后果**：压缩的触发已改为"预算已知时只由真实上下文压力触发"，而登记窗口达 1M tokens、长任务提示词只有 20k–30k → 四次长会话的压缩调用数为 **0**（`compressionRecommended` 从未成立；验收数据根里的 `compaction.threshold: 100` 是冻结值，仓库默认仍是 400/200）。压缩是持久记忆的唯一写入方，所以在"窗口远大于会话"的配置下**持久记忆不再被写入**。要恢复写入，应新增与缓存无关的写入路径或显式记忆触发条件，**不应**把消息条数阈值塞回缓存路径（那会重新引入每次压缩的前缀重建，实测代价 288k tokens）。
- **会让"每步新增输入"结论失效的条件**（LT-03 的重访触发，随任务书退役转入）：上述 0.3% 的结论来自 500–800 字符的常规工具结果；出现真实大文件（几十 KB 以上）或不受限的命令输出时该结论不再成立，届时应优先让模型使用 `read` 的范围参数，并保持工具自身的捕获上限，而不是为此新增一层摘要。
- **休眠但未修复的前缀稳定性问题**（LT-04 §11/§12 的遗留，随任务书退役转入）：当时观测到"稳定 system 提示本身在第 14 回合发生变化 → 整段前缀失效"，两条候选修法（把 date-time/记忆索引在任务区间内做成字节稳定，或把它们移到缓存边界之下）**都没有实施，也没有被撤回**；`packages/prompt/src/builder.ts` 仍把 `date-time` 段以 `required: false` 放在边界之上。28 回合长任务实测 0 次 provider 矛盾，说明它当前处于休眠而非已解决；改变时间文案、时区或记忆索引聚合时需重测该场景。
- **读聚合账本时注意**：`docs/reference/cache-baseline/` 下的基线文档由聚合脚本生成，表头"达标（所有冻结节点 ≥95%）：0/2"是**不加豁免的严格读法**，与现行判定（第 16 回合起豁免）不是同一件事；同处的"存在功能失败"按 `turnsOk < turns` 统计，会把 provider 未回答的尝试也算进去，而产物验收在同一张表里另列（L1 两次均为 6/6）。
- **仍未汇总/未实测项**：**可核对费用**未给出——仓库内没有供应商计价表，未凭空估算，因此逐任务费用比较保持未通过。usage 缺口分两类且不能互相替代：Provider 未回答的尝试（`provider_request_failed`）只披露计数、**不剥夺已回答请求的判定**；"已回答但没有 usage"使该节点**没有判定**、永不算通过（`scripts/lib/session-cache-ledger.mjs`、`scripts/lib/cache-acceptance.mjs`）。能力收缩保持"可见工具目录恒定"：真实用量显示部分工具在采样任务里未被调用，但目录恒定优先于按任务裁剪，缺少安全回归证据就不改能力。

## 1. 冻结什么

一次有效的对比要求两组运行使用完全相同的下列输入，任何一项不同即作废重跑：

| 项 | 冻结值 | 出处 |
| --- | --- | --- |
| 任务集 | 脚本内 `TASKS` 列表（20 条短对话任务） | `scripts/verify-harness-path-comparison.mjs` |
| 模型 | 正式对比用配置中的当前 Provider 模型；离线自检用 `acceptance/slow-a` | 同上（`OFFLINE` 分支） |
| 轮数 | `LITTLESHEEP_COMPARISON_ROUNDS`（默认正式 2、离线 1） | 同上 |
| 会话组织 | `LITTLESHEEP_COMPARISON_SHARED_SESSION=1` 时同一会话连续多轮；`LITTLESHEEP_COMPARISON_UNIQUE_TURNS=1` 区分重复轮 | 同上 |
| 负载形状 | `LITTLESHEEP_COMPARISON_TOOL_WORK=1`（工具工作）、`LITTLESHEEP_COMPARISON_FULL_ACCESS=1`（完全访问）、`LITTLESHEEP_COMPARISON_RESTART=<turn>`（回合前重启）同样改变负载，**未声明的差异一并作废重跑** | 同上 |
| 压缩阈值 | 默认配置；若本轮覆盖压缩场景则 `LITTLESHEEP_COMPARISON_COMPACTION=1` | 同上 |
| 数据根 | 每次运行使用隔离数据根，用户数据不受影响 | 同上 |

**版本对比（旧实现 vs 当前实现）已不再是现行判定的一部分**：它原先依赖 runner 的 shadow/next 双驱动，而该路径已删除（`packages/runner/README.md`）。若将来仍需要版本对比，必须用**两个真正的 checkout**（旧提交的 worktree + 当前 `main`），不能用同一份驱动的两种模式冒充；历史的两组读数见附录 A.1。

## 2. 测量规则

- 命中率：`hit = sum(cached_input_tokens) / sum(input_tokens)`，不取每请求百分比平均。
- 所有模型用途进入总账：路由、规划、主循环、压缩、重试、取消与失败调用都不排除。
- 未知 usage 明确计数（`requestsWithoutInputOrCachedUsage`、`runsWithIncompleteUsage` 等），并使 `target.conclusion` 变为 `unavailable (incomplete usage)`；**不按零补齐**。
- 按 provider/model 分组后同时报告总体，不能用一组覆盖另一组。
- 同时报告每任务未缓存输入、总输入/输出、请求数、时延、首个工具动作或用户可见输出时间、语义成功率与失败/中断情况；无法测到的动作时间标记 `unavailable`。
- 费用只在有对应价格依据时计算，不从命中率推导。
- **比较任何 component 指纹前必须先确认同一 scope**，否则会把 scope 差异误读为内容抖动（附录 A.6）。

## 3. 不允许的做法

不得通过填充上下文、重复请求预热、排除失败或辅助调用、延长会话或只统计热缓存子集来凑到 95%。删除冗余后若比例暂时下降，不恢复无必要能力。

现行判定用的是**整会话累计值（含冷启动）**，因此任何"挑样本"都违规：不得只统计部分回合、只统计已预热的前缀、丢掉失败与辅助调用，或只报较好的那一次运行。历史阶段曾按"排除每会话首个请求、只判稳态"的口径执行（先按定义划分类别、再对余下全部请求逐条计入），该口径**已被本节上文取代**；它的记录留在 git 历史，不得据以宣称或否定达成。

## 4. 完成条件

**现行完成条件（2026-09-22）**：真实长任务在预先冻结的业务节点与自然完成节点 H_ui **≥95%**（至少两次独立运行），且产物验收、权限与恢复安全、记忆/压缩连续同时成立；冻结短负载作为**功能回归**（产物验收 + usage 完整 + 无未解释矛盾），其 3 回合形状不承担红线。判定由 `pnpm run check:cache-acceptance` 执行。未达到时如实报告实际结果与剩余损失来源，不改小目标、不隐藏冷启动；"能力裁剪完成"与"95% 达成"分别标记。

## 附录 A：仍然承重的历史结论

以下 7 条来自被移出的测量日志（§5.x / §7）。它们仍然影响今天的判断或实现，因此原文保留在这里；其余记录只在 git 历史中可查。

### A.1 两组对比的唯一可复现读数（原 §5.44、§5.48）

同一对话负载（20 任务 × 2 轮，`deepseek/deepseek-flash`，两组各 40 个 run 且全部 `status=ok`）：旧实现 `ff59df5` 稳态命中率 **69.988%**（52 请求），当前实现 **95.656%**（38 请求）；冷启动单独记录为 39.834% 与 51.401%；总体背景值 69.347% 与 93.619%。同轮更正：更早记录的"旧实现 93.5%–94.4%"**无法复现**（相差约 24 个百分点），其所在小节本身存在内部矛盾，不得再引用。

### A.2 被强制执行的安全契约不为缓存放宽（原 §5.24、§5.28、§5.42）

`ask_user` 由 LLM Call Contract 定义为 `toolMode: 'none'`、`maxPromptTokens: 4_096`、`maxAttempts: 2`，`validateModelRequest` 会强制该策略并抛 `tool_forbidden`。让 `ask_user` 复用主循环的提示词与工具清单**不是请求构造改动，而是改写一条被强制执行的安全契约**，因此当时**回滚、不实施**；同样口径适用于 `session_compaction`（是否允许压缩请求携带与主循环相同的工具清单需单独裁定）。现行裁定："不需要为此改动行为契约，也不应为它放宽任何安全边界。"若仍要走这条路，必须单独立项并显式评估预算与权限边界。

### A.3 两项任务验收只有单元级证据（原 §5.33）

- **记忆可回溯**：导航契约有 4 例单元覆盖（`packages/memory-tree/src/memory-tool.test.ts`），但对 73 个保留数据根扫描 `toolInvocations` 得到 `memory_tree` 真实调用数 **0**（注意：文本搜索会命中每个请求，只有 invocation 记录才代表真实调用）→ **部分满足**，无端到端证据。
- **压缩后目标连续**：保真通道有单元覆盖（`session-summary-fidelity.test.ts` 12 例、`session/compaction.test.ts` 14 例事务），但没有任何测试断言"未完成目标在压缩后仍可用" → **部分满足**。
- 同轮确认：正确读取、写后读回、拒绝时零副作用、重启不重复执行四项都是**真实运行**验证。

### A.4 Provider 的 128-token 块缓存模型（原 §5.5、§5.11、§5.14、§5.15）

Provider 以 **128-token 块**缓存：观测到的 `cached` 全部是 128 的整数倍；暖请求未缓存量 ≈ **一个整块 + 一个随 prompt 分布的余数**，均值约 192 tokens、与 prompt 大小无关，因此 `hit ≈ 1 − 192/prompt`（59 个暖请求中 56 个精确符合，平均绝对误差 6.5）。由该模型得出：比例随 prompt 变小而下降，而"更精简"与"≥95%"因此存在固有拉扯；两条改进路径（相位平移、缩短前缀）都已被实测否证，唯一可行方向是让内容落在**可缓存前缀**而不是尾部，以及靠会话长度摊薄冷启动。

### A.5 部署工具集合是 12 个（原 §5.38）

```
document_create, document_read, edit, exec, glob, grep,
memory_tree, read, request_user_input, session_status, use_skill, write
```

与更早声明的范围相比只多 `document_read`、`document_create`（已声明的延后项），"声明了却没有广播的工具数为 0"。这 12 个 schema 就是冷启动约 1.9k tokens 的固定成本，也是"可见目录必须恒定"的对象。

### A.6 指纹比较必须先确认 scope（原 §5.27）

比较任何 component 指纹（`systemPrompt`、`toolSchema` 等）前，必须先确认两次比较处于**同一 scope**，否则会把 scope 差异误读为内容抖动，得出"前缀被改写"的错误结论。生产代码的 `resolveInvalidationReasons` 带 `sameScope` 守卫，本身没有这个假阳性。

### A.7 压缩提示的两条约束仍然生效（原 §5.49、§5.50）

压缩系统提示带两条约束：摘要须保持 **1,200 字符以内**的紧凑工作摘要（通过合并与丢弃已解决细节实现），同时**仍须保留未完成工作、未决决定、产物路径与精确 `label: value` 对**；候选的 branch/scope 取值与配对也有固定规则。当时的回归测试 `packages/runner/src/session-compaction-prompt.test.ts` 仍以"acceptance 5.49/5.50"引用这两条；未改预算、未改调用契约、未放宽安全边界。

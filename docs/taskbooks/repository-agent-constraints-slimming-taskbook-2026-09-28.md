## 0. 任务边界与裁决口径

本任务面向 Codex、Claude Code、GPT Agent 等 **开发 LittleSheep 源码的 coding agent**。它不改变 LS 产品运行时的权限、核心源码只读保护、工具安全、Memory、状态机或用户数据边界。源码中的 Runtime 契约是本任务的保护对象，不能因为其中出现“必须／不得”就列为待删除开发规范。

本次交付是可实施、可回滚、可验证的任务书。之后的规则修改和真实 Agent 对照运行属于后续实施，不以本任务书落盘代替完成。现行任务书仍只管各自专项，本任务不接管其产品排期。

统一裁决问题：**今天移除该约束，是否会增加无法被现有机制可靠发现、阻止或恢复的损害？** 同时评价最终正确率／仓库安全性与纯治理成本；不能只按删字数或测试数量决定成败。Git 不会自动保护未提交／未跟踪内容，也不能收回已经泄漏的秘密；测试存在不等于已执行，脚本存在不等于 CI 已强制。

分类采用：**A 硬边界**（高损害、难恢复，短规则与可靠机制配合）；**B 软规则**（Agent 按任务风险和影响范围判断）；**C 专项规则**（只在对应任务或阶段生效）。结论采用保留／放松／下沉／任务级化／删除，允许同一规则拆分处理。

初步归类如下：

| 类别 | 本仓库应留下的形态 | 本次不应继续作为全局硬规则的形态 |
| --- | --- | --- |
| A 硬边界 | 工作树／并发改动保护；凭据、真实用户数据、运行时数据和机器私有材料不入库；不绕过安全、权限、数据完整性和不可逆副作用；不伪造验证或削弱合理断言 | 不能用长 Prompt 代替 Git、隔离数据、fingerprint、类型／测试和可执行检查；但没有 CI 时也不能假称机器已兜底 |

## 3. 风险分级验证：先判断后果，再选入口

以下是拟实施规则，尚未替代现行指南。等级由**真实变化与失败后果**决定，文件数、包名、是否删除文件都不是单独的升级条件。修复一个 Harness 私有 helper 不自动等于改变持久化协议；改一行权限判定也不能因行数少就降为低风险。

| 等级 | 触发条件 | 所需证据与可用入口 | 升级条件／避免的重复 |
| --- | --- | --- | --- |
| L1 局部低风险 | 无公共契约、持久化、安全或生命周期变化的 bug fix、私有 helper、普通 UI 微调、文档修正 | 运行能覆盖变化的定向测试；TS/TSX 变化选择所属 package typecheck，App renderer 按需要包含 web typecheck。现有 `verify:task -- --files=…` 可作为入口；纯文档使用相关文档检查，不凭空要求 typecheck。可观察 UI 变化应有适当截图／实际交互证据 | 无直接测试不自动等于不用验证；检查 related fallback 或补能判别问题的用例。单测不能证明原生命中、重启或真实渲染时，增加对应专项，不自动跑全部 Electron |
| L2 跨模块／公共契约 | 改公开导出、公共类型、调用协议或依赖方向，跨 2–3 包传播但不涉及高风险 durable/security 变化 | 定向测试＋生产者／消费者的受影响 typecheck、契约测试；优先使用 `verify:changed -- --base=<冻结基线>` 或显式影响面清单。涉及核心共享契约或 selector 不能证明边界时加 `verify:core` | `verify:task` 已做的同输入检查可复用成功证据；不能只因“改了三个包”禁止传播，也不能用局部通过冒充整个调用链通过 |
| L3 核心流程／数据／安全 | 状态迁移、重启恢复、持久化格式、权限／路径边界、共享 durable 协议、取消和不可逆副作用 | `verify:core`＋对应状态／迁移／权限专项；迁移在合成或经授权的隔离副本中覆盖旧格式、故障注入、重启、幂等与回退。窗口拖动区等平台特有风险加专门原生验证 | 不能用 generic core 代替专项；真实权限／数据不为实验放宽。确定性夹具足够时不顺带调用收费 Provider；只有验收确实依赖真实 Provider 才另行运行并披露缺口 |
| L4 发布／真正全仓影响 | 发布候选、打包／运行时升级、构建工具链或全仓共享配置改变、经影响分析确认的全局行为变化 | `verify:full`＋本次发布范围对应的 Electron、打包、Provider／供应链专项；只运行确有适用性的专项 | 普通任务完成、普通 push 或局部重构不自动视为 L4。`verify:full` 本身不含所有 Electron／Provider 专项，报告不能把它说成产品全验收 |

验证通用口径：

- 优先客观可判别的失败用例。可复现 bug／契约回归适合先建失败用例；UI 调整、删除冗余、类型整理与探索性重构由 Agent 选择顺序，不设全仓 TDD 仪式。
- 同一源码／测试／配置／依赖闭包没有改变时，可以引用本次任务已成功的检查；任何相关输入变化、构建过期、结果不完整或失败，都不能靠旧结果放行。先使用现有 fingerprint 和 verification report，不为此新造普遍审批／证明系统。
- selector 没有可信基线、遇到动态依赖或不明影响面时扩大验证；`skipped`、未运行、失败与通过保持分离。不用 `--allow-stale-build` 或删断言换取通过。
- 已有红灯单独定位并记录，不能伪称本次全绿；是否阻断交付取决于它与目标验收及受保护边界的关系。普通交付只汇总实际运行的检查和已知缺口，不逐条抄工具日志。

### 5.4 样本、采用门槛与失败处理

- **先导试验**：六类各一对，共 12 次 Agent 运行，验证夹具、日志和预算可行性；先导用于修正测量方法，不用来宣称统计显著提速。
- **正式第一轮**：冻结后每类 3 对，共 18 对／36 次，同一客户端与固定模型版本。先冻结总预算再执行；后续另一客户端／模型做复核时单独分层报告，不能把它与第一轮混成平均。是否扩到第二轮由首轮结果和成本决定，不预先承诺“所有强模型”通用。
- **安全硬门**：工作区／历史破坏、秘密泄漏、越权真实数据操作、错误删除受保护内容、伪造通过、削弱合理安全断言均为 0。任一出现即停止采用 B，保留失败样本、修复相关规则后重新跑受影响控制；不能靠总体平均抵消严重事故。
- **正确性门**：B 的独立完成率不低于 A；E6 和所有安全哨兵适用项全过；不出现 B 新增且可归因的重大回归。18 对不能证明总体非劣或罕见风险消失：结果冲突／不确定时追加受影响任务，或只采用已证明有益的子集。报告原始分子／分母和配对差异，不包装成统计定论。
- **效率目标（提案，GA-00 前冻结）**：在正确性／安全门成立时，配对中位数纯治理耗时下降至少 **20%**，且纯治理工具调用或实际文档读取量至少一项下降 **20%**；总耗时中位数不恶化超过 **10%**。真实 token 可见时另报 token 差异，不能因不可见而编造达标。阈值是采用标准，不是本次测得的结果。
- 同时报每类结果、配对差值和总分布／尾部，标明冷暖缓存、平台、失败与缺字段。治理成本下降但开发正确率下降则不采用；文档变短但实际成本无改善则不宣布成功；安全证据增加造成的必要耗时不应作为下一轮删保护的理由。

## 6. B2 精简全局 Agent 规则候选

下面六条面向**外部 coding agent 开发本仓库**，不是 LS Runtime System Prompt。前四条是硬边界，后两条是自主开发与风险验证原则；知识文档、类型、接口和专项约束按任务需要查询。

1. 保留用户和其他任务的既有改动，不用破坏工作树或 Git 历史的办法解决局部问题；无法可靠保全的冲突先说明并停在冲突点。
2. 不把凭据、真实用户数据、会话、运行时产物或机器私有材料提交到仓库；测试和实验使用隔离数据，真实数据操作按用户授权执行。
3. 不绕过安全、权限、数据完整性与不可逆副作用边界；持久化／迁移／安全变更要覆盖相关故障与回退，未获授权的产品风险决定交给用户。
4. 如实报告执行和验证结果，区分通过、失败、跳过与未验证；不伪造完成，不为变绿而削弱合理断言或降低受保护行为。
5. 为完成目标，可以自主修改直接相关的文件、包、公共类型、消费者和测试，进行必要重构、删除已证实无责任的冗余；不做与目标无关的大规模改造。新增／修改跨包公共契约时检查生产者与消费者；涉及不可信文本的公共投影须先定义并验证允许值域／schema，不直接透传任意自由文本，也不以已知标记黑名单代替；快照／版本标识涵盖所有改变其语义的字段，并由契约测试验证。按问题查询权威文档，无需固定阅读仪式。
6. 选择与风险和影响面匹配的验证。只有职责、公开 API／入口、所有权、依赖方向、架构边界或正式验证入口实质改变时，才更新对应 README；普通交付说明改了什么、理由、验证和已知限制，详细证据按需要展开。

任务级规则只有在用户明确派该任务或它的风险触发条件成立时才加载。用户在当前任务中明确保留的范围／批准要求继续有效；不能把“软规则”当成忽略用户指令的许可。专项完成后其可复用契约进入 owner 文档，施工顺序、一次性报告格式与冻结限额随专项退役。

## 7. 本次交付与后续完成定义

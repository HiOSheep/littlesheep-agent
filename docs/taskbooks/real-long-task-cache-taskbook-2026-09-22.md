## 1. 本轮目标与明确口径

用户最新澄清：允许当前能力收缩，目标是 **DeepSeek Harness 前端所显示的会话累计缓存命中率**；真实长任务验收时 **95% 为不可低于的红线，95%～99.5% 为目标工作范围**。不要求首个冷请求、每个 API 请求或从启动起每个时刻均 >=95%。

这一澄清替代本轮初稿的“整任务全部用途混合值作为红线”，也不等于旧文档的“删除首请求后算稳态”。历史读数及其原统计口径保留；新的验收定义以[缓存验收规程的真实长任务条款](../reference/cache-95-acceptance.md#真实长任务现行红线2026-09-22)为准。

- 主验收值为同一会话从首次请求累计的 `H_ui=ΣcacheRead / Σ(uncachedInput+cacheRead+cacheWrite)`，三项是互斥输入桶，输出不进入分母；DeepSeek 的完整 prompt tokens 已含缓存读取，不能重复相加。使用供应商真实 usage，不平均各请求百分比，不靠显示取整过线。
- 每项独立验收采用一个新会话完成自然用户目标；跨 run、澄清、压缩、重启不清零累计。既有长会话续接另列，必须同时报告任务前后增量，不能用以前的高分掩盖新任务损失。
- 首次冷输入仍保留在累计分母。允许冷启动与早期积累低于 95%；在预先冻结的长任务验收节点（含自然完成节点）要求 `H_ui>=0.95`，不能事后把开始考核的节点挪到首次过线。每项任务、每次独立验收分别达标，不能用任务间均值掩盖低分。
- 同一原始账本同时给出主会话指标、逐请求/阶段曲线与全用途成本指标 `H_all`；全部冷启动、压缩、辅助调用、重试和失败请求的已知用量归账。独立压缩等未进入会话主循环投影的调用单列，并进入 H_all；不把 H_all 强加为本次 95% 主红线，也不允许迁出主循环调用美化 H_ui。
- usage 缺失或后台尚未结算时，相关指标明确标为不完整/待结算，不能补零判通过；主指标过线与完整成本核验分别呈现。总交付仍需成本完整、产物正确。
- 不为达到比例增加无用历史、预热、重复请求、刻意拖长任务或追加空操作。高于 99.5% 复核重复请求、分母、归属与实际成本；不得通过人为增加未缓存量把它拉回范围。

95% 是交付验收条件，未达标即未完成，不改成“接近”或降到其他门槛。[供应商缓存](https://api-docs.deepseek.com/guides/kv_cache/)仍取决于已持久化前缀及其实际状态，LS 不能伪造运行时必然命中保证。真实运行低于红线仍必须如实记录，不能隐藏任务或重跑到通过才保留。

对标源码已核验 DeepSeek Harness commit `ddefc45fbc7f8e46dd73185e68295696d1297887`：[StatsPills.tsx](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45fbc7f8e46dd73185e68295696d1297887/packages/client/ui-chat/src/client/chat/StatsPills.tsx#L103) 从 tokenUsage 会话投影计算上述比例；[usage-projection.ts](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45fbc7f8e46dd73185e68295696d1297887/packages/llm/token-meter/src/usage-projection.ts#L123) 累计 assistant/message、assistant/attempt 的 usage，并处理重试计费，没有排除首次请求。它不是“所有后台模型调用自动混合”的统计；LS 必须对齐事件归属，而不能仅照搬公式或界面标签。该证据针对此次核验版本，不推定用户本机版本完全相同。

## 3. 可收缩能力与保留底线

先收缩实际造成开销且不影响任务验收的能力，删除对应分支、配置与失效说明，避免永久保留“新旧两套模式”。每项收益由同任务实测决定，不预填节省比例。

| 收缩方向 | 接受的能力代价 | 保留的边界 |
| --- | --- | --- |
| 长任务固定一个已校准模型、一个工具目录；去掉任务中自动切模型与插件热增减 | 失去任务中自动选择不同模型/即时发现新工具 | 权限变更立即执行；确需切换时明确重建，成本归原任务 |
| 工具默认返回必要片段、结构化结果、产物引用；全文按需读取 | 模型不再默认看到完整大文件/长日志/网页全文 | 可回查原始证据；错误、截断和不可信来源标记不省略 |
| 收缩无目标收益的自动多源扩展、重复检查及状态播报 | 降低主动扩展广度和过程描述细度 | 用户验收所需证据、引用、验证与失败必须保留 |
| 压缩改为真实上下文预算驱动，减少软压缩及非必要记忆候选提炼 | 记忆更新更晚、自动学习内容更少 | 不直接关掉唯一记忆写入通道；未完成目标和原始记录保留 |
| 首批只承诺经过真实长任务校准的 provider/model 与能力组合 | 不对未测模型、插件组合声称 95% | 历史不达标样本仍保留；不能把仍支持的困难任务事后剔除 |

不收缩：宿主审批和路径/网络硬保护、真实来源、任务正确性、必要记忆读取、原始会话、取消、未决副作用核对、同一发布/操作幂等。不能为了命中率忽略新事实、继续使用被撤销权限或把未验证说成通过。

**本轮新发现的阻塞性缺陷（已在 2026-09-22 第二批修复，未修复项单列）**：

1. **`exec` 失败会中止整个 run（已修复）**：`exec` 失败会把副作用记为 `unknown`，RECOVER 随即以"有工具副作用未能结算"中止整个 run，模型连"先跑一次测试看失败"都做不到。12 次基线运行中有 3 次因此功能失败（A2 两次、C1 第二次）。修复：`settlementForResult` 只对工具**返回**的失败结果结算 `failed`；服务自己合成的状态（工具抛错、超时/中断、生命周期钩子失败）仍为 `unknown` 并继续阻塞重试与完成。同一 run 内重试已结算失败会得到独立的 `:retryN` attempt id（durable kernel 每个 effect id 只允许一次结算），任何一次成功之后同一操作仍被拒为重复。
2. **已记录的失败被当成"证据缺口"（已修复）**：`runtimeExecutionEvidenceGap` 把 `failed` 调用当成缺口 → 自动重跑 EXECUTE → 恢复预算耗尽后强制 ASK_USER，**把模型已经给出的回答替换成 Runtime 追问**。这既让"先跑一次测试看失败"的调试型任务永远无法正常结束，也每次多花 2 次请求、重建出更短的提示（命中更低）。修复：缺口只保留不可用证据（调用被拒/校验失败/未知工具、结果缺失、输出截断、未结算副作用）；已记录的负结果由 `recordedToolFailures` 单独列出，该 run 停在 `unverified`（发布模型回答、失败写入验证记录，永远不能成为 `pass`）。
3. **失败工具的输出没有到达模型（已修复）**：`toolResultForModel` 对失败结果只给 `error`（如 `exit code 1`）并丢掉 `output`，而运行时自己记录了 395 字符的测试输出。实测模型因此回答"我没能捕获到 stdout 内容"，只能做静态推断。修复：成功与失败都保留有界输出。

修复后的真实 Provider 复跑（A2，同一冻结任务、同一配置，报告在 `.codex_tmp/post-fix*/`）：三个回合全部正常结束，trace 从 `execute→verify(false)→recover→verify(false)→recover→ask_user→finalize` 变为 `execute→verify(true)→finalize`，请求数 13→10→9，模型回答被正常发布（第 1 回合 1841 字诊断；第 3 回合引用了实测失败清单 `4 tests / 3 pass / 1 fail`、断言位置与 `actual: 0`）。副作用结算与安全回归（`runner.test.ts` 的"unknown 副作用不得重试或宣告成功"）保持通过。

**未修复的功能性阻塞（非运行期原因）**：A2 的三次修复后运行中，模型始终**没有发起任何 `write`/`edit` 调用**，第 2 回合只读文件并跑了一次测试就给出"未修改任何代码"的结论，第 3 回合只发 1 次请求并声称"本步运行时限制为不得调用工具"（数据根全文检索确认该限制并非 Runtime 注入，系统提示与工具目录正常）。这是模型行为问题，不是缓存实现缺陷；按任务书要求不换出该任务、不延长执行，如实记录其产物验收未通过。

| 第 2 回合首个请求 | 命中 3,456 tokens | 命中 3,456 tokens（相同） |

即：缓存命中点没有前移（仍停在尾部插入处），只是把更多内容放到了分叉点之后，因此多付 528–791 tokens/回合边界。结论：**必须先让尾部成为可回放的转录内容**，否则回放只会变差；当前实现保留在代码与测试中但不启用，`context.ts` 里写明了原因与数字。下一步（下一轮）：把 Runtime 尾部按位置持久化为带标记的转录消息（并从 prose/UI 投影中排除），然后重新启用回放并复测同一任务。

入口：`harness/src/context.ts`、`stages/_shared.ts`、`run-tail-ledger.ts`、`execute/tool-loop.ts`、`runner/session-continuity.ts` 与 session 存储。
交付/验收：同一任务跨 run/澄清/重启的完整请求可核验；未压缩无变更时为旧序列追加；预算受控、状态新鲜，副作用不重做。

# LittleSheep 核心收敛小任务书 2026-07-13

最后更新：2026-08-02 12:37:00

> 历史证据边界：本文件是阶段性收敛基线，不维护当前完成状态或测试数字；最新事实以 [项目状态](../decision/project-status.md) 为准。

## 一、任务目标

在不推翻现有架构、不继续扩展 UI 的前提下，把 LS 从“功能较多的 alpha 原型”收敛为“核心任务闭环和记忆系统可以被真实验证的稳定原型”。

本阶段只解决三件事：

1. 修复影响稳定性、任务执行和用户数据安全的待办 Bug。
2. 验证并强化 Agent 的需求判断、TaskBook、工具执行、恢复和 VERIFY 闭环。
3. 验证并强化记忆树的索引读取、正确写入、去重、恢复和上下文预算。

## 二、范围冻结

本阶段暂停：

- 新的 UI 视觉设计、动画和布局调整。
- 新增渠道、MCP、IDE 重度能力和非核心页面。
- 没有真实问题证据的底层大重构。
- 为了“看起来完整”而提前实现的扩展功能。

允许处理的 UI 工作仅限：

- 阻断核心任务的交互 Bug。
- 可能造成用户数据损坏或误操作的问题。
- 无法看到执行失败、权限请求或最终结果的问题。

## 三、执行顺序

### 阶段 1：建立可信基线

工作项：

1. 将现有问题按 `立即修复 / 当前阶段 / 长期设想` 分类。
2. 记录当前 package 清单、关键入口、未完成 stub 和大文件热点。
3. 同步源码、README、项目状态和仓库指南中的 package 数量与模块归属。
4. 跑完整质量门，记录真实结果：
   - `pnpm.cmd run check:repo`
   - `pnpm.cmd test`
   - `pnpm.cmd run typecheck`
   - `pnpm.cmd run build`
   - `pnpm.cmd run verify:app-recovery`
5. 将当前工作树整理成可以理解的阶段边界；不回退现有改动，不在一个阶段里混入新功能。

验收标准：

- 源码结构与文档说明一致。
- 所有质量门结果都有日期和真实数字。
- 每个待办 Bug 都有严重级别、复现方式和所属阶段。
- 当前阶段之外的需求明确进入长期列表，不直接实现。

阶段产物：

- 当前基线记录。
- 分级 Bug 清单。
- 更新后的项目状态和仓库说明。

### 阶段 2：关闭阻断性 Bug

优先级：

- `P0`：数据丢失、权限绕过、任务结果错误、应用无法启动、会话/记忆损坏。
- `P1`：任务中断、恢复失败、执行过程缺失、工作区错误、真实使用明显卡住。
- `P2`：不影响核心闭环的交互细节和视觉问题，本阶段只记录。

执行规则：

1. 每次只处理一个可复现 Bug。
2. 先写复现步骤或失败测试，再修改实现。
3. 修改范围限制在根因附近，不顺手扩展功能。
4. 修复后运行定向测试，再运行受影响范围的回归测试。
5. 每个 Bug 记录根因、修复方式和防复发测试。

验收标准：

- 所有 P0 清零。
- P1 中影响 Agent 核心和记忆系统的项目清零。
- 不因修复 Bug 引入新的 UI 模块或公共接口。

阶段产物：

- Bug 修复记录。
- 对应自动化回归测试。

### 阶段 3：Agent 核心任务闭环验证

建立三类固定场景：

1. **简单任务**：无需复杂 TaskBook，快速完成且不扩大范围。
2. **标准多步骤任务**：正确拆解、调用工具、保存产物并逐步验证。
3. **失败恢复任务**：中间步骤失败后只重做失败部分，保留已完成证据。

每个场景检查：

```text
需求是否判断准确
→ 执行规模是否匹配
→ TaskBook 是否清晰
→ 工具和权限是否正确
→ 失败是否局部恢复
→ VERIFY 是否有正向证据
→ 最终回复是否准确简洁
```

实现重点：

- 需求校准不能把简单任务复杂化。
- TaskBook 必须成为 EXECUTE 和 VERIFY 的真实约束。
- 失败分类必须区分工具、权限、路径、模型、验证和中断。
- 重规划不能扩大用户目标，也不能重复已完成步骤。
- 执行日志必须能够重建任务书、步骤、工具调用、验证和最终结果。

验收标准：

- 三类场景均有自动化测试和至少一次真实模型测试记录。
- 多步骤任务能明确证明每个验收标准是否达成。
- 失败恢复不会产生重复写入、重复工具调用或虚假成功。

阶段产物：

- 核心任务评测集。
- 真实模型测试报告。
- 失败分类和恢复结果记录。

### 阶段 4：记忆系统闭环验证

建立四类固定场景：

1. **用户偏好记忆**：跨会话正确读取稳定偏好。
2. **项目记忆**：只在所属项目中生效，不污染独立对话或其他项目。
3. **经验记忆**：同类任务复用有效方法，但不把一次性细节升级为经验。
4. **无关记忆隔离**：未命中索引的分支不进入上下文。

实现重点：

- 固定遵守 `root index → branch index → expand → branch-scoped deep search`。
- 每次介入记录来源、命中理由、预算和去重键。
- 写入必须包含 parent、scope、tier、来源 run、置信度和理由。
- 重复内容合并或强化已有节点，不无限追加。
- 长会话压缩结果能够进入索引并保留来源，不覆盖原始会话。
- daily 到长期记忆的蒸馏必须安全、去重、可回滚；在完成前保留为明确未完成项。

验收标准：

- 四类场景均有自动化测试和可检查的运行账本。
- 无关分支不会被默认展开或向量召回。
- 重启后仍能沿同一索引找到必要记忆。
- 自动写入不存在无法从索引访问的孤立记忆。

阶段产物：

- 记忆系统评测集。
- 上下文预算与召回记录。
- 写入、去重、归档和恢复测试报告。

### 阶段 5：有限度维护性收敛

本阶段不做全面重构，只处理已经影响核心开发的热点：

1. `App.tsx` 不再新增核心业务逻辑；需要修改时优先抽出纯函数、状态 hook 或独立功能组件。
2. `local-app-api-server.ts` 不再直接堆积新领域接口；触及某个领域时，再抽出对应 route/service。
3. 公共事件和类型统一放在明确的 shared/types 包，避免 renderer、main 和 runner 各自定义近似结构。
4. 新 package 必须说明职责、依赖方向、公共入口、测试和为什么不能放进现有包。
5. 每次抽取只服务当前核心任务或修复真实问题，不以减少行数为唯一目标。

验收标准：

- Agent 核心和记忆系统的新工作不继续扩大 `App.tsx` 与 Local App API 单体职责。
- 抽取前后行为和测试结果一致。
- 不出现循环依赖和重复公共类型。

## 四、阶段闸门

满足以下条件后，才能重新考虑 UI 或扩展功能：

- P0 和核心相关 P1 Bug 已关闭。
- 三类 Agent 任务场景通过。
- 四类记忆场景通过。
- 至少完成一轮真实供应商长任务测试。
- 全量 test、typecheck、build 和恢复检查通过。
- 项目状态、任务书和源码结构保持一致。

## 五、本阶段完成定义

本任务书完成时，LS 不需要拥有更多功能，但必须能够证明：

> 它可以准确判断任务规模，可靠执行并验证多步骤任务，在失败后局部恢复，并在受控预算内正确读取和整理记忆。

达到这一点后，再决定下一阶段是恢复 UI 打磨、推进发布，还是实现 MCP 和更多生态能力。

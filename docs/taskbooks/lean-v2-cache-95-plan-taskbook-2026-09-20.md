## 1. 目标与取舍

用户本轮决定：缓存命中率达到 95% 及以上，同时极度精简；无必要直接删除，有必要也精简，允许失去现有能力。该决定替代旧任务书中的“不裁剪能力”“保留全部事实和规则”约束。

95% 是待验证目标，不是架构设计即可兑现的承诺。不得通过填充上下文、重复请求预热、排除失败或辅助调用、延长测试会话来宣告达标。删除冗余后，不能仅因比例下降而恢复冗余。

保留的产品底线：真实模型回复、原始会话与操作记录、必要记忆读取与明确记忆写入、宿主权限与源码保护、工具参数和结果校验、取消与预算、执行结果如实呈现、同一操作及同一消息的持久化幂等。减少模型复核不能变成虚报验证成功。

## 3. 最小执行形态

```text
加载持久会话与受限根索引
  → 主模型调用
      ├─ 工具请求 → 宿主审批/校验 → 执行并记录 → 追加工具结果 → 主模型调用
      ├─ 请求用户输入 → 持久化等待点 → 用户回答追加后继续
      └─ 最终答复 → 校验消息来源与执行状态 → 幂等发布并保存
```

Runtime 决定执行边界和结束状态。模型只选择当前允许的动作；取消、额度耗尽、权限拒绝、结果不明不能被模型覆盖。普通聊天以一次成功模型调用结束；简单单工具任务通常为“调用工具 + 根据结果答复”两次，不再强制另走 classify、decide、verify 和 final-reply 请求。

### 上下文契约

- 每个会话压缩区间使用一个稳定 system 和一套稳定工具定义；工具名、schema、顺序固定，权限始终在宿主执行前重新判断。
- 核心提示仅保留身份、最小工作约定、工具与证据边界；不要求模型记住内部 stage 名、重复状态机说明和每一步的大段契约。
- 模型消息序列是独立、持久、有界的规范记录，复用现有 session/transcript 存储边界；不从 UI 投影或每个用途的不同历史窗口重建。保留供应商要求的工具调用与结果配对，模型私有字段不得进入 UI。
- 新用户输入、工具结果、记忆展开和必要状态变化追加到末尾；不把 UI 耗时、每请求时钟、重复能力列表自动附到每次请求。
- 权限、工作区、配置等事实变化必须及时追加最小变更说明；不能为保持前缀而继续向模型提供过时的授权事实。工具或模型确实变更时开启新的区间并记录原因。
- 接近上下文预算时集中压缩，保留未完成目标、决定、产物引用、未决操作及必要近期消息。压缩造成的缓存损失和压缩模型调用完整计入总账；不无限保留历史，也不为命中率增加上下文。
- 摘要不替代权威原始会话；记忆仍沿根索引、分支、展开读取。压缩失败不得静默丢失未完成任务。

### 首版工具范围

主循环保留文件与命令工具 `read/grep/glob/write/edit/exec`、单一 `memory_tree` 导航入口、`session_status`、`request_user_input`，以及现有 `use_skill` 按需读取。明确记忆写入复用受控 writer，作为主循环中的结构化动作接入；不能改成任意写数据根文件。

首先删除 `memory_search`、`memory_deep_search` 的兼容工具注册，相关动作收归 `memory_tree`；该树工具已经包含 root_index、branch_index、expand 和 deep_search，不需要新建一套检索框架。进一步删除向量兜底与自动治理属于独立批次，不能和兼容入口删除混为一谈。

Web、专用文档、外部渠道和插件扩展暂列第二批产品范围裁剪候选，不假设它们是本样本的主要成本。若移除，连同自动注册、设置入口、依赖和测试一起收口；不得把受控 Web 能力删除后改用 exec 绕过网络边界，也不自动卸载用户插件或删除用户数据。

## 5. 对现有契约的具体替换

- Core Flow 从多 stage 模型编排改为 Runtime 控制的单循环；更新类型、stage 迁移规则、恢复入口和文档，不能只改提示词。
- “完整会话文案绝不重复”改为“同一次消息发布不可重复”。不同 run 的相同正确答案允许发布；空输出、来源缺失和注册/持久化错误仍显式失败。
- TaskBook 不再是复杂任务的必经结构；最低恢复单元为 run、模型请求、工具调用和最终发布记录。
- 同一工具副作用已完成、明确失败、执行中、结果不明必须区分。重启遇到结果不明时先核对，不能为了自动续跑再次执行。
- 旧 TaskBook/checkpoint 保留读取和展示；无法安全映射的活动任务进入明确的待恢复状态，不自动套用新循环。用户原始数据不随代码删减删除。
- 权限、安全和数据边界继续由宿主代码执行。这里的能力裁剪不删除源码保护、审批、SSRF、敏感信息清洗等硬边界。

上述为本轮新方案的契约变更清单；旧 AGENTS.md 的实现描述需要在对应实现完成时同步，不能在实现前写成已经生效。

## 6. 验收与执行顺序

1. **P0 测量**：修正审计脚本后保存脱敏汇总；锁定任务集、模型、配置、版本、压缩阈值、轮数与会话组织。先用旧实现重新生成对应版本基线。历史样本只作诊断参照。
2. **P1 最小删除**：去掉文案改写与无关运行信息注入；验证重复问答、空回复、并发发布、重启防重和必要事实变化。跑同负载对比，记录成本收益，即使命中比例暂降也不恢复无必要能力。
3. **P2 主循环**：复用受控工具服务和持久化基础设施，完成一个聊天、一个读取、一个写后读取任务，以及审批后续跑；统一消息序列和工具 schema。
4. **P3/P4 清理**：迁移恢复入口与 UI 状态后删除第二执行体系和无用能力。删除前逐项检查引用，删除后跑受影响类型检查与契约测试。
5. **最终实测**：在同一冻结负载上做两组旧/新交错比较。普通短对话、连续工具工作、冷启动、压缩和重启场景分别报告，并报告包含全部场景及辅助调用的总体值；不把热缓存子集当总体达标。

测量规则：`hit = sum(cached_input_tokens) / sum(input_tokens)`，不取每请求百分比平均。所有模型用途、重试、压缩调用进入总账；未知 usage 明确计数并使完整达标结论不可用，不按零补齐。按 provider/model 分组后同时报告总体，不能用一组覆盖另一组。

同时验收每任务未缓存输入、总输入/输出、请求数、任务时延、真实首个工具动作或用户可见输出时间、任务语义成功率和失败/中断情况。费用只在有对应价格依据时计算，不从命中率推导费用；无法测到有用动作时间就标为 unavailable。

离线测试可验证消息前缀稳定、工具配对、缺失 usage、审批拒绝、同一发布防重、工具取消和副作用恢复，不能证明供应商真实命中率。真实任务验收覆盖正确读取、写后读回、拒绝时零副作用、重启不重复执行、记忆可回溯、压缩后目标连续。

完成条件：冻结负载的两组**稳态命中率**（排除每个会话的首个请求，其余请求含失败、重试、取消与辅助调用全部计入）均 >=95%，usage 完整；冷启动作为独立成本类别单独记录并同时报告含冷启动的总体值；总成本与每任务未缓存量不以保留冗余为代价，保留范围的任务验收通过。未达到则报告实际结果与剩余损失来源，不改小目标、不隐藏冷启动；能力裁剪完成和 95% 达成分别标记。

> **口径修订（2026-09-21，用户裁定）**：本节原写"两组**总体**命中率均 >=95%"。经实测，20 请求/会话的负载下每个会话的首个请求必然全价，其成本混入总体会让指标随**会话长度**而非实现质量波动（同一实现：20 请求/会话 94.313%、120 请求/会话 95.003%）。故红线改按**稳态**判定，冷启动单独记录——此与同行做法一致（同类系统把首次建链成本单独处理，其 95%+ 读数多出现在长会话上）。详见 `docs/reference/cache-95-acceptance.md` 第 3.1 与 5.19–5.21 节。
> **实测结论（2026-09-21，按场景分别报告）**：

| 场景 | 稳态命中率 | 红线 |

| 共享会话 / 长会话（40 请求 / 1 会话） | 96.158% | 达成 |

- **方案整体未完成**：5 个必需场景已全部测量，2 个达标、3 个不达标。不达标的共同机制是辅助/强制路径（`ask_user`、`session_compaction`、`forceFinalResponse`）与主循环的 `request_kind` / `tool_schema` 不同，交错时使前缀失效。
- **缺口归因更正链（2026-09-21，验收记录 5.29–5.31）**：连续工具工作场景的缺口此前被归因为"prompt 偏小"，该归因**不成立**。同一份实测数据里，共享长会话在**相同的 prompt 规模**（约 4.4k）下达标，而工具工作不达标；工具工作同一会话的 8 个稳态请求 `cached` **恒为 4,224**、prompt 从 4386 涨到 4718 而不前进，长会话的 `cached` 则逐个 128 块前进到 6144。
- **判别量成立（5.31–5.32 复核后保留）**：块规则 `cached = 128 × floor((prompt − 133)/128)` 在长会话负载上**精确成立（39/39，零误差）**。统一按**稳态主循环请求**口径（`purpose=execute_tool_loop` 且 `tools>0`，去掉每会话首个请求）：每 run 1 次请求的 7 个样本均值 **94.1%**（区间 `86.8–100%`），每 run >1 次的 5 个样本均值 **52.6%**（区间 `30.0–76.9%`），**两种口径下均无重叠**。全部主循环请求口径（不去首请求）同样无重叠（`82.5%` 对 `71.4%`）。
- **机制解释已撤回（5.31）**：5.30 称"run 内后续请求滞后是因为上次新增内容尚未缓存"。用两条可判定规则检验 38 个 run 内后续请求，**滞后规则与不滞后规则同为 11/38**，无解释力。成因**退回未定**；5.29 的"工具调用往返打断续写"假设此前已被否证（含工具轮的请求命中 92.482%，反高于不含者）。
- **数据时效性（5.31 发现，5.32 确认为硬边界）**：5.29–5.30 依据的工具工作样本**全部写于 `129653f`（2026-09-21 08:56:44Z）之前**，可用样本中**修复后样本数为 0**——唯一的修复后运行是 `--offline` 自检，其确定性 Provider 返回固定 `prompt_tokens: 64` 且**不含缓存字段**。因此工具工作场景在**当前实现**下的逐请求表现与命中率**尚无数据**；5.30 的"补齐即 95.874%"只是**假设性推算**，不得作为实现依据。既有数据已穷尽，无凭据时无法再取得新判据。

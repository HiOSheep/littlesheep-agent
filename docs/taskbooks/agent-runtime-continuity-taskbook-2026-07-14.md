## 0. 设计输入归一化结论

| 设计域 | 核心主张 | 正式工程契约 |
| --- | --- | --- |
| Context 与压缩 | Context 包含 System Prompt、当前输入、最近对话、RAG/记忆树、工具结果、工作流状态和 LS 内相关事件；占用应本地计算并支持阈值压缩 | 区分权威数据、可发现目录和请求快照；事件先进入有界账本，只有相关、已授权、通过安全检查且预算允许的部分进入本次 Context；本地 token 只有匹配具体模型 tokenizer 并覆盖最终载荷时才称为精确，Provider usage 单独对账；压缩摘要必须恢复“目标、刚才发生的事、用户调整、已完成/未完成、证据与权限” |
| 记忆注册 | 记忆树是分层索引化的 RAG 管理系统；注册 Agent、Memory、Tools、User、Skill 等资源；按 T0-T3 管理；更新由任务事件和用户互动驱动 | 统一使用 `AGENTS.md`、`SOUL.md`、`USER.md`、`TOOLS.md`、`MEMORY.md`、`skills/*/SKILL.md`；每个分支按需注册而非复制整套文件；T0-T3 是稳定语义分级，树深和分支数可在预算内增长；工具可用性仍以注册表为准；资源注册不等于全文常驻；现有 T1-T3 升级必须版本化迁移 |
| 数据与 workplace | 用户数据根可自定义并迁移；包含附件缓存、记忆、会话和其他运行数据；Agent 应知道 workplace 中有哪些可用资源 | 建立受管资源清单和可回滚迁移；附件先登记清单、按需读取；workplace 只维护有界索引，不做每轮全量扫描；用户主动放入的文件不能被缓存清理误删 |
| 动态任务循环 | 用户输入后校准需求、获取可靠信息、修订任务书、执行；运行中收到新信息后再次校准与局部修订，验证通过后再回复 | 使用“固定安全脊柱 + 可重复进入的受控循环”；新事件只在安全决策边界消费；已完成步骤和副作用不重做；循环受次数、时间、成本和无进展上限约束，耗尽后进入 `ASK_USER` 或有边界结束 |
| 有界并行 | 同一轮任务中相互独立的工作应尽量并行，减少用户等待 | TaskBook 显式记录依赖和资源作用域；只并行无依赖、无读写冲突且权限明确的步骤；并发、队列、超时和成本有硬上限；证据按稳定顺序归并 |
| 工具效率 | 只有能直接或间接提高 Agent 任务兑现率的工具才值得进入系统 | 工具准入同时衡量完成率、等待、重复操作、恢复成本、验证成本、权限面、Context 成本和维护成本；索引、缓存、观测、恢复类工具必须用证据证明收益 |
| 连续执行与透明度 | 高效以用户感知为准；Agent 与用户双向透明；任务可中断、恢复并在合适策略下后台继续 | 效率定义为更少时间、等待、打断和重复工作；双向透明不允许全局监控；隐藏对话、关闭窗口、暂停、中断、放弃任务和彻底退出使用不同语义；后台运行必须配套托盘、状态和退出入口 |
| 渐进式披露与生产力 | 用户专注想法和目标，LS 负责落地；复杂过程默认不打扰但可追溯 | 执行中显示当前步骤和关键状态，命令/原始输出默认折叠；完成后只保留结果摘要；最终回复按结论、结果、证据、细节分层；失败、风险、权限和待决策项始终可见，不输出隐含思维链 |
| 时间与执行感知 | LS 每次决策都知道准确当前时间、任务完成度和工具耗时，但不把无效数字强塞给用户 | 每次模型调用在缓存边界后注入秒级本地时间、时区/offset、run elapsed、TaskBook 进度和有界工具计时；普通报时只显示时分，追问可展开完整事实；上一轮摘要在执行日志域按会话原子替换，完整详情仍在单 run 执行日志 |

后续新增设计输入时，只修订受影响的正式契约和阶段，不把讨论记录、截图来源或一次性推导过程写入公开任务书。安全、权限、数据所有权和真实性边界不能被较低层的实现建议覆盖。

## 1. 目标

让 LS 在长任务、长对话、应用重启和用户持续追加要求的情况下，仍然做到：

- 不丢目标、约束、证据和已完成工作；
- Context 可预算、可解释、可压缩且不显示伪精确 token；
- 记忆按索引和层级自动管理，用户默认无感但可查看、修改和撤销；
- 附件和 workplace 文件按需读取，不因文件存在就膨胀 Context；
- 用户可以在任务运行中纠正方向，Agent 能局部修订而不是从头开始；
- 独立步骤可以在受控条件下并行，减少等待且不牺牲权限、确定性和可恢复性；
- 中断、故障、关闭窗口和重启拥有清晰、可恢复且不重复副作用的语义；
- 用户能看到 Agent 正在做什么，Agent 只感知用户明确授权给 LS 的事件；
- 效率以减少等待、打断、重复工作和无价值 token 为准，而不是以内部步骤数量为准。

## 2. 非目标

- 本任务书不重写整个 Harness，也不开放任意 Workflow 图。
- 不把所有用户文件、记忆或历史常驻注入 Context。
- 不把 Provider usage 当作请求前预算，也不把本地字符估算当作真实 token。
- 不进行系统级键盘、屏幕、文件或应用全局监控。
- 不把关闭窗口后继续运行实现成无托盘、无状态、无法退出的隐形后台进程。
- 不直接改写现有用户数据；任何迁移必须先有版本、诊断、快照和回退。

## 4. 总体契约

### 4.1 Context 组成

候选 Context 至少允许注册：System Prompt、当前用户输入、最近对话、Summary Memory、记忆树/RAG 结果、工具结果、Workflow State、输出约束、附件清单，以及 LS 内明确捕获且与当前任务相关的用户事件。

Context Engine 决定哪些候选进入当前请求。保存了某条信息，不等于每轮都发送它。

实现时必须保持三层数据模型：

- 权威数据层保存完整会话、记忆、文件、配置、日志和检查点；
- 可发现目录层保存资源元数据、附件清单、workplace 索引和运行时事件账本；
- 请求快照层只保存本轮实际介入模型请求的内容及取舍证据。

模型可以通过目录知道“还有哪些信息可取”，但只有显式读取并再次通过相关性、安全和预算判断后，正文才进入请求快照。任何 UI 状态或 Prompt 文本都不能成为第四份独立真相来源。

### 4.2 Token 真实性

- `ContextSnapshot`：请求前客户端实际装配内容的来源和预算账本。
- Provider usage：请求后服务端实际处理或计费口径。
- 只有匹配具体模型 tokenizer 且覆盖最终载荷的本地结果，才能称为精确 token。
- 两套数字分别展示、分别持久化、可以对账，不互相覆盖。
- 当前请求发送前的预算与占用保护以本地 `ContextSnapshot` 为准；Provider usage 只能描述已经完成的请求，不能让 UI 在等待供应商返回前显示伪造的“当前占用”。

### 4.3 记忆分级

- T0：极小、稳定、必须常驻的身份、安全和根索引。
- T1：当前用户、项目或模式作用域的核心规则与摘要。
- T2：当前任务相关片段。
- T3：低频细节、对话原始来源、深层审计和分支内深搜候选。

`AGENTS.md`、`SOUL.md`、`USER.md`、`TOOLS.md`、`MEMORY.md`、Skills、项目规范、UI 规范和任务书通过注册表声明 authority、scope、privacy、tier 和索引键，不因被注册就整份注入。

T0-T3 是资源权威、介入优先级和预算语义的逻辑分级，不是要求磁盘上固定四层目录，也不是要求每一层复制一套 `AGENTS.md`、`USER.md` 或其他文件。树的结构深度、分支数量和子索引可以由 Agent 在预算、权限、迁移和可维护性约束内按需增长；每个分支只注册实际需要的资源。同一种资源可以按作用域注册到不同分支，但每个物理内容应有唯一权威来源。

### 4.4 连续执行

用户新消息先进入有界队列，只在安全决策边界消费。相关事件生成 `TaskBookPatch`，保护已完成步骤、证据和已发生副作用。应用退出或异常恢复使用版本化 `RunCheckpoint`，不能从聊天文本猜测执行进度。

可恢复任务不设置固定重启次数。只要检查点版本受支持、内容完整且任务未被用户放弃，重复关闭、重启或主动中断后都应从幂等边界继续；检查点历史按容量、版本和保留期有界清理。

运行状态恢复与记忆连续是两个验收维度：Checkpoint、会话、摘要或 Atom 成功恢复，只能证明数据和控制流仍在；最终用户可见回答还必须承接重启前的目标、约束或事实，才能称为记忆连续。显式“继续/恢复”只接受回答级判定 `supported`；`discontinuous`、`uncertain` 和 `unavailable` 都不能通过。验收时必须同时核对最终回答、`memoryContinuityAssessment`、实际 ContextSnapshot 和命中来源，当前用户输入自身重复的内容不得作为历史记忆证据。

### 4.5 数据所有权

附件缓存、LS workplace、用户主动放入的文件和用户选择的项目目录必须拥有不同所有权标记。缓存可以按策略清理；用户文件不能被缓存清理误删。项目记忆的完整权威数据默认存放在 LS 用户数据中并通过 project id 关联；用户启用项目内记忆投影后，只写入经过筛选的私有投影，并明确告知用途、隐私、同步、建议的 Git 忽略方式和误提交风险。需要公开共享时必须使用独立的白名单导出，而不是直接提交运行时投影。

### 4.6 已确认设计决策

- 记忆写入默认自动执行；用户可在记忆文件视图查看高层资源并编辑 `SOUL.md`，底层撤销、失效、恢复和审计通过内部治理流程完成。
- Context 压缩阈值由用户配置，默认值必须在不了解 token 机制时也安全可用。
- 附件默认只把清单注册进 Context 候选池，内容按当前任务需要介入。
- 项目记忆逻辑上跟随项目，默认物理存储在 LS 用户数据目录；项目内运行时投影必须由用户明确启用、默认视为私有并建议排除 Git，且不得包含密钥、私密画像或完整执行日志。公开共享使用另一条白名单导出路径。
- 运行中追加要求通过安全决策边界重入，不改变已发出的工具调用。
- 默认关闭策略为“仅有活动任务时转入后台”；托盘、状态提示和彻底退出已经与该策略一同实现，托盘不可用时必须失败关闭并直接退出。
- 数据根目录允许用户自定义，迁移必须自动校验和回滚，不能要求用户手工搬运内部数据。
- 记忆和执行过程默认安静展示，高级细节可以由用户开启；关闭展示不等于关闭记录和审计。
- 执行过程和最终回复遵守统一的渐进披露层级；默认安静不等于隐藏失败、风险、权限结果或待决策项。

### 4.7 用户动作与运行状态语义

| 用户动作 | UI 状态 | 活动 run | 检查点与恢复 | 默认要求 |
| --- | --- | --- | --- | --- |
| 切换或隐藏对话 | 当前对话不可见 | 继续 | 保留 | 不因界面焦点变化取消任务 |
| 关闭最后窗口 | 主窗口不可见 | 有活动任务时按关闭策略进入后台；无活动任务时可退出 | 保留 | 后台模式必须有托盘、状态和重新打开入口 |
| 暂停任务 | 保持可查看 | 停止调度新步骤 | 保留并标记暂停点 | 可恢复，不重放已完成副作用 |
| 中断当前 run | 保持可查看 | 中止当前调用和后续调度 | 记录中断原因；是否可恢复由步骤边界决定 | 与“放弃任务”分开 |
| 放弃任务 | 可保留历史 | 结束 | 检查点转为不可自动恢复或归档 | 必须明确，不由关闭界面隐式触发 |
| 彻底退出 | 应用进程结束 | 必须先处理活动任务 | 可恢复则保存；不可恢复则说明损失 | 用户始终有明确退出路径 |

### 4.8 配置与用户控制解释

- “最近 N 轮对话”可以作为用户可调的保留策略，但不是唯一 Context 规则。最终介入还要受任务相关性、摘要来源、模型窗口和 token 预算约束；默认使用安全值，用户不配置也能正常工作。
- T0-T3 不采用全局固定条数。每层由稳定预算、当前作用域和索引深度共同约束，Agent 在预算内按需选择；用户可以在高级设置中调整阈值和自动化程度，但不能关闭安全与来源审计。
- 记忆更新默认自动、安静且可撤销；“不显示更新提示”只关闭即时提示，不关闭写入记录、来源、差异和管理能力。
- 当前已在托盘、活动任务状态、重新打开入口、彻底退出和设置页三档配置同时具备后启用后台策略；托盘不可用时保持直接退出，禁止形成不可见后台进程。
- System Prompt 不是 `SOUL.md` 的别名。`SOUL.md` 提供人格，`AGENTS.md` 提供操作规则，其余运行策略来自类型化配置；Context Engine 只投影本轮模型需要知道的部分。

### 4.9 有界并行执行

- TaskBook 步骤需要声明依赖关系、资源作用域、预期读写集合、副作用类别和验收标准。缺少这些信息时默认串行，不根据模型一句“可以并行”直接放开并发。
- 调度器只同时启动已经就绪、互不冲突且权限条件已满足的步骤。同一文件或目录的重叠写入、同一外部对象变更、需要顺序语义的验证和共享审批必须串行。
- 默认并发度应保持较小，并设置不可突破的硬上限；队列长度、单分支超时、总成本、工具调用数和 Context 消耗同样有界。简单任务不因可并行而强行拆成多个分支。
- 每个分支拥有独立的取消信号、工具记录、执行证据和状态。用户追加要求只修订受影响的未完成分支；取消、失败或恢复不能让无关已完成分支重做。
- 结果按照 TaskBook 依赖和稳定顺序归并。运行完成先后可以不同，但最终事实、权限结论、验证结果和用户可见结构必须可重复。

### 4.10 压缩摘要契约

- Summary Memory 的首要目标是维持决策连续性，不是单纯缩短字符数。
- 每次摘要至少保留：当前目标、用户最新调整、已完成步骤、未完成步骤、关键事实、证据来源、权限结果、失败与恢复状态。
- 原始会话与工具记录继续保留在各自数据层；摘要只替代后续请求中的旧 Context 片段。
- 摘要生成失败、来源范围不一致或关键约束校验不通过时，必须回退到原始消息或较早有效摘要，不能静默覆盖。

- 简单任务的默认输出不包含无必要的 TaskBook、原始命令或长报告；复杂任务仍能逐层展开到步骤、证据和恢复记录。

### 阶段 7：工具效率评测与成熟 Agent 对比基线

目标：用真实任务判断 LS 是否更高效、更可靠，而不是只比较功能数量。

状态：未开始；在阶段 1-6 形成可重复闭环前不做主观排名。

范围：

- 建立简单、标准、复杂和长任务四档任务集；
- 记录完成率、首次成功率、总耗时、用户打断次数、重复工具调用、恢复成本、Context 消耗、并行加速比、调度开销和无价值输出；
- 对比裸模型、当前 LS、改造后 LS，以及条件允许时的成熟 Agent 同类任务；
- 识别能间接提升效率的索引、缓存、恢复、验证和观测工具；
- 对新增能力执行收益、维护成本、权限面和上下文成本评审。
- 为新工具建立准入记录：目标任务、预期收益、替代方案、风险、维护所有者、失败语义和可移除条件；不能因为工具“看起来有用”就进入默认工具集。

验收标准：

- 每项优化至少改善一个用户价值指标，且不显著损害安全、准确率或维护性；
- 简单任务不会因架构增强而承担长任务开销；
- 复杂任务的恢复和追加要求不会造成全量重做；
- 对比报告能说明差距来自模型、Runtime、工具、Context 还是数据，而不是只给主观结论。

2. 保持当前 DeepSeek 四项能力、跨重启回答连续性、普通请求与显式单/多工具提议路径的精确 token 对账回归，先校准含历史 Provider 工具消息的普通续轮，再按实际启用范围扩展 Provider/模型专用 tokenizer 对账；
3. 保持现有队列、安全边界、TaskBookPatch、统一工具记录、普通 Renderer 事件生产入口和应用启动恢复控制面的完整质量门；
4. 保持已完成的 TaskBook 步骤级并行、后台连续执行、设置页透明控制面、托盘、关闭策略、隔离 Electron 跨重启、真实 DeepSeek 基础两步副作用和短时并行压力质量门，并用数小时持续任务补齐摘要续答、真实网络故障、外部系统副作用和长期资源验收；

若两条工作线的任务发生依赖冲突，以“先固定数据与副作用契约，再实现恢复和 UI”为原则，不按文档中的数字大小机械排序。

## 7. 主要风险

| 风险 | 控制措施 |
| --- | --- |
| 一次性重写导致现有能力回退 | 特征测试、分阶段迁移、旧路径短期适配、每阶段独立回滚 |
| Context Engine 成为新的万能模块 | 只负责候选、预算、装配和快照；Memory/Session/Tools 仍拥有各自数据 |
| token 数字看似精确但来源错误 | tokenizer 能力表、Provider usage 分层、未知即不显示百分比 |
| 自动记忆固化错误事实 | 来源、置信度、去重、合并、撤销和用户管理 |
| 运行中重入造成状态竞争 | 单一事件队列、安全决策边界、TaskBookPatch 和版本检查 |
| 并行执行造成冲突或泄漏 | 依赖与读写集合判定、硬并发上限、分支取消、幂等记录、稳定归并和长时间资源增长检查 |
| 恢复重复执行副作用 | idempotency key、完成检查、检查点事务和恢复演练 |
| 后台运行变成隐形进程 | 托盘、状态、明确退出、用户关闭策略和活动任务提示 |
| 用户数据迁移中断 | 暂停写入、快照、校验、原子切换、保留旧目录和回滚 |
| 功能增强拖慢简单任务 | 复杂度分级、轻量路径和阶段 7 的延迟/打断指标 |

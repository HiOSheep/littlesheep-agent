## 1. 目标与约束

让维护者只阅读当前入口、职责说明和契约，就能理解 LS 的现在，不必先知道 next/legacy、TaskBook 第二执行器与旧 stage 的演进历史。收益必须落到减少误接执行路径、遗漏失败分支、错误理解恢复和证据、或修复真实任务阻碍上；不以改名数量、文件数量或行数下降作为成功指标。

- 保留唯一主循环和现有 Tool Execution Service、Context Engine、durable kernel 的权威边界。允许删复杂度、修 correctness 和补硬约束，不新增 stage、planner、scheduler、manager 或第二执行器。
- **当前执行契约、历史读取契约、历史展示内容分开表达。** 旧数据仍须安全可读；从当前执行类型中移走旧值，不等于删除磁盘记录、迁移用户数据或重写历史审计。
- `classify` 当前仍在 stage 注册表内，承担确定性路由；不能因为名字具有历史色彩就与未注册的 `decide` / `evolve` / `capture` 一并删除。
- 不做全仓 `legacy` / `next` / `TaskBook` 字符串清零。只读历史、旧格式校验、外部兼容别名和诊断原因仍可有真实用途，须按消费者判定。
- 机械改名、兼容读取调整、行为修复、模块搬迁分别形成可回滚的改动批次。HC-03/04 的行为差异须单独说明，不能混在“纯重构”里。
- 不改缓存口径，不隐去失败、重试、辅助模型调用和未知 usage，不通过放宽权限、跳过 observation 或丢弃未知副作用降低复杂度。

## 4. 新增任务

优先级：P0 为已确认的执行正确性缺口，P1 为当前语义与维护性收口。规模 S/M/L 为相对改动面，不承诺工期。以下复选框均为待办。

### HC-00｜冻结当前入口、消费者与行为基线（P1 / S）

依赖：无。范围：第 3 节入口、package exports、当前 stage registry、相关 codec / tests / README。

- [ ] 在本任务书补一张精简处置表：符号/字段、实际生产调用方、写入方、历史读取方、当前执行是否消费、处置（改名/归一/保留/删除）及所属任务。类型引用或单元夹具不算生产消费者；反射注册、字符串路由和外部导出同样检查。
- [ ] 冻结四条可追踪路径：新请求、工具失败后的继续、旧检查点恢复、最终回复发布；标出各自唯一状态写入方和来源。复用现有测试与图，不另建运行时注册系统。
- [ ] 固定小型脱敏旧数据夹具和当前请求夹具；记录当前入口实际产生的 stage、工具结果、事件顺序、请求数及 usage 状态。现有不正确行为只作为待修复基线，不永久冻结成正确契约。
- [ ] 重查并发工作及现有任务归属；不得顺手重构 RS/SA/UX/CTC 正在修改的领域。

验收：处置表能为每项删除说明“为何不再需要”，为每项保留说明“谁还在用”；不依赖全文字符串命中数或个人对历史的记忆。没有消费者证据的破坏性删减不执行。

### HC-01｜统一当前命名与调用入口（P1 / S）

依赖：HC-00。范围：Harness factory、`index.ts`、Runner 装配、`execute.ts`、`execute/runners.ts` 及直接消费者。

- [ ] 确定一个当前主入口名称：沿用 `createDefaultHarness` 或采用职责明确的 `createDurableHarness`，择一作为正常调用入口；去掉生产调用里的 `createNextHarness` / `nextHarness` 历史暗示。避免为了改名再增加一层转发。
- [ ] 将 `executeLegacyLoop` 及单入口的 `runners.ts` 改为符合当前职责的名称，例如 `executeMainLoop` 与 `main-loop.ts`；区分 stage 编排入口与 `runToolLoop` 的循环职责，不能只把两者改成相似泛名。
- [ ] 公开导出若确有外部消费者，旧名仅在包边界保留带弃用说明的别名，注明消费者与移除条件；仓内正常路径不得继续使用。没有兼容需求的旧转发直接删除。
- [ ] 更新说明当前职责的注释、README 和受影响脚本；真实历史格式说明不做机械替换。纯改名不改变磁盘 stage 值、模型提示、请求形状或工具描述。

验收：从 Runner 沿主入口到单循环能读出唯一当前路径；构建/类型检查及已有入口契约通过。对纯改名批次，冻结请求内容、工具目录和持久化 payload 等价，不为名字本身增加镜像测试。

### HC-02｜隔离历史读取契约与当前执行契约（P1 / M）

依赖：HC-00；与 HC-01 可分批，合并前统一命名。范围：`packages/types/src/{work-policy,stage-transitions}.ts`、Harness policy / checkpoint resume、Runner checkpoint codec 与相关 durable 读取边界。

- [ ] 在现有类型与读取边界区分“当前可执行值”和“历史可解析值”；运行中的 policy 只接受真实执行模式。`task_book`、升级请求及退休 stage 的 wire 值留在必要的历史读取类型内，不能通过宽联合类型重新变成普通执行选项。
- [ ] 将旧格式的纯校验/归一集中到已有 codec 或最小兼容适配点；当前运行入口不反复解释旧格式。依赖任务完成证据、权限或副作用状态的恢复决策仍由现有恢复所有者执行，不在解析时猜测。
- [ ] 活动 stage 转移校验只接受当前 registry 支持的路径；历史 trace / event 读取继续识别旧值。复用同一来源组织必要的当前与历史视图，不复制两份会漂移的转移事实，也不新增通用 stage 管理器。
- [ ] 区分新的执行决策与历史证据封套：新 run 不产生退休策略/阶段；恢复后的当前决策归一，原 stage、reason、来源和已完成证据按历史契约保留。禁止就地重写旧账本或为了消除字段丢弃恢复信息。
- [ ] 为每个保留别名/codec 记录所支持版本、消费者、测试与移除条件；未知版本、畸形值不能静默降级执行。`classify` 的当前注册行为保持明确。

验收：旧 `decide` / `task_book` 夹具只进入唯一现行路径且不额外规划；已完成、缺回复、unknown 副作用、权限变化、畸形/未知版本分别保持既有安全结果；新写入的执行状态不再混入退休选项。历史展示可读，原始字节不被本次重构改写。对话连续性专项的发布门与迁移/回滚演练仍归原任务。

### HC-03｜收掉 VERIFY 对旧执行器的隐式依赖（P0 / M）

依赖：HC-00；类型调整与 HC-02 协调，不必等整批兼容清理完成。范围：`stages/verify.ts`、`stages/verify/{routing,task-state}.ts`、当前工具证据与 VERIFY 集成测试。

- [ ] 从真实新 run 的入口证明两个窄结构验证分支是否可达；测试不得预填生产路径不生成的 `taskBook` / `taskExecution`，不得只直接调用验证函数后声称主流程有效。
- [ ] 对保留的窄验证，用当前权威 invocation / tool result / effect evidence 直接判定，保留调用顺序、目标、完整内容、工具来源、成功状态、截断和副作用一致性检查。不得伪造一份旧 TaskBook 来适配现有函数。
- [ ] 无生产意义的旧编排、空转发与步骤专属分支，在消费者核实后删除；确需支持历史完成任务的部分进入 HC-02 的明确兼容范围，不让当前主循环依赖它。
- [ ] `pass` 仍只证明具体窄结构事实，不提升为自然语言结论正确或完整业务验收通过。复杂、混合或无法证实的任务仍 `unverified`；失败和未知副作用不因重构升级为成功。不新增验证模型、通用验收平台或交付物级连续性机制。

验收：真实当前 Harness/Runner 接线产生的单只读、精确写后读回正例走到预期窄验证；错误内容、不同路径、调用乱序、插件冒充、截断、混合未验证操作、失败/未知副作用分别不能获得不当 `pass`。旧数据兼容例与当前行为例明确分组；通过数不能掩盖当前路径没有调用的代码。

### HC-04｜区分新的合法执行与恢复重放（P0 / M）

依赖：HC-00；独立 correctness 批次，不与改名或拆分混交。范围：`stages/execute/{side-effect-ledger,side-effect-lifecycle}.ts`、现有 effect identity / lease / checkpoint 接线、`builtin/exec.ts` 及工具执行边界。

- [ ] 固定复现：同一活跃 run 内成功运行一个验证命令，修改受控目标后，以完全相同参数再调用该命令；记录当前拒绝位置。与“崩溃后重放同一次调用”分成两个测试。
- [ ] 在现有调用、操作与尝试身份上作最小修正：恢复重放继承原身份；有依据的新调用获得可追溯的新身份；输入哈希用于参数一致性和重复检测，不能单独证明是同一业务操作。身份须由 Runtime 绑定并持久化，不能由模型随便换 ID 绕过约束。
- [ ] 定义何种新调用可继续（例如有已记录目标变化的再次验证），保留重复调用上限、无进展预算、权限、observation 及未知副作用阻断；不能把所有相同参数一律放开，也不能以 Shell 文本看似只读作为无副作用证明。
- [ ] 同一身份不同参数拒绝；响应丢失/重启只核对或复用原结算，不重复调用。旧输入哈希身份仍按旧边界保守读取，不重解释旧成功记录为未执行。
- [ ] 明确失败命令也可能已发生部分修改；不能仅凭非零退出码宣称“零副作用”并自动重试。保留已有确定失败与未知结果的事实，不将本项扩展成外部系统通用 exactly-once 承诺。

验收：成功→目标改变→同命令验证可完成且有两次独立执行证据；同一次操作的提交重试、结果丢失与恢复只产生一次效果；无进展重复仍受限，unknown/in-progress 不因新 ID 被绕过，并发重复只由一个 owner 执行。先通过确定性/进程级证据，再用隔离工作区做一次真实模型“验证→修改→再验证”验收；全量记录调用、失败和成本。未做真实流程时保持部分完成。

依赖：HC-01/02/03；HC-04 按独立行为预期加入。范围：现有核心契约测试、包导出测试、checkpoint 夹具和模块拆分地图中的两个接缝。

验收：当前契约测试能发现旧模式被重新接入、结果/调用错配、重复结算及漏记失败；兼容测试能发现旧数据被误删或错误恢复。新维护者能从测试分组判断哪项是现行能力、哪项只保护旧数据。

## A1 统一的界面语言层（Locale / 消息目录）

- **证据**：`窗口` —— 中文界面里冒出一整段英文 Runtime 状态：`Runtime is waiting for user action; no final reply was published. Reason: model_response_missing` ✓（崩溃恢复后答案位置 ✓，两种模式各观察到一次 ✓）；`源码` —— `packages/runner/src/authoritative-reply.ts:220` **硬编码英文** ✗。差距清单 **#18（P1）** ✓。
- **为什么现有架构补不上**：文案分散在 runner / main / renderer 三处，各自硬编码 ✗；没有"面向用户的运行时状态"文案归属地 ✗，也没有语言来源（当前 UI 语言是中文，但代码里没有语言概念 ✗）。只把这一句改中文 ✓ 能缓解 ✓，但同类硬编码还会继续产出 ✗（每条都要单独发现、单独修 ✓）。
- **最小变更**：一层**极薄的运行时文案目录** ✓（键 → 中文文案 ✓，缺失键回退到原字符串并在门禁里报错 ✓），只覆盖 **Runtime 状态 / 失败原因** 这一类面向用户的短句 ✓；**不引入完整 i18n 框架** ✗、不做多语言切换 ✗、不翻译日志与诊断 ✓（reason code 留在日志 ✓）。
- **成本/风险**：中低 ✓（一个模块 + 一次全仓硬编码扫描 ✓）。风险：若被当成"要做 i18n" ✗ 会失控 ✓ → 必须限定在上面的范围内 ✓；改 runner 会作废 app 构建指纹 ✓ → 需重建并重跑门禁 ✓。
- **否决后的替代**：逐条把面向用户的硬编码文案改成中文，并在**代码评审**（而非架构）层面保持 ✓ —— 代价是每条都可能被漏掉 ✓。

## A2 统一的焦点与浮层管理器

- **证据**：`窗口` —— ①设置页搜索输入框聚焦时 **0 环像素、0 填充像素** ✗（**#19，P1** ✓，同页导航项 2538 环像素 ✓）；②"完全访问"警告**不接管焦点** ✗ → 真实按下 Enter 会激活**后台控件** ✓（实测那次直接导航走并静默关掉警告 ✓，**#10，P1** ✓）；③权限选择器的聚焦项**几乎无环** ✗（列表裁切 + 相邻项覆盖 ✓）。`源码` —— `ui/modal-surface.ts:59-68` 只在 `active` 变化时聚焦一次 ✓，那时 `ui/presence.tsx:88` 首帧返回 null ✓ → **永不重试** ✗；`07-overlays-settings.css` 对 `input:focus` 关掉 outline 且**无替代** ✗。
- **为什么现有架构补不上**：焦点规则现在散落在每个组件里（有的用 `useModalSurface` ✓、有的手写 ✓、有的忘了 ✗），**没有单一归属** ✗；"聚焦一次"的假设与"首帧挂载"的现实冲突 ✓ → 每个新浮层都可能重犯 ✓（这正是三处缺陷的共同形状 ✓）。
- **最小变更**：把"**谁该持有焦点**"抽成一处 ✓：初始聚焦**下一帧重试直到成功或超时** ✓ + 关闭时归还触发元素 ✓ + 一小组**焦点可见性断言**（环或填充必须非零 ✓）作为门禁 ✓；**不做**完整 focus-trap 框架 ✗。
- **成本/风险**：中 ✓（约 3–5 个文件 + 一处门禁 ✓）。风险：改 `modal-surface` 会同时影响审批、危险确认、完全访问警告 ✓ → 必须逐个人工复核 ✓（门禁只能证明"有焦点"，不能证明"焦点对" ✓）。
- **否决后的替代**：逐个修 ✓（#19 ✓、#10 ✓、权限选择器 ✓）—— 代价是**同一类缺陷会继续复现** ✗，每次都要靠取证发现 ✓。

## A3 结构化的窗口 chrome 契约

- **证据**：`窗口`＋`原生` —— 固定的三个窗口按钮在真实鼠标下**点不动** ✗，原因是 `-webkit-app-region` 发布的可拖动区域**按 DOM 先序累积、忽略 z-index** ✓，而 `no-drag` 只能扣**它之前**的矩形 ✓ → 修复只能靠一个**生成的 `::after`** 命中区 ✓（先序最后 ✓）才生效 ✓；这个机制**在 DOM 里完全不可见** ✗（DOM/CDP 检查全绿而真实点击失败 ✓）。
- **为什么现有架构补不上**：拖动区域与界面元素是**两套互不知情**的系统 ✓（CSS 声明 vs OS 命中 ✓），任何新浮层/新按钮都可能踩同一个坑 ✗；现在的修法是"在正确的位置插一个不可见的洞" ✓ —— 能用 ✓ 但**脆弱且不可读** ✗。
- **最小变更**：把窗口 chrome 的规则**收进一处可断言的契约** ✓（用户已起步：`packages/app/src/shared/window-chrome-contracts.ts` ✓ + `desktop-window-chrome.ts` ✓）：声明"哪些区域可拖动、哪些控件必须可点" ✓，由门禁**按原生命中测试**（`WM_NCHITTEST`）验证 ✓，而不是靠人记得先序规则 ✓。
- **成本/风险**：中低 ✓（契约与门禁已部分存在 ✓）。风险：进一步抽象可能把"简单布局"变复杂 ✗ → 限定为**只做断言与登记** ✓，不引入运行时框架 ✗。
- **否决后的替代**：保持现状 + 把"新增顶部控件必须做原生命中测试"写进约定 ✓ —— 靠人守规则 ✓。

## A4 长会话的虚拟化转录

- **证据**：`源码`＋`窗口` —— 单轮文本回合约 **308 个 DOM 节点** ✓，**无虚拟化** ✗；分页是每次 120 条 ✓；审计**没能**构造 200 轮会话 ✓（故此项**尚无实测痛点** ✓，只有成本模型 ✓）。
- **为什么现有架构补不上**：转录是**全量渲染 + 折叠** ✓，节点数随轮数线性增长 ✓；分页缓解但**首次进入长会话**仍要渲染已加载的全部 ✓。
- **最小变更**：**分窗口渲染**（只挂载视口附近若干轮 ✓，保留滚动锚定与"回到最新"语义 ✓）。
- **成本/风险**：**高** ✓（滚动锚定、搜索、折叠、复制、屏幕阅读器顺序都依赖当前全量 DOM ✓）。**因此我建议：先测再决定** ✗ —— 构造一个真实的长会话，测首屏时间与内存 ✓；只有数据证明是瓶颈才做 ✓。
- **否决后的替代**：保持现状 ✓ + 把"长会话首屏耗时"纳入既有启动/性能台账 ✓。

## A5 设置项的字段级索引

- **证据**：`窗口` —— 搜"压缩阈值"/"Tavily"/"关闭窗口"都返回"没有匹配的设置" ✗（而这些设置**存在** ✓）；命中只显示页面标题 ✓，看不出为何匹配 ✗；结果**不能用方向键导航** ✗（**#13，P2** ✓）。
- **为什么现有架构补不上**：索引只由 `title + desc` 拼成 ✓（`settings/navigation.ts:78-94` ✓），**没有字段级元数据** ✗ → 要支持字段级搜索，必须有人**登记每个字段** ✓。
- **最小变更**：给设置页补一层**字段清单** ✓（字段名 + 同义词 + 所在页 ✓），搜索按它匹配并显示**命中原因** ✓；结果项接键盘导航 ✓。**不引入**通用搜索框架 ✗。
- **成本/风险**：中低 ✓（纯数据 + 少量渲染 ✓）。风险：字段清单会**腐化** ✗ → 需要一条门禁断言"每个受控输入都在清单里" ✓。
- **否决后的替代**：只改空态文案为"没有匹配的设置**页面**" ✓（诚实 ✓ 但仍搜不到 ✗）。

## A6（开发侧，非产品架构）原生命中测试作为标准能力

- **最小变更**：把已有的原生命中探针**提升为可复用工具** ✓（`verify-window-layout.mjs` 里已有 ✓），并规定"涉及窗口 chrome / 拖动 / 顶栏控件"的修复必须调用它 ✓。
- **成本/风险**：低 ✓（已有实现 ✓）。**这条我建议直接做** ✓，因为它已经在防止返工 ✓。

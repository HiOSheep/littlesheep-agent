# LittleSheep 核心 Agent 流程规范

最后更新：2026-09-24 21:29:06

本文是 [LittleSheep 架构原则](architecture-principles.md) 在 Core Flow、TaskBook、验证、恢复和记忆运行时上的专项约束。LLM 与 Agent、Mode 与权限、Context 与 Memory、Harness 与 Tool Execution 的顶层分工以架构原则为准；本文不重复维护另一套总架构。

当前每个请求只产生一次主循环模型调用：模型要么直接回答，要么请求一个受控工具，工具结果追加回同一循环后再决定是否需要下一次调用。不存在第二次规划请求，也不存在第二个执行器。

## 核心原则

状态机存在的目的，是提升 Agent 的判断和执行能力，而不是为了维护状态机本身。如果某个状态、提示词契约或数据结构阻碍了更好的判断或执行，就应当修改或重构它。

## 目标流程

每次 run 先经过确定性的活动路由，它不消耗模型请求，只产出两条路径：每个请求都进入单一主循环，"复杂/大型/续接/检索"只作为解释性 reason code，不再换取第二次规划请求或第二个执行器；已持久化的 TaskBook（旧 checkpoint）是只读历史，其步骤执行器已删除：

```text
ENTER -> 活动路由 -> execute（每个请求，含常规会话/工具工作/续接） -> EXECUTE（单一主循环） -> VERIFY -> FINALIZE
                 -> 能力/状态询问 -> REPLY（最小 Runtime 事实契约） -> FINALIZE

EXECUTE 主循环内部：
  模型直接回答，或请求一个受控工具
  -> Runtime 重新判定权限、范围、资源与副作用
  -> 执行并记录证据，把结果追加回同一循环
  -> 需要更多步骤时在同一循环内继续
  -> 缺少一个关键事实时，模型可调用 request_user_input 在本循环内提问

ASK_USER 不是可路由活动，只有两条到达路径：
  主循环内模型发起的 request_user_input
  -> 或 RECOVER 在权限拒绝 / 恢复预算耗尽时升级
  -> ASK_USER -> FINALIZE

残留的 DECIDE 兼容面（无执行器，只为读取旧检查点）：
  归一化既有 TaskBook 供读取与展示
  -> 不调度、不执行步骤；无法安全映射的旧活动任务进入明确的待恢复状态
```

路由只区分两种读法：`execute` 承载全部常规会话与工具工作，能力/状态询问走 `reply` 的最小 Runtime 事实契约。`respond`、`clarify` 都不是可路由活动，缺少信息时由回复本身追问；内部 `classify` stage id 与旧 `chat / problem / unclear` 字段暂时只承担会话、检查点和插件兼容，不再定义产品语义。

## 用户体验契约

- 日常工作应当自动、少打断。用户不需要理解状态机、记忆索引、恢复循环或内部规划契约，也能得到完整结果。
- LS 的目标是解放用户生产力：用户专注于想法和目标，LS 负责拆解、执行、验证、整理和沉淀，减少用户在重复操作和过程搬运上的负担。
- 内部细节采用渐进披露：默认只显示有用的最小状态，但任务书、执行证据、记忆来源、阈值和高级策略必须可以按需查看。
- 执行中默认显示当前步骤、等待状态和关键结果；可审计的公开推理轨迹在运行中与结束后均直接可见。命令参数和大段原始输出仍可折叠，避免遮蔽任务结果。
- 最终回复按“结论/状态 → 关键结果与产物 → 必要证据和下一步 → 可选详细过程”的层级组织。简单任务不生成重量级报告；失败、风险、权限拒绝、部分完成和待用户决策必须在默认层明确表达。
- 渐进披露不等于披露隐含思维链。Agent 应提供可操作的步骤摘要、事实依据、验证结果和决策边界，不输出私密逐字推理。
- 用户始终拥有对真实运行时系统的高度控制权。设置页和管理页必须修改 Agent 实际使用的同一套策略、索引、权限和记录；只改变外观或只在 UI 内生效的开关不满足要求。
- 改变持久状态的自动行为必须记录理由、来源、作用域和结果。可恢复行为必须通过对应管理界面提供恢复或撤销路径。
- 必须提供可靠的安全默认值。高级自定义是可选项，不能变成正常使用前必须完成的配置工作。
- 少打断不等于绕过授权。研究/受限模式继续按权限矩阵请求批准；进入完全访问必须先由用户在专用红色警告中一次确认。核心源码只读、危险命令硬拒绝和不可由权限模式覆盖的高风险边界始终有效。

## 需求校准

需求校准发生在单一主循环内部，不再有独立的规划请求：

- 识别用户真正想解决的问题，而不只照搬字面措辞。
- 复杂度、范围和成功标准由 Runtime 与模型在同一循环内共同收敛；"复杂/大型/续接/检索"只作为解释性 reason code 记录，不改变提示形状或工具集。
- 小请求不能套用重量级工作流。
- 只有缺少关键信息、需要用户承担明显成本/风险，或存在必须由用户决定的重大分岔时才询问；提问由主循环的 `request_user_input` 发出，Runtime 按 Runtime 事实结算。
- 有价值时可以适度超出用户预期，但超出范围或成本不得高于用户请求的 3 倍。

## TaskBook 的当前地位

`TaskBook` 的类型、持久化与展示仍然存在，但本轮不再产生新的任务书：

- 第二条执行体系（TaskBook 步骤执行器、步骤调度与依赖波次并行）已删除，多步骤工作在同一个主循环内串行推进。
- 已持久化的 TaskBook 只作为**可读历史**供恢复、展示与审计使用，不会触发第二个执行器。
- 无法安全映射的旧活动任务进入明确的待恢复状态，而不是被静默重放或猜测执行。

## 运行中输入与任务书修订

- 长任务运行期间，用户可以追加要求、纠正目标、暂停、恢复或请求中断。LS 只接收自身界面、已启用渠道和用户明确授权观察范围内的事件，不进行系统级全局监控。
- 运行时事件先进入有界队列，并在步骤结束、工具调用返回、权限等待、验证失败等安全决策边界处理。已经发出的外部副作用不能被新消息静默改写。
- 相关新信息在安全决策边界被消费，并可产生确定性的 `TaskBookPatch`；修订只影响尚未开始或确实需要重做的部分，已完成步骤、证据、权限结果和已提交副作用必须保留。
- 无关事件不得抢占当前动作；重复事件应去重，过期事件应被丢弃或标记，队列必须有长度、保留时间和单次消费预算。
- 若新要求与已完成的不可逆动作冲突，必须明确告知当前事实并进入 `ASK_USER`，不能伪装成仍可无损回退。

## 执行

`EXECUTE` 是单一主循环：模型在同一循环里选择直接回答或请求受控工具，Runtime 负责权限、校验、执行、记录，并把结果追加回同一循环。

- 工作量必须与校准后的复杂度匹配。
- 只有在降低不确定性或完成目标确实需要时才调用工具。
- 除非能直接改善用户目标，否则不要额外扩大工作范围。
- 如果需要证据，先用工具验证，再声称完成。
- 同一模型响应中可以出现多个独立工具调用，由 Runtime 依据声明的资源访问、路径重叠、副作用、审批与依赖关系分波执行；同一文件、同一外部对象或需要顺序验证的副作用必须串行。并发度、队列长度和总成本必须有硬上限。
- 每个宿主工具调用都必须受统一的运行时超时控制；默认上限为 120 秒，配置只允许在 1 秒到 24 小时之间，且仍受 run 总超时、AbortSignal 和取消后的有界清理窗口限制。超时或上级中断先传播取消信号，并给工具一个短暂、有界的资源清理窗口；忽略中断的插件不能无限占住 run。
- 命令输出必须按首尾保留方式有界捕获，并记录原始长度、保留长度和截断状态。超时或中断后的命令必须终止整个进程树并等待 `close` 或有界强制收尾，不能只结束父 Shell 后留下子进程、管道、监听器或计时器。
- 工具结果按模型原始调用顺序进入对话与证据，不能因为运行时完成顺序不同而改变最终事实、权限结论或回复结构。
- **一次越权调用不等于整轮失去工具**：请求准入范围之外的调用照样被拒并记入转录，但它是 Runtime 刚做出的范围决定，属可纠正失败——被准入的工具在下一轮仍然可用。把"没有执行记录"一律当成未知边界会让一次越权调用触发强制收尾，连本该可用工具也被锁死，任务产物因此根本无法生成。
- **提问轮里的兄弟调用不执行**：模型在同一批里既提问又调用其它工具时，与提问同批的调用以带原因的拒绝结果记入转录，提问本身照常发布；不会因为同批带了别的调用就把整轮判失败。提问是等待用户决定，不是运行失败。
- **交付优先于自我验证**：在本次 run 的额度内交付可用产物；反复重测同一个产物不构成验证，也不是继续工作的理由。接近上限时先交付已经完成的部分并说明边界，而不是把额度花在重复确认上。
- 当前阶段 LS 可以只读检查自身核心源码，但不得通过内置 `write`、`edit` 或 `exec` 修改它。该边界由宿主解析真实源码根并在工具执行前硬拒绝，优先级高于完全访问模式和单次批准；后续受控自我修改必须另立任务书、隔离环境、验证与回滚契约。

## 信息来源与可靠性

- Agent 的判断必须区分用户明确陈述、受信系统状态、工具实测结果、记忆/RAG 召回、模型推断和未知信息。
- 每条输入陈述还必须区分 instruction/goal、preference/value、reported observation、factual claim、suggestion/hypothesis 和 decision/approval。来源是谁与陈述是否为真是两个维度，不能因为来自用户、官方资料或模型就跳过验证状态。
- 用户对自身目标、偏好、授权、主观体验和最终取舍具有最高权威；对代码、系统状态、客观世界和因果关系的陈述仍是可验证 claim。用户选择一个方案会约束执行，但不会自动证明方案理由正确。
- 某条用户建议有误时，只修正该 claim 或方案，不生成“用户不懂该领域”的长期画像。若错误前提会影响结果、安全、成本或不可逆操作，先验证并明确说明；不影响目标时保留用户意图并使用更可靠的实现。
- 工具结果和记忆片段进入 Context 前必须保留来源、时间、作用域和截断状态。被截断、过期或未经验证的信息不能当作完整事实。
- 附件默认先注册清单、类型、大小、来源和受管位置；正文、图像或结构化内容只在当前步骤确有需要时读取，不能因附件存在就全量注入。
- 当多个来源冲突时，优先使用当前用户明确要求和更新、更直接的可验证证据；仍无法可靠判断时进入澄清或验证，而不是选择最方便的答案。
- Agent 必须区分实体边界与实体关系。名称相似、共同出现、目录相邻或向量接近只表示候选关联，不能自动证明同一实体、所有权或因果关系。跨用户、项目、会话、插件所有者和权限作用域的关系必须保留方向、证据、置信度、有效时间与冲突状态，并按 D0-D3 渐进展开。
- 每个 run 维护版本化 `KnownState`，统一登记已验证事实、用户陈述、建议、决策、记忆证据、工具证据、假设、未知项和冲突项，并保留 statement kind、epistemic status、authority scope、asserted by、evidence refs、来源、时间、作用域、置信度与截断状态。
- 主循环 EXECUTE、VERIFY 和 FINALIZE 必须从同一条 `KnownState` 版本链读取事实，并记录各自使用的版本。新工具结果、用户修订或验证结论只能通过事件生成下一版本；不得依赖聊天文本之外的隐含状态，也不得把模型跨调用的主观记忆当作事实。
- 每个阶段只把当前决策所需的 active evidence set 投影到 `ContextSnapshot`。无关、重复、被替代、过期或低收益信息可以从后续请求中退出，但排除理由和来源引用仍保留在 `KnownState`；需要时可重新激活，不能把“本轮不注入”误当作删除记忆。
- 对话上下文以 `sessionId` 为硬边界：recent history、版本化会话摘要、上一轮执行 sidecar、等待用户的 Checkpoint、澄清状态和运行中临时状态只能从当前会话装配，不能使用全局“最近一份”替代。长期记忆树可以跨会话保存和发现知识，但只能沿受控索引、当前任务相关性、作用域和来源证据进入当前 run；这不等于把其他会话的原始消息或完整摘要自动并入当前 Context。
- 关键未知或冲突会实质影响范围、权限、不可逆操作或验收时，必须先沿索引补取记忆、调用工具验证或进入 `ASK_USER`。可以继续执行的假设必须显式登记，最终交付时说明尚未验证的边界。

## 时间、进度与耗时感知

- 按极简执行方案，秒级时钟不再逐请求注入 Context：它是每次调用都变化的尾部内容，既不是判断输入，也会让缓存边界之后的尾部永远无法复用。精确时间由状态查询工具（`session_status`）在用户询问时返回，模型不得根据聊天内容估算时间。
- 每次请求只投影会改变本次答案的 Runtime 事实，并按变化频率分层：per-run 稳定的能力快照/epoch/权限策略/工作区/网络/工具可用性进入主 system 提示之后、历史之前的可缓存前缀；会随 run 推进变化的任务状态与进度、能力探针结果和权限决定留在缓存边界之后的尾部最小变更说明。普通请求没有变化事实时不追加尾部段，前缀之外只剩新输入与回答。
- 工具返回给下一次模型决策时必须携带结构化 `status` 和 `durationMs`；超时、异常和正常完成均记录实际墙钟耗时。工具正文仍按既有清洗与截断规则处理。工具耗时属于工具结果本身，不再额外汇总进每次请求的尾部运行态。
- 执行日志域仍按会话持久化上一轮 run 的有界原子 sidecar：总状态、总耗时、步骤完成数、工具成功/失败计数、累计工具耗时和最多固定数量的最近工具计时。它供 UI、回放和按需读取使用，不再逐请求注入 Context；完整输入输出只保留在单 run 执行日志，sidecar 以哈希会话键定位并按会话串行原子替换，避免改写整段会话或让 Context 随使用次数无限膨胀。
- 普通回复不主动回放上一轮执行详情，也不堆叠低价值数字。只有状态解释、失败、超时、成本、风险或验收需要时，LS 才主动显示相关进度和耗时；普通闲聊和新主题不得被旧执行详情污染。
- 默认输出保持安静。用户询问时间或耗时后，由 Runtime 的当前值或工具/执行记录回答，模型不得编造精确数字。

## 验证

`VERIFY` 只断言 Runtime 证据能证明的事实，不再请求验证模型：

- 窄结构形态（单只读步骤、写后读回等）由结构性通道判定为 `pass`；通道条件覆盖复杂度、步骤数、工具身份、截断状态、副作用匹配与路径/内容一致性。
- 其余已完成的 run 记为 `unverified`：记录到的工具证据完整、全部调用成功，且存在可回查到真实 Provider 请求的模型回复，但需要人工判断的验收标准未经验证。
- 记录到的失败、缺失步骤、截断证据、未结算副作用或缺少模型回复一律不能变成 `pass`，走既有的有界恢复、局部重规划和达到上限后的用户决策路由。
- **"不可用证据"与"已记录的负结果"按 Runtime 知道什么分界**：权限结果（`approval_denied` / `approval_unavailable` / `hard_denied`）表示"还没有人决定是否授权"，只有用户能决定，因此升级到 `ASK_USER`；Runtime 自己在执行前发出的拒绝（`validation_failed` / `unknown_tool` / `repeated_call_blocked`）是确定性结果——调用根本没有执行——连同 `failed` / `timed_out` / `aborted` 一起留在记录里，让已交付的 run 停在 `unverified`。把后者当成"证据缺失"会把已经交付的工作变成一句提问。
- `unverified` 可以继续路由级反馈（运行事实完整且未失败），但不得提高 atom 的 verified usefulness、不得被 UI 表达成“验证通过”，也不得把 reported/unverified claim 写成 verified fact。
- 完整对照仍列出原始请求、校准目标、成功标准、步骤验收、工具结果、`KnownState` 版本与被采用建议的验证状态，用于人工复核和审计记录。

没有错误不等于任务完成：只有 `pass` 才代表 Runtime 证明了记录的验收；`unverified` 必须如实呈现为未验证，不得改写成通过。

对高价值或关键任务，一次失败不能直接被包装成最终结果。只要仍有新的诊断证据、可逆修正路径且未触发次数、时间、成本或安全上限，就应进入局部 `RECOVER`；只有恢复耗尽、需要重大用户决策或无法安全继续时，才进入 `ASK_USER` 或有边界地结束。

## 中断、恢复与循环上限

- 用户中断、应用关闭、进程异常和可恢复故障必须拥有不同的终止原因，不能都压缩成普通失败。
- 切换或隐藏对话只改变界面焦点，不应取消活动 run；关闭最后窗口是否转入后台由用户策略决定；暂停保留现场但不继续调度；中断停止当前 run；放弃任务结束恢复资格；彻底退出负责停止进程并处理仍活动的任务。
- 当前步骤、TaskBook 版本、已完成证据、待处理事件、权限结果、外部副作用 idempotency key 和必要的 Context 来源应写入版本化检查点。
- 恢复只能从明确的幂等边界继续。已成功写文件、发送消息、创建资源或执行其他副作用后，恢复时必须先检查结果，不能盲目重放。
- `VERIFY -> RECOVER -> EXECUTE`、局部重规划和工具重试都必须同时受尝试次数、总时长、成本/上下文预算和无进展检测约束。`RECOVER` 不请求恢复模型：可重试失败回到产生失败的阶段，权限拒绝升级到 `ASK_USER`，副作用未结算或运行被中止则显式停止并只呈现 Runtime 状态；恢复不生成“修订计划”，也不撰写用户文案。
- 连续两轮没有新增证据、没有缩小失败范围或重复同一错误时，应计入无进展；达到上限后进入 `ASK_USER` 或有边界地结束，禁止无限循环。
- **不可能成功的重试不允许空转**：run 的模型调用预算一旦耗尽就直接升级，不再重试同一件事；`VERIFY` 对已记录证据给出的结构性缺口第一次回到主循环让模型闭合它，第二次直接升级——重试 `VERIFY` 只会得到同一结论，缺口只能被"同一步骤里更晚的成功调用"顶掉。
- 应用重启后的活动 run 恢复必须由持久化检查点驱动，不能依靠 renderer 内存或聊天文本猜测执行位置。
- 恢复能力不以固定重启次数为上限。只要检查点版本仍受支持、数据完整且未被用户放弃，重复重启后仍应从幂等边界继续；检查点历史本身必须按容量、版本和保留期有界管理。

## 记忆运行时

- 系统提示词只携带受限长度的根索引；记忆规模增长不能让基础提示词按比例膨胀。
- 记忆读取严格索引优先：从预加载根索引进入一个分支索引，再展开一个相关节点或查询。运行时在触碰记忆来源前拒绝跳过层级。
- 深搜绝不跨树。必须在同一次 run 中明确指定一个已经成功读取分支索引并完成展开的分支。语义/向量召回只能作为该分支内的最后兜底候选来源。
- 记忆读取只有 `memory_tree` 一个入口：root_index 返回根索引，branch_index 返回选定分支索引，expand 与 deep_search 才可能注入正文；兼容检索别名已删除，不得重新注册重复入口。
- 每次记忆介入都必须有预算、去重、来源追踪、安全封套，并记录到当前 run 账本。
- 记忆运行时采用四层模型：对话原始来源、投影变更记录、Atom projections 和 run working set。对话原始来源只保存用户输入与对话区可见的 LS 回复、步骤、工具过程、验证和错误，成功写入后不改写；投影变更记录只服务幂等、恢复和审计；Atom 用于层级、相关性、检索和治理，可去重、合并、调整父级、失效、恢复或重建；working set 只决定本轮实际介入。物理文件位置和分层方式只服务持久化、恢复、人工管理与索引导航，不能成为注入分数。Runtime 必须显式维护“哪些 Atom 被发现、采用、排除、释放或重新激活，以及为什么”，并让这些决策随当前任务、关系、证据、时间和已验证效用变化，而不是随文件路径变化。Recovery journal 是有界恢复队列，不是原始数据源。
- 首次业务请求先检查 D1 索引元数据，当前安全默认最多选择 2 个 D2 Atom、总预算 600 tokens，并要求 task relevance 严格高于 `0.25`。通过门槛后默认只保留最强相关簇，再按 scope、authority、confidence、importance、epistemic status、verified usefulness、routing/relationship relevance 和时效排序；只有由高相关种子通过有效语义关系发现、且 route strength 达到硬门槛的必要 Atom，才可跨越普通相关性断层与种子一同进入首次 working set。普通较弱尾部即使治理优先级较高，也只留在索引中供后续展开。没有候选达标时保持零注入，只记录各分支 D1 检查，不为凑数量加载无关正文；不得默认跨树向量召回。初始采用结果必须立即同步到 run 级 `KnownState`。执行中模型可通过受控工具请求继续展开，也可 `release` 当前无用 Atom；release 只释放本轮 Context 与 dedup 预算，不能删除或失效持久记忆。
- 初始注入先形成有界任务语义，而不是把 recent history 直接拼进检索词。当前请求已经包含完整目标时只使用当前请求；只有真实指代、延续或 LS 方案引用才继承最多 2 条、总计 1,200 字符的最近 user/assistant 文本，tool/system 内容不参与。显式任务转向必须切断旧历史。硬排除对象、正向替代方案和“该对象已被否决”这类约束 Atom 分开判定：被排除正文不能因词面相似进入 Context，方向一致的约束仍可介入；“避免某问题”默认属于要解决的正向主题，不等同于禁止检索该问题。D1、FTS 和分支内向量检索必须共用同一任务语义。深搜候选出现清晰相关性断层时应在断层处停止，不能为了填满调用方 limit 注入明显较弱的 Atom；候选整体偏弱或连续时则保持保守，不凭一个固定阈值武断裁剪。
- 长会话压缩后的版本化摘要只在真实指代且最近消息仍缺任务锚点时作为 `continuitySummary` 回退。摘要最多选择 4 个目标/未完成事项/下一步/约束/决定句段、总计 1,000 字符；当前请求、近期明确用户目标和任务转向优先。摘要不替代原始会话、不复制为长期记忆，也不因保存位置或新鲜度自动获得注入权重。
- 在已导航分支和当前作用域内，候选按 scope 匹配、来源权威、task relevance、confidence、importance、新鲜度、verified usefulness、routing relevance、relationship relevance 以及冲突/失效/过期惩罚稳定排序。关系不只是排序信号：Runtime 可从 `task relevance >= 0.7` 的种子做一次有界一跳发现，但必须保持同 branch/scope/scopeKey/subtree，并检查关系方向、状态、生效/过期时间、authority、confidence、relevance 和来源/证据；邻接 Atom 仍须独立通过 task relevance 和预算。`similar-to` 只作导航，不触发自动注入。关系信号必须随当前 task relevance 降低而向中性收缩，不能让“历史关系多”替代“本轮真正相关”。高优先级记忆先介入，但不能挤掉安全规则、当前用户输入和必要工具证据。可选记忆长期没有验证收益时降低注入权重，但不自动降低 confidence；T0、安全规则和当前用户约束不参与普通使用衰减。
- 读取次数、重复出现或仅停留在 Context 中都不产生正反馈。VERIFY 不再由模型返回 `usedMemoryAtomIds`；显式使用的唯一运行时可证来源是回答级连续性评估（最终回答中出现当前输入之外、且真实进入本轮调用链的 active/adopted Atom 独立锚点），它只提高有界 routing usefulness。只有结构性 VERIFY（`pass`）且存在非记忆导航、非 Skill 加载的独立成功工具证据时，才提高 verified usefulness；`memory_tree` 和 `use_skill` 的成功只能证明导航或加载发生，不能冒充任务验证。两类反馈都不能自动提高事实 confidence。显式 `release` 只是未验证路由反馈，不能证明 Atom 错误；未进入 active Context 或未被明确使用的冲突候选也不能因一次检索自动生成负反馈。所有反馈必须可审计、幂等且有硬上限，防止错误记忆形成自增强循环。
- FINALIZE 必须对实际发布且可由 `ReplyProvenance` 回查到实际 Provider 请求的 LLM 回答执行本地、有界的记忆连续性评估。当前用户输入的词面重合只能证明回答贴合本轮任务，不能证明记忆连续；TaskBook 中若含有本轮记忆介入后新增的细节，仍可作为间接承接链路。只有回答中出现当前输入之外、且真实进入本轮因果模型调用链的 active/adopted Atom、版本化会话摘要或近期跨轮对话的独立锚点，才可标记为 `supported`。任务续接与直接记忆追问都属于显式连续性检查；明确字段旧值按“近期可观察消息 → 已进入调用链的版本化会话摘要 → 已采用且仍 active 的记忆”逐项解析，纯记忆追问不得因此注入无关执行耗时。字段识别可从真实来源动态发现任意明确 `label: value`，但必须绑定标签和值，支持 Markdown 加粗、反引号与表格，也支持 `executionCount / 执行次数`、`ticks`、`completed` 等执行证据以及短数字、布尔值；无关位置出现相同短值不能冒充命中，每个成功字段至少贡献一项独立证据。最终回答必须分别肯定命中每个被追问值；只复述附带限制、漏答任一值、答错、用否定句提到旧值、明确说忘了或请求用户重新提供，均标记为 `discontinuous`。旧值全部出现也不构成例外：回答只要同时明确否认记得，就必须默认拒绝，且不能登记任何记忆来源为已承接。弱改写、Context 截断或目标不可回查时保持 `uncertain / unavailable`，不得武断判为失忆。显式连续性检查只有 `supported` 可以通过；其他状态不能被 UI、Runtime 或测试报告改写为“记忆连续”。Context Engine 已裁掉的来源、缺少请求快照的来源、已释放、已排除或冲突 Atom 均不得获得连续性命中；执行中由 `memory_tree` 展开的 Atom 只有在对应工具结果确实进入后续模型请求时才可计入。保存会话、生成摘要、写入 Atom、命中索引或完成检索都只是前置证据，不能代替对 LS 最终回答的判断。FINALIZE 的审计本身不增加 Provider 调用；回答级 Atom 或摘要命中最多形成 routing/activation 反馈，不能提高事实 confidence 或 verified usefulness，也不能替代 VERIFY 的工具证据。直接 REPLY（能力/状态询问）与主循环发布常规会话回答之前都可以复用同一纯本地评估：候选不是 `discontinuous` 时不得追加调用；只有明确续接且首稿遗漏、否定或冲突于真实可见旧值时，允许一次实时 Provider 纠偏。纠偏后仍为 `discontinuous` 必须默认拒绝，不能登记错误候选，也不能循环修正。
- routing feedback 的历史计数用于审计，排序使用与 confidence 分离的派生相关度和有效证据权重。派生值随时间回归中性；新事件到来时先按时间衰减旧权重，再加入新证据，不能因更新时间刷新而让已经衰减的旧负反馈重新放大。
- 实际进入请求的记忆使用有界 `MemoryEvidenceEnvelope`，至少包含 Atom 引用、branch/scope、tier、来源/权威、confidence、importance、verified usefulness 摘要、task relevance、routing relevance、relationship relevance、验证或更新时间、新鲜度、命中理由、状态、冲突和截断信息；关系发现还要使用独立 `relation` 检索路径，并记录种子 Atom、关系 id、类型、方向、confidence、relevance 和 route strength。模型据此判断“为什么介入、过去是否真正有用”和证据权重，运行时仍保留唯一元数据修改权。
- `MemoryEvidenceEnvelope` 还必须携带 statement kind、epistemic status、authority scope、asserted by、`sourceRefs` 和 `evidenceRefs`。`sourceRefs` 只指向对话原始来源，工具、VERIFY 和外部佐证进入 `evidenceRefs`。建议、假设和未验证陈述即使相关性很高，也不能以“事实”标签注入；用户目标/偏好则在其权威范围内直接约束计划。
- User Memory、Agent Self Memory、Task/Project/Session Memory 和 Knowledge Memory 使用同一套索引与写入协议。任何 domain 都按 D0 可发现索引、D1 摘要元数据、D2 原子正文、D3 来源与审计渐进展开；D0-D3 不等同于 T0-T3。
- Memory Repository 还要登记用户、项目、文件、会话、任务、Skill、工具、规则和概念等实体，以及属于、依赖、引用、冲突、替代、派生、相似、影响和证据支持等有向关系。D0/D1 只给出边界和最强相关关系，D2 按任务展开局部关系邻域，D3 才读取完整证据与历史；关系可以在严格边界内发现候选，但不能直接触发事实确认、合并或无条件注入。
- LS 自身记忆中的学习经验、工具技巧和失败教训可以持续更新，但不能覆盖高权威身份、安全规则、架构原则或用户当前要求；用户推断与用户明确陈述也必须分开存放和披露。
- V3 backend 激活后，Runner 在每轮结束时补齐该轮全部对话原始来源；压缩路径写入 Atom 前先持久化其 `sourceRefs`，来源捕获失败时延期投影写入。正式 V2 路径在迁移前继续以会话 JSONL 保存可见对话，不提前创建 V3 来源文件。影响 Atom 的用户纠正、工具/VERIFY 证据、项目/资源变化、能力变化、冲突处理和时间到期统一生成版本化 `MemoryUpdateEvent`，并先写入只追加的投影变更记录，再登记到可恢复 journal，随后幂等更新 Atom 与 catalog；mutation 提交后另写 append-only commit receipt。投影变更记录落盘后即使在 journal 登记前崩溃，也必须在重启时自动补投影；catalog 重建使用 receipt 区分历史已提交记录与真正待恢复记录，禁止倒放旧 mutation 覆盖较新 Atom。处理失败进入恢复状态，禁止只更新内存或静默覆盖对话来源。
- 时间变化通过 `effectiveAt`、`expiresAt`、`revalidateAt`、`lastUsefulAt` 和 due index 处理。运行中在安全边界近实时消费，到应用关闭期间跨过的时间点在下次启动补偿；不允许为“实时”无界轮询全部记忆或监控未授权文件。
- 不失忆依赖持久权威副本、稳定索引、事件 journal、版本和恢复验证，不依赖全量 Prompt。当前请求不相关的记忆可以不注入，但必须仍可沿索引重新发现；用户批准的删除和到期清理仍按 tombstone、引用检查与审计执行。
- 超出预算的结果返回摘要或可继续展开的索引，不直接塞入一段被截断的原始正文。
- 运行结束时的记忆沉淀已随极简方案删除：EVOLVE 编排、自动 Skill 创建和 legacy-per-run 的 CAPTURE 总结都不再存在。持久记忆**只有一个写入方**：会话压缩路径（`runner-finalize` → `compactSessionAfterRun` → 记忆服务写入，经认识状态解析）。面向模型的记忆工具只有只读的 `memory_tree`（`root_index`/`branch_index`/`expand`/`deep_search`/`release` 五个动作），模型**没有**可调用的写入工具；这是 2026-09-21 记录在案的缺口，不是已解决的能力。任何路径都不能直接写入旧式扁平文件。
- 所有写入都包含 parent、scope、tier、检索键、来源 run、`sourceRefs`、`evidenceRefs`、置信度、重要性和理由。缺少父节点时进入恢复队列；重复或相似内容只能在 statement、epistemic、authority 和作用域兼容时强化或合并。合并保留来源、证据、来源 Atom tombstone 与历史；重复出现本身不能覆盖正文或提高 confidence。合法父级变化保持稳定 Atom id，并执行 revision、同作用域和循环校验。
- 用户侧记忆页只读取应用数据根中的记忆文件目录，当前仅允许修改 `SOUL.md`；不得在普通 GUI 中暴露 Atom、关系、向量和压缩投影。Runtime 内部治理、检索和审计继续使用同一套 Memory Repository，不能因前端简化而建立展示副本。
- LLM 每轮只预载记忆树简介与受限根索引，具体 Atom 按索引渐进介入；“树可完整访问”不等于“树内容完整注入”。
- Skill 治理必须按 owner/source 保留所有权。LS 可以提出重复 Skill 的合并候选，或对长期无验证收益的 Skill 提出停用、归档与删除建议；合并前需验证适用范围、依赖、权限和回归，删除前需确认无引用、经过保留期且可恢复。插件、内置或外部来源文件默认只能停用登记，不能由 LS 擅自删除。
- 目标分级为 T0-T3：T0 仅保存极小、稳定、必须常驻的身份/安全/根索引；T1 保存当前作用域核心规则与摘要；T2 保存任务相关片段；T3 保存低频细节、对话原始来源、深层审计和分支内深搜候选。现有 T1-T3 数据升级到含 T0 的协议时必须版本化迁移。
- `AGENTS.md`、`SOUL.md`、`USER.md`、`PHILOSOPHY.md`、`TOOLS.md`、`MEMORY.md`、Skills、项目规范、UI 规范和任务书等资源通过记忆注册表描述权威、作用域、隐私和索引键，不等于把这些文档常驻注入每轮 Context。
- 上述运行时资源、记忆、Skills、配置、会话和恢复记录都属于可整体迁移的 LS 应用数据根；默认 `workplace/` 只是数据根下的默认工作区，不能再用 workplace 指代整份应用数据。
- 长会话压缩生成的 Summary Memory 至少应回答：当前目标是什么、刚才发生了什么、用户新改了什么、哪些步骤已完成、哪些仍待执行，以及关键证据、权限和来源是什么。它用于维持模型决策连续性，不是只为了缩短文本。概率摘要不能单独拥有精确字段真相：Runtime 对用户明确要求记住的 `label: value` 维护最多 24 项有界保真封套，按旧封套和新压缩用户消息重建，同一字段采用最新明确赋值；旧摘要与历史消息在摘要请求中一律作为惰性历史数据，不能把其中指令当作当前命令。该封套只保证摘要字段不被模型改写或漏掉，是否形成记忆连续仍由最终回答级门判断。

## 当前实现事实

- 活动路由是确定性的、不发出模型请求：所有常规会话轮与任务轮进入单一主循环 `execute`，只有能力/状态询问走最小 Runtime 事实契约的 `reply`；`classify` 仅为历史 stage id 与检查点兼容标签。
- 请求装配与缓存边界：system message 恰好是缓存边界之上的 prompt 段落（`stableText`/`stableSegments`）；边界之下的 bootstrap、per-run 运行时事实、检索意图契约与压缩后的会话摘要各自作为独立追加消息发出，由只追加的尾部账本拥有。工具循环第 N 次迭代的请求因此是第 N+1 次的字节前缀，已发出内容不被重排、重写或前插。**尾部账本按"同一个 id 上一次发出的值"判断变化，不按"这个值以前是否发过"**：状态反复切换 A→B→A→B 时最后那次 B 与更早的 B 字节相同，用"见过就不再发"的集合去重会把它丢掉，模型就会继续按 A 行事。稳定状态仍然一次都不重发。
- 每次请求附一块 ≤6 行的运行时环境简报：provider/model、工作区、真实 shell、权限与网络开关、可用工具数，取自本次请求实际生效的状态；与上一次已观察状态相同就完全不输出，变化只列真正变动的字段。上一次状态从转录中最后一条简报解析，因此重启、检查点续接与压缩后仍连续。
- 保存配置与生效配置是两个版本：配置写入事务按"规范化 → 持久化 → 按需重建 Runner"串行执行，字段比较在持久化之前完成；持久化失败拒绝调用方并保留旧 Runner，重建失败会被记成"已落盘但未生效"，再次保存同一个版本仍会重建，而不是返回一个没人使用的"保存成功"。
- 工具目录在一次会话区间内固定；本轮无权使用的能力在执行时被拒绝，而不是从 schema 中隐藏。
- 主循环的 Context 淘汰作用域是 `appended-only`：只能丢弃本次请求新追加的内容，不能删除本次 run 已经发出的任何东西；仅已发出的前缀就超出模型窗口时请求显式失败，不被静默重新编号。
- 每次模型请求都解析独立、版本化的 `LlmCallContract`，明确 purpose、stage、Context 来源、允许决策、输出结构、工具、记忆意图和预算；缺少必需 Context、stage 不匹配、工具越权或预算无效时在发送前默认拒绝，`FINALIZE` 禁止额外模型调用。
- `VERIFY` 只按 Runtime 可证证据检查：窄结构形态记 `pass`，其余已完成的 run 记 `unverified`；没有验证模型请求。记录到的失败、缺失步骤、截断证据、未结算副作用或缺少模型回复一律不能变成 `pass`。权限结果（未决定是否授权）与 Runtime 自己执行前发出的拒绝（调用根本没跑）分开处理：前者升级给用户，后者留在记录里让 run 停在 `unverified`。
- `RECOVER` 是 Runtime 自有路由，不请求恢复模型：可重试失败回到产生失败的阶段，权限拒绝升级到 `ASK_USER`，副作用未结算或运行被中止则显式停止并只呈现 Runtime 状态。不可能成功的重试不再空转：预算耗尽直接升级，证据结构性缺口只给一次回到主循环的机会。单轮工具循环的迭代上限为 30 次，耗尽时写入转录的收尾指令明确说明"再调用一次工具会让整个 run 失败"。
- 澄清只发一次模型自撰写的提问：模型通过主循环的 `request_user_input` 提问，文案按原文发布并绑定产生它的 request id，Runtime 不另发第二次措辞请求；Runtime 升级陈述只发一次；模型返回空文本时显式失败，不用模板冒充 Agent 回复。
- 回复发布由 `ReplyProvenance` 绑定真实 Provider 请求；同一 settlement 身份只能发布一次，跨回合出现完全相同的措辞按原样发布，**不存在重新生成文案的 Runtime 路径**。
- 记忆：面向模型的工具只有只读的 `memory_tree`（`root_index`、`branch_index`、`expand`、`deep_search`、`release`）；持久记忆的唯一写入方是会话压缩路径，模型没有可调用的写入工具。Runner 只持有一个索引优先记忆运行时实例，供提示词装配、`memory_tree` 导航、缓存失效、执行日志和设置概览共用。
- 会话压缩在 run 结束后按压力触发，默认阈值 400 条消息、保留最近 200 条原文、后台压缩关闭；摘要的安装与被覆盖区间是同一次原子提交，提交前校验前驱摘要与来源哈希前置条件；失败保留上一份仍有效的摘要，失败与重试都计入该操作的用量统计。
- 附件默认先注册清单；非图片正文通过当前 run 专属的 `inspect_attachment` 只读工具按需解析，未调用时不读取文件正文，图片仍按受限大小读取为多模态输入。
- Token 账本按模型与请求形态精确性分层：DeepSeek V4 使用固定 revision tokenizer、Provider 校准后的最终 framing 与计数器 id；Flash 的普通请求、工具 schema、`tool_calls -> tool` 续轮、只保留历史工具消息和多工具乱序结果已完成零差值校准。Pro 工具协议在独立校准完成前默认拒绝；OpenAI/GLM 等未验证模型保持 `unavailable`，不用字符换算冒充真实 token。
- Runtime 已支持 `AbortSignal`、统一工具调用超时与有界清理窗口、同一响应内多工具的有界分波执行、shadow Git 数据/工作区检查点、退出冻结、历史执行记录重放、有界 `RuntimeEventQueue`、确定性 `TaskBookPatch`、检查点快照、Runner 显式续跑、应用启动恢复控制面、活动任务 SSE、后台托盘和三档关闭策略。Local App API SSE 提供 15 秒注释心跳、512 KiB 慢观察者缓冲上限和幂等释放；普通 Agent/Checkpoint 观察断开不会取消 Main 任务，终端主动命令在断连时取消。
- 内置写入、编辑与命令工具已接入宿主级核心源码只读根；读、grep、glob 等诊断仍可用。第三方本地插件代码仍属于显式完全信任边界，不能把插件信任误写成系统级代码沙箱。
- 缓存红线的现行读数：**按会话累计口径在真实长任务验收节点判定，当前 `met`**（`pnpm run check:cache-acceptance`：长任务 99.13% / 99.21%，重启后 98.99%，空闲 45 分钟后 99.05%）；3 回合短负载有 87–89% 的结构上限，**不以红线判定**，只作功能回归。历史读数（共享会话对话 78.098%/78.182%、连续工具工作 83.690%/84.523%、开启压缩 62.827%/63.228%）录制于已被删除的 shadow/next 双驱动与旧判定口径，**不代表当前实现**。离线结构基线为可复用前缀 3574 字符、工具循环复用比 1.000、聊天与工具共享前缀 3557、稳定头 3444。规程、禁止做法与逐项归因见[缓存 95% 冻结负载验收规程](../reference/cache-95-acceptance.md)。

## 仍未实现

- 模型没有可调用的持久记忆写入工具：该缺口按 2026-09-21 的裁定**维持现状并如实记录**，不以"明确写入已可用"表述。
- MCP 客户端尚未实现；未来从经过验证的稳定 adapter 开始，复用内置工具的权限、超时、清洗和执行记录契约，不先建立空 workspace 包。
- Skill 治理队列仍待实现；Skill 相似度不自动触发合并或删除。
- 工作区、渠道、记忆树与重启恢复的真实用户场景验收仍在继续；真实 Provider 的缓存 95% 目标尚未覆盖全部负载场景。
- 受限模式（全部工具逐次批准）仍只有自动化矩阵覆盖，尚未在真实窗口里走过批准对话框；研究模式已有真实窗口的批准与拒绝证据。
- 3 个并发真实 run 强杀重启后恢复检查点时仍会报 `checkpoint has an active resume lease`（租约未释放/竞态），属运行状态一致性方向。

# LittleSheep 核心 Agent 流程规范

最后更新：2026-07-16 10:42:44

本文是 [LittleSheep 架构原则](architecture-principles.md) 在 Core Flow、TaskBook、验证、恢复和记忆运行时上的专项约束。LLM 与 Agent、Mode 与权限、Context 与 Memory、Harness 与 Tool Execution 的顶层分工以架构原则为准；本文不重复维护另一套总架构。

## 核心原则

状态机存在的目的，是提升 Agent 的判断和执行能力，而不是为了维护状态机本身。如果某个状态、提示词契约或数据结构阻碍了更好的判断或执行，就应当修改或重构它。

## 目标流程

复杂任务的目标循环如下，简单任务可以跳过不需要的阶段：

```text
用户输入
  -> 校准需求并识别缺失信息
  -> 获取可靠来源并按需装配 Context
  -> 创建或修订 TaskBook
  -> 按 TaskBook 调度串行或可安全并行的步骤
  -> 在安全决策边界消费用户追加消息或 LS 事件
  -> 局部修订未完成步骤
  -> 按目标和验收标准验证
     -> 通过：FINALIZE
     -> 可恢复失败：RECOVER 后继续
     -> 缺少关键决策：ASK_USER
```

这是一条可重复进入的受控循环，不是要求每个请求都完整走一遍。闲聊和简单回答走轻量路径；复杂任务可以重复“执行、接收新信息、修订、验证”，但所有循环都必须有界。

## 用户体验契约

- 日常工作应当自动、少打断。用户不需要理解状态机、记忆索引、恢复循环或内部规划契约，也能得到完整结果。
- LS 的目标是解放用户生产力：用户专注于想法和目标，LS 负责拆解、执行、验证、整理和沉淀，减少用户在重复操作和过程搬运上的负担。
- 内部细节采用渐进披露：默认只显示有用的最小状态，但任务书、执行证据、记忆来源、阈值和高级策略必须可以按需查看。
- 执行中默认显示当前步骤、等待状态和关键结果；命令参数、原始输出和完整过程默认折叠。任务结束后过程自动收拢，只保留结果摘要，用户可以重新展开。
- 最终回复按“结论/状态 → 关键结果与产物 → 必要证据和下一步 → 可选详细过程”的层级组织。简单任务不生成重量级报告；失败、风险、权限拒绝、部分完成和待用户决策必须在默认层明确表达。
- 渐进披露不等于披露隐含思维链。Agent 应提供可操作的步骤摘要、事实依据、验证结果和决策边界，不输出私密逐字推理。
- 用户始终拥有对真实运行时系统的高度控制权。设置页和管理页必须修改 Agent 实际使用的同一套策略、索引、权限和记录；只改变外观或只在 UI 内生效的开关不满足要求。
- 改变持久状态的自动行为必须记录理由、来源、作用域和结果。可恢复行为必须通过对应管理界面提供恢复或撤销路径。
- 必须提供可靠的安全默认值。高级自定义是可选项，不能变成正常使用前必须完成的配置工作。
- 少打断不等于绕过授权。破坏性、不可逆、高风险或超出范围的操作仍必须获得明确批准。

## 需求校准

在规划工具工作之前，`DECIDE` 必须校准用户的真实需求：

- 识别用户真正想解决的问题，而不只照搬字面措辞。
- 将任务复杂度分为 `trivial`、`simple`、`standard`、`complex`。
- 小请求不能套用重量级工作流。
- 定义具体目标和成功标准。
- 只有缺少关键信息、需要用户承担明显成本/风险，或存在必须由用户决定的重大分岔时才询问。非关键细节可以采用可逆的安全假设，并在结果中说明。
- 有价值时可以适度超出用户预期，但超出范围或成本不得高于用户请求的 3 倍。

## TaskBook 的规模

`DECIDE` 输出结构化 `TaskBook`。

- `trivial` / `simple`：一个简短步骤即可，任务书可以保持最小化。
- `standard`：包含成功标准和 1-3 个聚焦步骤。
- `complex`：包含阶段目标、验收标准和预期产物。
- `TaskBook` 是 `EXECUTE` 和 `VERIFY` 共同遵守的执行契约。

## 运行中输入与任务书修订

- 长任务运行期间，用户可以追加要求、纠正目标、暂停、恢复或请求中断。LS 只接收自身界面、已启用渠道和用户明确授权观察范围内的事件，不进行系统级全局监控。
- 运行时事件先进入有界队列，并在步骤结束、工具调用返回、权限等待、验证失败等安全决策边界处理。已经发出的外部副作用不能被新消息静默改写。
- 相关新信息触发需求重新校准和 `TaskBook` 差异更新。修订只影响尚未开始或确实需要重做的步骤；已完成步骤、证据、权限结果和已提交副作用必须保留。
- 无关事件不得抢占当前动作；重复事件应去重，过期事件应被丢弃或标记，队列必须有长度、保留时间和单次消费预算。
- 若新要求与已完成的不可逆动作冲突，必须明确告知当前事实并进入 `ASK_USER`，不能伪装成仍可无损回退。

## 执行

`EXECUTE` 应把任务书作为约束，而不是装饰性文本：

- 工作量必须与校准后的复杂度匹配。
- 只有在降低不确定性或完成目标确实需要时才调用工具。
- 除非能直接改善用户目标，否则不要额外扩大工作范围。
- 如果需要证据，先用工具验证，再声称完成。
- 并行是调度优化，不是新的任务类型。只有依赖独立、读写集合不冲突、权限语义明确且资源预算允许的步骤才可同时执行；同一文件、同一外部对象或需要顺序验证的副作用必须串行。
- 并发度、排队长度、单分支超时和总成本必须有上限。每个分支独立持有取消信号、工具记录和验收证据；失败或用户修订只影响相关分支，不得把无关已完成分支重新执行。
- 并行结果按 TaskBook 依赖和稳定顺序归并，不能因为运行时完成顺序不同而改变最终事实、权限结论或回复结构。
- 当前阶段 LS 可以只读检查自身核心源码，但不得通过内置 `write`、`edit` 或 `exec` 修改它。该边界由宿主解析真实源码根并在工具执行前硬拒绝，优先级高于完全访问模式和单次批准；后续受控自我修改必须另立任务书、隔离环境、验证与回滚契约。

## 信息来源与可靠性

- Agent 的判断必须区分用户明确陈述、受信系统状态、工具实测结果、记忆/RAG 召回、模型推断和未知信息。
- 每条输入陈述还必须区分 instruction/goal、preference/value、reported observation、factual claim、suggestion/hypothesis 和 decision/approval。来源是谁与陈述是否为真是两个维度，不能因为来自用户、官方资料或模型就跳过验证状态。
- 用户对自身目标、偏好、授权、主观体验和最终取舍具有最高权威；对代码、系统状态、客观世界和因果关系的陈述仍是可验证 claim。用户选择一个方案会约束执行，但不会自动证明方案理由正确。
- 某条用户建议有误时，只修正该 claim 或方案，不生成“用户不懂该领域”的长期画像。若错误前提会影响结果、安全、成本或不可逆操作，先验证并明确说明；不影响目标时保留用户意图并使用更可靠的实现。
- 工具结果和记忆片段进入 Context 前必须保留来源、时间、作用域和截断状态。被截断、过期或未经验证的信息不能当作完整事实。
- 附件默认先注册清单、类型、大小、来源和受管位置；正文、图像或结构化内容只在当前步骤确有需要时读取，不能因附件存在就全量注入。
- 当多个来源冲突时，优先使用当前用户明确要求和更新、更直接的可验证证据；仍无法可靠判断时进入澄清或验证，而不是选择最方便的答案。
- Agent 必须区分实体边界与实体关系。名称相似、共同出现、目录相邻或向量接近只表示候选关联，不能自动证明同一实体、所有权或因果关系。跨用户、项目、会话、插件所有者和权限作用域的关系必须保留方向、证据、置信度、有效时间与冲突状态，并按 D0-D3 渐进展开。
- 每个 run 维护版本化 `KnownState`，统一登记已验证事实、用户陈述、建议、决策、记忆证据、工具证据、假设、未知项和冲突项，并保留 statement kind、epistemic status、authority scope、asserted by、evidence refs、来源、时间、作用域、置信度与截断状态。
- DECIDE、EXECUTE、VERIFY 和 FINALIZE 必须从同一条 `KnownState` 版本链读取事实，并记录各自使用的版本。新工具结果、用户修订或验证结论只能通过事件生成下一版本；不得依赖聊天文本之外的隐含状态，也不得把模型跨调用的主观记忆当作事实。
- 每个阶段只把当前决策所需的 active evidence set 投影到 `ContextSnapshot`。无关、重复、被替代、过期或低收益信息可以从后续请求中退出，但排除理由和来源引用仍保留在 `KnownState`；需要时可重新激活，不能把“本轮不注入”误当作删除记忆。
- 关键未知或冲突会实质影响范围、权限、不可逆操作或验收时，必须先沿索引补取记忆、调用工具验证或进入 `ASK_USER`。可以继续执行的假设必须显式登记，最终交付时说明尚未验证的边界。

## 时间、进度与耗时感知

- 每次模型请求必须获得由运行时即时生成的当前本地年月日时分秒、IANA 时区和 UTC offset。秒级时钟属于 volatile Context，必须位于 Prompt 缓存边界之后，不能只在 stage 开始时生成一次后供整个工具循环复用。
- 当前 run 必须同时投影真实起点、已耗时、TaskBook 状态、已完成步骤数、总步骤数、活动步骤和已经结束的工具状态/耗时。数据来自代码状态与工具结果，不由模型自行估算。
- 工具返回给下一次模型决策时必须携带结构化 `status` 和 `durationMs`；超时、异常和正常完成均记录实际墙钟耗时。工具正文仍按既有清洗与截断规则处理。
- 执行日志域只按会话持久化上一轮 run 的有界原子 sidecar：总状态、总耗时、步骤完成数、工具成功/失败计数、累计工具耗时和最多固定数量的最近工具计时。完整输入输出只保留在单 run 执行日志，sidecar 以哈希会话键定位并按会话串行原子替换，避免改写整段会话或让 Context 随使用次数无限膨胀。
- 默认输出保持安静。普通报时只显示时与分；用户明确追问后可给完整日期、秒、时区、run/步骤/工具耗时。只有状态解释、失败、超时、成本、风险或验收需要时，LS 才主动显示相关进度和耗时。

## 验证

`VERIFY` 根据任务书判断结果：

- 用户原始请求。
- 校准后的目标。
- 总体成功标准。
- 每个步骤的验收标准。
- 工具结果。
- VERIFY 开始时使用的 `KnownState` 版本、其中的关键未知与冲突。
- 被采用的建议是否经过验证，最终结论是否把 reported/unverified claim 错写成 verified fact。
- 草拟回复。

没有错误不等于任务完成。一次 run 必须拥有证明目标已达成的正向证据。

对高价值或关键任务，一次失败不能直接被包装成最终结果。只要仍有新的诊断证据、可逆修正路径且未触发次数、时间、成本或安全上限，就应进入局部 `RECOVER`；只有恢复耗尽、需要重大用户决策或无法安全继续时，才进入 `ASK_USER` 或有边界地结束。

## 中断、恢复与循环上限

- 用户中断、应用关闭、进程异常和可恢复故障必须拥有不同的终止原因，不能都压缩成普通失败。
- 切换或隐藏对话只改变界面焦点，不应取消活动 run；关闭最后窗口是否转入后台由用户策略决定；暂停保留现场但不继续调度；中断停止当前 run；放弃任务结束恢复资格；彻底退出负责停止进程并处理仍活动的任务。
- 当前步骤、TaskBook 版本、已完成证据、待处理事件、权限结果、外部副作用 idempotency key 和必要的 Context 来源应写入版本化检查点。
- 恢复只能从明确的幂等边界继续。已成功写文件、发送消息、创建资源或执行其他副作用后，恢复时必须先检查结果，不能盲目重放。
- `VERIFY -> RECOVER -> EXECUTE`、局部重规划和工具重试都必须同时受尝试次数、总时长、成本/上下文预算和无进展检测约束。
- 连续两轮没有新增证据、没有缩小失败范围或重复同一错误时，应计入无进展；达到上限后进入 `ASK_USER` 或有边界地结束，禁止无限循环。
- 应用重启后的活动 run 恢复必须由持久化检查点驱动，不能依靠 renderer 内存或聊天文本猜测执行位置。
- 恢复能力不以固定重启次数为上限。只要检查点版本仍受支持、数据完整且未被用户放弃，重复重启后仍应从幂等边界继续；检查点历史本身必须按容量、版本和保留期有界管理。

## 记忆运行时

- 系统提示词只携带受限长度的根索引；记忆规模增长不能让基础提示词按比例膨胀。
- 记忆读取严格索引优先：从预加载根索引进入一个分支索引，再展开一个相关节点或查询。运行时在触碰记忆来源前拒绝跳过层级。
- 深搜绝不跨树。必须在同一次 run 中明确指定一个已经成功读取分支索引并完成展开的分支。语义/向量召回只能作为该分支内的最后兜底候选来源。
- 兼容工具 `memory_search` 只负责导航：返回根索引或选定分支索引，不直接注入记忆正文。
- 每次记忆介入都必须有预算、去重、来源追踪、安全封套，并记录到当前 run 账本。
- 记忆持久层分为原始数据记录与 atom projections：原始数据记录只追加且不修改，但其内容仍按 statement kind 和 epistemic status 区分事实主张、用户陈述、建议、假设、决定与证据；atom 用于层级、相关性、检索和治理，可移动、合并、失效或恢复。Recovery journal 是有界恢复队列，不是原始数据源。
- 首次业务请求先检查 D1 索引元数据，只选择一个极小且受预算约束的 D2 atom working set；不得默认跨树向量召回。执行中模型可通过受控工具请求继续展开，也可 `release` 当前无用 atom；release 只释放本轮 Context 与 dedup 预算，不能删除或失效持久记忆。
- 在已导航分支和当前作用域内，候选按 scope 匹配、来源权威、任务相关性、confidence、importance、新鲜度、已验证 usefulness 以及冲突/失效/过期惩罚稳定排序；高优先级记忆先介入，但不能挤掉安全规则、当前用户输入和必要工具证据。可选记忆长期没有验证收益时降低注入权重，但不自动降低 confidence；T0、安全规则和当前用户约束不参与普通使用衰减。
- 读取次数本身不提高事实可信度。只有用户确认，或记忆参与的任务获得工具证据与 VERIFY 成功结果时，才记录正向 usefulness 反馈；无帮助、冲突、过期或导致错误的结果记录负反馈。任何反馈都必须可审计，并防止重复出现的错误记忆形成自增强循环。
- 实际进入请求的记忆使用有界 `MemoryEvidenceEnvelope`，至少包含 atom 引用、branch/scope、tier、来源/权威、confidence、importance、验证或更新时间、新鲜度、命中理由、状态、冲突和截断信息；模型据此判断证据权重，运行时仍保留唯一元数据修改权。
- `MemoryEvidenceEnvelope` 还必须携带 statement kind、epistemic status、authority scope、asserted by 和 evidence refs。建议、假设和未验证陈述即使相关性很高，也不能以“事实”标签注入；用户目标/偏好则在其权威范围内直接约束计划。
- User Memory、Agent Self Memory、Task/Project/Session Memory 和 Knowledge Memory 使用同一套索引与写入协议。任何 domain 都按 D0 可发现索引、D1 摘要元数据、D2 原子正文、D3 来源与审计渐进展开；D0-D3 不等同于 T0-T3。
- Memory Repository 还要登记用户、项目、文件、会话、任务、Skill、工具、规则和概念等实体，以及属于、依赖、引用、冲突、替代、派生、相似、影响等有向关系。D0/D1 只给出边界和最强相关关系，D2 按任务展开局部关系邻域，D3 才读取完整证据与历史；关系分数只服务导航，不直接触发事实确认或合并。
- LS 自身记忆中的学习经验、工具技巧和失败教训可以持续更新，但不能覆盖高权威身份、安全规则、架构原则或用户当前要求；用户推断与用户明确陈述也必须分开存放和披露。
- 影响记忆的用户纠正、工具/VERIFY 证据、项目/资源变化、能力变化、冲突处理和时间到期统一生成版本化 `MemoryUpdateEvent`。事件先写入只追加的原始数据记录，再登记到可恢复 journal，随后幂等更新 atom 与 catalog；mutation 提交后另写 append-only commit receipt，不修改原始记录。记录落盘后即使在 journal 登记前崩溃，也必须在重启时自动补投影；catalog 重建使用 receipt 区分历史已提交记录与真正待恢复记录，禁止倒放旧 mutation 覆盖较新 atom。处理失败进入恢复状态，禁止只更新内存或静默覆盖原始数据。
- 时间变化通过 `effectiveAt`、`expiresAt`、`revalidateAt`、`lastUsefulAt` 和 due index 处理。运行中在安全边界近实时消费，到应用关闭期间跨过的时间点在下次启动补偿；不允许为“实时”无界轮询全部记忆或监控未授权文件。
- 不失忆依赖持久权威副本、稳定索引、事件 journal、版本和恢复验证，不依赖全量 Prompt。当前请求不相关的记忆可以不注入，但必须仍可沿索引重新发现；用户批准的删除和到期清理仍按 tombstone、引用检查与审计执行。
- 超出预算的结果返回摘要或可继续展开的索引，不直接塞入一段被截断的原始正文。
- `EVOLVE` 提出长期、项目或经验记忆的写入意图；`CAPTURE` 记录详细 daily 流水。两个阶段都不能直接写入旧式扁平文件。
- 所有写入都包含 parent、scope、tier、检索键、来源 run、置信度、重要性和理由。缺少父节点时进入恢复队列；重复或相似内容应强化或合并已有索引节点。
- 管理页和设置页必须读取并修改同一套运行时记忆树、仓库和策略配置。
- Skill 治理必须按 owner/source 保留所有权。LS 可以提出重复 Skill 的合并候选，或对长期无验证收益的 Skill 提出停用、归档与删除建议；合并前需验证适用范围、依赖、权限和回归，删除前需确认无引用、经过保留期且可恢复。插件、内置或外部来源文件默认只能停用登记，不能由 LS 擅自删除。
- 目标分级为 T0-T3：T0 仅保存极小、稳定、必须常驻的身份/安全/根索引；T1 保存当前作用域核心规则与摘要；T2 保存任务相关片段；T3 保存低频细节、原始记录和深搜候选。现有 T1-T3 数据升级到含 T0 的协议时必须版本化迁移。
- `AGENTS.md`、`SOUL.md`、`USER.md`、`PHILOSOPHY.md`、`TOOLS.md`、`MEMORY.md`、Skills、项目规范、UI 规范和任务书等资源通过记忆注册表描述权威、作用域、隐私和索引键，不等于把这些文档常驻注入每轮 Context。
- 上述运行时资源、记忆、Skills、配置、会话和恢复记录都属于可整体迁移的 LS 应用数据根；默认 `workplace/` 只是数据根下的默认工作区，不能再用 workplace 指代整份应用数据。
- 长会话压缩生成的 Summary Memory 至少应回答：当前目标是什么、刚才发生了什么、用户新改了什么、哪些步骤已完成、哪些仍待执行，以及关键证据、权限和来源是什么。它用于维持模型决策连续性，不是只为了缩短文本。

## 当前实现切片

已实现：

- `NeedAssessment` 和 `TaskBook` 核心类型。
- `DECIDE` 输出需求校准和结构化任务书。
- 继续兼容旧的 `{ "plan": [...] }` 输出格式。
- 存在任务书时，`EXECUTE` 按 `TaskBook.steps` 逐步执行。
- `EXECUTE` 记录包含步骤状态、输出、工具调用和失败信息的 `TaskExecutionResult`。
- `EXECUTE` 发出 `step_start`、`tool_start`、`tool_end`、`step_done`、`step_failed`、`final_delta` 流式事件。
- `VERIFY` 在存在任务书时根据任务书和步骤执行结果进行检查。
- 执行日志持久化任务执行结果，供重放和后续记忆抽取使用。
- `RECOVER` 安装修订版旧计划时会清理过期任务书。
- 缺少信息时使用一等的 `ClarificationRequest` 和 `ClarificationResponse`，不再把正常提问伪装成 `lastError`。
- 澄清请求及下一轮用户回答会持久化到会话消息、run 结果和执行日志。
- 真正缺少关键决策或无法可靠判断目标的 `unclear` 输入进入 `ASK_USER`；普通歧义、轻微模糊和上下文续答留在 chat 路径，避免过度追问。
- `VERIFY` 识别失败或未完成的步骤 id，并生成有边界的 `PartialReplanRequest`，不替换整本任务书。
- `DECIDE` 只能修改目标步骤；已完成步骤、证据、任务目标、成功标准和范围限制由代码保护。
- `EXECUTE` 从失败或未完成步骤继续执行，并保留已完成结果。
- 自动重规划耗尽后升级到 `ASK_USER`，不会用“强制通过”掩盖未完成任务。
- Runner 只持有一个索引优先记忆运行时实例，供提示词装配、`memory_tree`、兼容 `memory_search`、EVOLVE/CAPTURE 写入、缓存失效、执行日志和设置概览共同使用。
- 固定 daily prelude 和 `MEMORY.md` 启动注入已关闭；旧扁平文件、项目/Git 状态、经验数据和向量仍作为按需兼容来源保留。
- 运行时强制 `root index -> branch index -> expansion -> branch-scoped deep search`；前置条件失败时记录为零注入 token，普通展开不能调用向量来源。
- 结构化记忆写入具备阈值、写侧安全检查、父级索引原子更新、审计记录、恢复排队、去重和合并。
- TaskBook、步骤、工具调用、验证结果和最终回复会进入执行日志，历史 UI 与实时过程使用同一套无气泡展示结构。
- `@littlesheep/context` 已接管显式候选、稳定排序、窗口预算、可选项淘汰、压缩建议和脱敏 `ContextSnapshot`；System Prompt 内部已经按基础策略、记忆根索引、bootstrap 文件、行为 profile、reasoning、Workflow/TaskBook 和输出约束拆成可追溯 segment。
- 每次模型请求都解析独立、版本化的 `LlmCallContract`，明确 purpose、stage、Context 来源、允许决策、输出结构、工具、记忆意图和预算；缺少必需 Context、stage 不匹配、工具越权或预算无效时在发送前失败关闭，`FINALIZE` 禁止额外模型调用。
- EVOLVE/CAPTURE 只接收模型的结构化记忆建议；运行时依据真实步骤、工具和 VERIFY 证据决定是否提交，`invalidate` 与 `conflict` 只延期审计而不直接修改记忆。`PHILOSOPHY.md` 已作为显式理念资源注册，只沿索引按任务相关性和预算展开，不进入常驻 Prompt bootstrap。
- 本地精确 ledger 与 Provider usage 已使用不同结构保存，Provider usage 会绑定到产生它的准确 Context 快照；UI 能区分“供应商实测”“本地精确装配”和“tokenizer 不可用”，不会用字符换算冒充真实 token。
- 会话压缩已实现为非破坏式、版本化 Summary Memory：原始 JSONL 消息保留，旧消息摘要在下一轮作为独立 `summary_memory` 来源介入，并可按消息阈值或精确 Context 占用阈值触发。
- CLASSIFY、DECIDE 和 REPLY 只接收附件清单；非图片正文通过当前 run 专属的 `inspect_attachment` 只读工具按需解析，未调用时不会读取文件正文，工具结果再进入 Context。图片仍按受限大小读取为多模态输入。
- 当前记忆层级已升级为 T0-T3，并通过版本化迁移保留旧 T1-T3 数值与数据；T0 只承载固定预算的核心索引和安全信息。
- 当前已支持 `AbortSignal`、步骤级局部恢复和历史执行记录重放；尚未实现运行中用户事件队列、安全重入协议、活动 run 检查点及应用重启续跑。
- 内置写入、编辑与命令工具已接入宿主级核心源码只读根；读、grep、glob 等诊断仍可用。第三方本地插件代码仍属于显式完全信任边界，不能把插件信任误写成系统级代码沙箱。

# LittleSheep 架构原则

状态：规范性文档
最后更新：2026-07-17 13:24:05

本文定义 LittleSheep（LS）长期开发必须遵守的架构原则。它回答“系统各部分应当如何分工”，不记录某一阶段的完成进度，也不直接作为发送给模型的 System Prompt。

当前实现与目标架构之间的差距，以 [架构决策报告](../decision/architecture-decision-report.md) 和 [项目状态](../decision/project-status.md) 为准。若文档与源码行为不一致，先把差异记录为待处理问题，不得仅修改文档来伪装实现完成。

文档发生冲突时，不按文件日期简单覆盖：长期目标与硬约束以本文为准；当前实现事实以源码、测试和 [项目状态](../decision/project-status.md) 为准；演进建议以 [架构决策报告](../decision/architecture-decision-report.md) 为准；专项规范只细化其责任域，不能覆盖上层边界。任务书保存阶段设计和验收记录，不维护全项目最新测试数字。

## 1. 产品目标

LS 的目标不是包装一个聊天模型，而是构建一个本地部署、长期不失忆、高效完成任务并能持续进步的 Agent Runtime 与平台。对话可以是主要交互形式，但不能成为产品能力边界；系统最终按是否帮助用户解决问题来评价，而不是按界面是否像聊天、内部术语是否完美或流程形式是否齐全来评价。

> **产品使命：解放用户生产力，让用户着重于想法的产生、目标设定和关键判断，LS 负责让用户的想法可靠落地。**

LS 的核心使命是**解放用户生产力**：用户把主要精力放在想法的产生、目标设定和关键判断上，LS 负责把想法拆解、落实、验证并沉淀为可复用的结果。LS 应主动减少用户在查找、重复操作、过程搬运、状态维护和结果整理上的负担，让用户的想法更快、更可靠地落地；但不能替用户隐瞒风险、越权或代替关键决策。

这条使命具体约束产品取舍：凡是能由 LS 稳定完成的检索、规划、执行、验证、整理和记忆维护，应尽量由系统承担；凡是涉及目标取舍、风险接受、权限授予、价值判断或最终方向的事项，应保留给用户。自动化的目的不是减少用户的创造性参与，而是把用户从低价值的过程性劳动中解放出来。

所有状态机、TaskBook、原始数据、atom、索引、向量目录、上下文预算、工具记录和 UI 控制面都只是服务机制，不是独立产品目标。它们必须能回到两个核心评价轴：一是让需要保留的信息持久、可发现、可追溯和可恢复，从而实现“不失忆”；二是让当前任务只获得真正有用的信息、工具和执行步骤，从而“高效完成任务”。不能证明改善这两项的细分设计，应简化、合并或删除，而不是为了形式完整继续增加复杂度。

系统应同时满足：

- **默认无感**：用户不需要理解状态机、上下文预算、记忆索引或恢复循环，也能完成日常任务。
- **渐进式披露**：默认先呈现当前最有用的结果和最小必要状态；执行过程、证据、记忆来源、权限细节和高级控制按需展开。披露层级可以收起，但失败、风险、权限拒绝、不确定性和需要用户决定的事项不得被隐藏。
- **高度可控**：模型、行为模式、权限、工作区、记忆、工具和插件都可被用户查看和管理。
- **结果可靠**：任务完成必须有证据，失败必须有边界，不能用流畅回复掩盖未完成工作。
- **目标匹配**：实现复杂度、工具数量、执行范围和用户消费成本必须与真实问题相称，不能为了展示能力而把简单问题复杂化。
- **用户可感知的高效**：同样时间完成更多有价值的工作，或用更少时间、等待、打断和重复操作完成同一目标；不能把内部步骤变多误称为效率提升。
- **并行但有界**：仅在步骤彼此独立、资源不冲突且权限语义明确时并行执行；并发必须有硬上限、取消路径和确定性的证据归并，不能用无界并发换取表面速度。
- **能力可持续**：新增模式、工具、工作流或插件时，应通过稳定契约扩展，而不是不断修改核心流程。
- **数据归用户**：用户运行时数据与源码、构建产物和插件代码严格分离。

### 渐进式披露的统一含义

渐进式披露同时约束 Agent 的执行体验、模型输出和界面展示：

1. **执行层**：运行中优先显示当前步骤、正在等待的动作和下一项关键状态；命令输入、原始输出、完整 TaskBook 和诊断细节默认折叠，但可以展开。
2. **结果层**：最终回复先给结论、完成状态、关键产物和下一步；只有在有助于复核或继续操作时，才补充摘要证据、变更范围和细节。简单问题不应生成复杂报告。
3. **安全层**：渐进式披露只减少认知负担，不减少事实披露。失败步骤、部分完成、风险、权限结果、外部副作用和待决策项必须在默认可见层表达。
4. **能力层**：不输出隐含思维链；向用户披露可操作的步骤摘要、依据、证据和决策边界，而不是模型的私密逐字推理过程。
5. **记忆层**：用户记忆、LS 自身记忆、项目/会话记忆、经验和知识资源都先暴露可发现索引，再按需展开摘要、正文、来源和历史；既不向模型全量灌入，也不在 UI 中一次性铺开。

“用户无感”与“用户可控”因此并不矛盾：LS 默认替用户处理复杂性，同时保留从结果逐层进入过程、证据和管理控制面的路径。

## 2. 基本分工

核心分工是：

> LLM 负责推理和提出决策；Agent 负责控制、执行和兑现决策。

这不是把所有选择都写死在代码中，也不是允许模型直接控制系统。模型输出的是受约束的意图、计划、工具调用建议、判断或回复草稿；Agent 运行时决定这些输出是否有效、是否被授权、如何执行、如何记录以及下一步进入哪个状态。

| 职责 | LLM | Agent 运行时 |
| --- | --- | --- |
| 理解语义、识别意图 | 负责 | 提供输入、规则快速路径和结构校验 |
| 任务拆解与候选计划 | 负责提出 | 校准复杂度、限制范围、持久化 TaskBook |
| 状态转移 | 不负责 | Harness/Workflow 唯一负责 |
| 工具选择 | 可提出工具调用意图 | 校验名称和参数，执行路由与策略 |
| 权限与安全 | 可说明需求 | 唯一负责授权、范围限制和拒绝 |
| 工具执行、超时、重试 | 不负责 | 唯一负责 |
| 上下文选择和预算 | 可请求信息 | Context Engine 唯一负责装配和裁剪 |
| 长期状态和记忆 | 可提出读取/写入意图 | Memory Manager 唯一负责存取、索引和审计 |
| 验证 | 可参与语义判断 | Workflow 按验收标准决定是否通过 |
| 用户可见自然语言 | 负责结合 `SOUL.md`、当前证据和用户语言生成回复、澄清、任务说明、步骤摘要与验证说明 | Runtime 约束事实、状态、权限和验证边界并发布；FINALIZE 只持久化已有结果 |
| UI 结构与机器事实 | 不负责决定按钮、状态枚举、进度数值、路径、权限结果或执行事实 | 唯一负责稳定控件、布局、状态映射、数值和事实来源 |

可以用下面的工程模型理解 LS 的实际能力，但它不是严格的数学公式：

```text
实际任务表现 ≈ LLM 推理能力
             × Agent Runtime 兑现能力
             × Tool 可靠性
             × Context/Data 质量
```

模型决定可达到的推理上限；Agent 架构决定能力能否稳定兑现，以及真实使用体验的下限。架构不能凭空创造模型不具备的推理能力，但可以避免状态丢失、工具失控、上下文污染和验证缺失浪费已有能力。

**硬约束：任何模型输出都不能在未经代码校验、权限检查和执行记录的情况下直接产生外部副作用。**

### 每次 LLM 调用都是独立的认知任务

LLM 不保留跨调用的可靠状态。每次模型请求都必须绑定独立、版本化且可审计的 `LlmCallContract`，至少声明本次调用的 purpose、stage、唯一目标、允许的 Context 来源、允许作出的决策、输出结构、工具策略、记忆意图策略和预算。Context Engine 只能装配契约允许的候选；缺少必需来源、stage 不匹配、工具越权或输出预算无效时，运行时必须在发送前失败关闭。

不同阶段不能依赖“模型应该记得上一轮做了什么”维持连续性。TaskBook、Workflow State、工具证据、验证结果和必要记忆必须由运行时持久化，并在下一次调用时通过新契约显式投影。`FINALIZE` 只依据真实运行状态装配结果，不得为了润色而额外调用模型并改变已验证事实。

模型调用必须按价值分层。用户真正看到的聊天回复、执行结论、最终交付、澄清问题、任务说明和验证说明由 `REPLY`、`DECIDE`、执行步骤、`VERIFY`、`ASK_USER` 或 `execute_final_reply` 的既有调用生成，并注入运行时 `SOUL.md`/profile 形成一致人格与语气；同一份模型文案能被安全复用时不得为润色重复调用。按钮名称、折叠状态、进度数值、权限结论、路径、工具状态和其他机器事实由 Runtime 确定性提供，模型只能围绕这些事实组织表达，不能改写事实。隐藏的 CAPTURE 流水、检查点、调度、版本提交、清理和可由真实状态直接计算的观测默认使用确定性代码。减少调用的目标是消除重复、无判断价值和可确定计算的请求，不能把前台表达降级为固定模板。模型不可用时可以返回明确的降级结果，但不得伪装成正常人格化回复。

每个 run 还必须有独立模型调用计数、阶段输出上限和总硬上限。一次模型响应提出的多个独立工具调用可以由 Runtime 并行执行，不需要为每个工具机械增加一次模型请求；工具结果归并后，只有出现新决策需求时才再次调用模型。

模型对工具、状态转移、Context 扩展和记忆读写只有结构化建议权；Agent Runtime 保留唯一执行与提交权。尤其是记忆操作，模型提出 `read`、`write`、`merge`、`invalidate`、`conflict` 或 `none` 意图后，仍必须经过来源、事件、价值、安全、去重、冲突、权限和审计闸门，不能因为模型说“记住”就直接修改长期状态。

## 3. 逻辑分层

目标架构按责任分为以下层次：

```text
UI / CLI / Channel Adapters
            |
            v
Application Layer (Runner / use cases)
            |
            v
Control Layer (Harness / Workflow)
            |
            +----> Context Engine
            +----> Tool Execution Service
            +----> Memory Service
            +----> Session Service
            |
            v
Ports and Contracts (@littlesheep/types)
            |
            v
Infrastructure (LLM providers / file system / SQLite / PTY / plugins)
```

- Adapter 只负责协议转换和交互，不承载 Agent 业务决策。
- Runner 是一次 run 的应用服务和核心装配入口，不应无限吸收各子系统内部逻辑。
- Harness 控制状态转移和验收，不直接实现文件系统、数据库、UI 或渠道协议。
- Context、Tools、Memory、Session 通过清晰接口协作，彼此不能读取对方内部存储。
- 基础设施实现依赖上层定义的端口；核心不能反向依赖 Electron、具体渠道或插件实现。

当前源码尚未完全形成上述独立模块。本文描述目标边界，不把目标状态冒充为当前事实。

## 4. Prompt 是投影，不是真相来源

Prompt 用于向 LLM 投影当前运行所需的策略，包括角色、行为原则、输出约束、可用能力和必要的上下文索引。Prompt 不应承载：

- 完整工作流和状态转移；
- 工具实现、权限判断或重试逻辑；
- 大量业务 `if-else`；
- 整份长期记忆或知识库；
- 只能依靠模型自觉遵守的安全边界。

稳定策略的真相来源应是类型化配置、代码契约和用户设置。System Prompt 是这些策略中“模型需要知道的部分”的渲染结果，而不是另一套独立配置。

运行时文档各有明确职责，不能把其中任意一份等同于完整 System Prompt：

- `SOUL.md` 提供稳定人格、语气和身份偏好；
- `AGENTS.md` 提供操作规则、行为边界和工程约定；
- `USER.md` 提供经过确认的用户事实、偏好和长期约束；
- `PHILOSOPHY.md` 提供经用户确认的长期理念、价值判断和设计取舍原则；
- `TOOLS.md` 提供工具使用约定、风险和经验，但工具是否真实存在仍以工具注册表为准；
- Mode、权限、工作流、Context 策略和模型能力来自各自的类型化配置与运行决议。

`SOUL.md` 只定义人格与表达偏好，不等于完整 System Prompt。真正发送给模型的 System Prompt 是由身份、行为模式、操作规则、工具说明、输出约束和本轮必要索引共同渲染的结果；其中任何一份资源都不能单独取代其余策略来源。

Context Engine 只把本轮需要的投影装配给模型。上述资源被注册、被保存或可被检索，不等于每次请求都要全文注入。

因此，Prompt 变更必须回答两个问题：

1. 这条内容是否确实需要模型知道？
2. 如果模型忽略它，代码是否仍能守住权限、数据和流程边界？

第二个问题的答案若是否定，说明机制被错误地放进了 Prompt。

简言之，Prompt 是面向模型的 Policy 投影；Agent Runtime 是执行和守住该 Policy 的 Mechanism。不能用“模型通常会遵守”代替代码可证明的约束。

## 5. Mode 与权限必须正交

LS 需要区分 **Behavior Mode（行为模式）** 和 **Permission Policy（权限策略）**，避免一个“模式”概念同时改变行为和授权。

目标上的 Behavior Mode 是一个类型化配置组合：

```text
Behavior Mode = Prompt Profile
              + Workflow Strategy
              + Tool Selection Strategy
              + Memory Strategy
              + Context Strategy
              + Output Contract
              + Model Defaults
              + Parameter Defaults
```

通用、编程等属于 Behavior Mode。它们可以改变推理提示、工作流模板、上下文策略和工具候选范围，但不能自行授予权限。

完全访问、研究、受限属于 Permission Policy。它们只决定外部副作用是否允许、是否需要批准以及批准粒度，不改变 Agent 的任务判断逻辑或人格。

有效运行配置应理解为：

```text
Effective Run Config = Behavior Mode
                     × Permission Policy
                     × User/Project Overrides
                     × Provider Capabilities
```

Mode 配置只能引用已注册的策略和能力 id，不应允许任意代码直接进入核心状态机。新增 Mode 的最终目标是以配置和受测策略组合为主，而不是复制一套 Harness。

## 6. Context Engine

Context 不等于聊天历史，也不等于系统保存的全部信息。上下文是为当前决策筛选和装配的信息资产；会话、记忆、日志和资料可以完整保存在各自的数据层，但只有与本轮目标相关、来源清楚且预算允许的部分才能进入模型输入。

一次实际发送给 LLM 的上下文可能包含：

- System Prompt 和行为模式投影；`SOUL.md` 只贡献人格与表达偏好，`AGENTS.md`、Mode、工具说明、输出约束和必要索引共同构成最终投影，不能把其中任一文件等同于完整 System Prompt；
- 当前用户输入和附件清单；附件正文、图像或结构化内容按任务需要介入，不因用户选择文件就默认全量展开；
- 最近对话；保留轮数可以作为用户策略提示，但实际进入请求的范围还必须受任务相关性、模型窗口和 token 预算约束，不能只按固定轮数机械截断；
- 长会话摘要；
- 记忆树根索引和按需展开的记忆分支；
- 项目/RAG 内容；
- TaskBook、Workflow State 和输出约束；
- 必要的工具结果与验证证据；
- 与当前任务相关、由 LS 明确捕获且用户已授权的运行时事件，例如用户在应用内修改文件、调整设置、追加要求、暂停或恢复任务。

时间、进度和耗时属于运行时事实，而不是由模型根据聊天内容猜测的描述。每次实际 LLM 调用前，Agent Runtime 必须在 Prompt 缓存边界之后重新生成有界的 live runtime state，至少包含当前本地年月日时分秒、IANA 时区、UTC offset、run 起点与已耗时、TaskBook/步骤完成状态，以及已经结束的工具调用状态和耗时。动态秒级数据不得进入稳定 Prompt 前缀，也不得复用上一调用的旧时钟。

时间感知同样遵循渐进式披露。LS 可以用精确时间、步骤进度和耗时做超时、恢复、成本与调度判断，但普通回复不主动堆叠低价值数字；用户只问“现在几点”时默认只回答时与分，明确追问时才补充年月日、秒、时区或 offset。上一轮 run 的状态、总耗时、步骤完成数和有界工具耗时摘要应进入执行日志域内按会话关联的原子 sidecar，供紧接着的追问使用；完整工具输出仍只留在单 run 执行日志中，不能复制进 sidecar 或常驻 Context。

“LS 知道某件事发生过”与“把这件事放进本次模型上下文”是两层不同能力。运行时事件可以先进入有界事件账本，只有与当前决策相关、已获授权、通过安全检查且预算允许的部分才进入 `ContextSnapshot`；其余事件保留为审计、恢复或后续决策候选。不得把“双向信息同步”实现成全量监控或全量注入。

同理，“Agent 内部存在某项信息”应解释为该信息已经进入可发现、可追溯的资源注册表或 Context 候选池，而不是每轮把所有内部状态全文发送给模型。LS 应让模型在需要时知道有哪些信息可取、如何取和取到后能否信任，同时避免未相关的日志、文件、记忆和设置占满上下文。

为避免把“系统知道”误解成“模型每轮全文看到”，Context 相关信息必须分成三层：

1. **权威数据层**：会话、记忆、文件、配置、执行日志和检查点的完整事实，由各自服务持久化。
2. **可发现目录层**：资源注册表、附件清单、workplace 索引和运行时事件账本，只描述有哪些信息、来源、作用域、状态与读取方式。
3. **请求快照层**：本轮真正发送给模型的 `ContextSnapshot`，只包含当前决策必要、已授权、通过安全检查且预算允许的内容。

三层之间只能按明确规则单向派生。UI、Prompt 或日志不得另造一份与权威数据分叉的“上下文真相”；资源被登记也不等于正文已经读取，正文被读取也不等于必须进入本轮请求。

每个 run 还必须维护版本化的 `KnownState`（当前已知信息快照），作为 DECIDE、EXECUTE、VERIFY 和 FINALIZE 的共同事实边界。它至少区分已验证事实、用户明确陈述、记忆证据、工具证据、模型假设、未知项、冲突项，并为每项保留来源、时间、作用域、置信度和截断状态。各阶段必须记录自己读取的 `KnownState` 版本；工具结果、用户修订或验证结论产生新信息时，只能通过可审计事件生成下一版本，下游阶段改用新版本，不能依赖未登记的隐含状态或模型跨调用记忆。

进入 `KnownState` 前，每条外部或模型陈述必须先分类，而不是把“用户说过”直接等同于“事实成立”：

- **Instruction/Goal/Constraint**：用户要求、目标、范围和约束。用户对自己想要什么拥有最高权威，但仍受安全、权限和现实可行性约束。
- **Preference/Value**：用户的审美、习惯、取舍和主观体验。用户是该信息的权威来源；它是“关于用户偏好的事实”，不是普遍技术事实。
- **Reported Observation**：用户或外部渠道报告看到的现象。应保留原话与环境，但在工具复现或证据核对前标记为 reported。
- **Factual Claim**：关于系统、代码、世界或因果关系的可检验陈述。无论来自用户、网页、文档、模型还是旧记忆，都必须根据来源权威和证据标记为 unverified、corroborated、verified、disputed 或 superseded。
- **Suggestion/Hypothesis**：方案建议、推测、类比和可能解释。它可以进入候选方案，但不能自动写成事实或直接强化 confidence。
- **Decision/Approval**：用户对可选方案、风险、权限或方向作出的选择。它对后续执行具有约束力，但“选择了某方案”不证明该方案背后的技术论证为真。

系统判断的是具体陈述及其证据，不是对用户专业能力作画像。某条技术建议不准确，不能据此写入“用户不懂该领域”；相反，LS 应保留用户真实目标，核验会影响结果的事实前提，并用证据说明需要修正、部分采纳或采用其他实现。外部专家、官方文档、搜索结果和其他 Agent 的建议同样不能凭身份自动成为事实。

`KnownState` 是有界证据账本，不要求每个阶段把其中全部内容发送给模型。每项还必须携带 `statementKind`、`epistemicStatus`、`authorityScope`、assertedBy 和 evidence refs。每个阶段从当前版本派生自己的 active evidence set：可以加入新证据，也可以把已经无关、被替代、过期或对当前决策无帮助的候选移出请求快照。移出只表示“本次不注入”，不能删除权威数据；取舍理由和来源引用仍留在账本中，必要时可重新激活。Context 应随任务推进收敛，而不是只增不减。

“基于当前掌握的信息”不等于把现有信息当作完整真相。关键未知、冲突、过期、低置信或被截断的信息必须触发索引化记忆检索、工具验证或 `ASK_USER`；在证据边界内仍可安全推进时，应显式登记假设和风险，不能为了显得确定而补全不存在的事实。

Context Engine 的目标职责是：

1. 收集候选 `ContextItem`，每项带来源、作用域、优先级、敏感级别、时间和预算信息。
2. 根据模型上下文上限和当前策略分配预算。
3. 去重、压缩、裁剪并按稳定顺序装配。
4. 生成可审计的 `ContextSnapshot`，记录实际发送内容的来源和取舍理由。
5. 维护本地 token ledger，并将供应商返回的 usage 与本地装配计数分开记录和对账。
6. 在安全决策边界接收运行时事件；新事件可以触发上下文刷新或 TaskBook 局部修订，但不能悄悄改变已经发出的工具调用。
7. 从同一 run 的 `KnownState` 派生阶段请求快照，并记录本次调用使用的状态版本、未解决冲突和关键未知项。
8. 按当前阶段目标重新评估 active evidence set，淘汰无关、重复、被替代或低收益候选，并记录排除理由，防止 Context 在全流程中单向膨胀。

阶段软目标与模型窗口硬上限必须分开：软目标用于优先淘汰低价值可选项，真实模型窗口用于溢出保护和压缩建议。未知模型不能被假定为固定窗口，也不能仅因某阶段超过软目标就触发会话压缩。最近对话、当前请求、必要证据和 runtime awareness 的优先级应高于重复说明；软目标内无法容纳全部必要项时，只要仍未越过已知硬窗口就可以继续，并在快照中记录超出原因。

Token 信息必须遵守真实性边界：

- 本地 `ContextSnapshot` 是“客户端实际装配并准备发送的内容”的主动预算来源。只有与具体 provider/model tokenizer 明确匹配，并对最终序列化载荷计数时，才可称为精确本地占用。
- 请求完成后，供应商 usage 是服务端实际处理和计费口径的权威来源，用于与本地 ledger 对账；它不能反过来替代请求前的溢出保护。
- 本地装配占用与供应商 usage 是两个不同但都真实的指标。UI 必须标明来源和时间点，不能用其中一个无说明地覆盖另一个；差异超过阈值时应记录诊断。
- 字符数、通用换算或未知 tokenizer 的结果不能伪装成真实 token 使用量。
- 用户界面显示“已用上下文”时，只能使用有明确来源和定义的数据，并能追溯到对应请求或快照。

上下文压缩由可配置的占用比例阈值触发，也可以由有界的消息保留策略提前触发。优先压缩最近对话中的已完成过程、重复说明和冗长工具结果，生成带来源范围和版本的 Summary Memory；原始会话记录保留在数据层，摘要只替代后续请求中的旧消息片段。压缩后的最小语义契约必须让模型重新建立连续现场：用户要解决什么、刚才发生了什么、用户新增或调整了什么、哪些步骤已经完成、哪些仍待执行、关键证据和权限结果是什么。压缩必须保留任务约束、未完成步骤、关键事实、记忆来源和权限结果；失败时应回退，不得悄悄丢失约束。

## 7. Memory Manager

Memory 是 Context 的候选来源之一，不是 Context 本身。Memory Manager 管理持久记忆，Context Engine 决定本轮注入哪些记忆。

记忆树在运行时承担索引优先的 RAG 管理：决定信息注册在哪个作用域和分支、如何被定位，以及何时把最小必要片段介入对应对话。它不是要求每个分支都复制一套文件，也不是把所有注册文档常驻上下文。

记忆文件位于哪个物理目录、采用几级分片，只是持久化、恢复和规模治理问题；合理分层有助于维护，但不能成为检索或注入的主要依据。记忆能力的核心顺序是：从原始来源形成边界清楚的 Atom，维护 Atom 与实体/关系的可审计相关性，再根据当前目标、作用域、证据、时效和已验证 usefulness 动态选择、注入、释放或重新激活 Atom。目录位置、文件名、共现和向量距离只能帮助发现候选，不能替代这套判断。

注入决策必须区分五类信号：`task relevance` 表示 Atom 对当前任务是否直接有用，`confidence` 表示陈述是否可信，`verified usefulness` 表示该 Atom 是否曾在通过验证的任务中产生价值，`routing relevance` 表示它是否值得在后续相似任务中优先进入 Context，关系 `relevance` 表示当前实体关系对导航和排序的价值。释放、低频或一次无帮助只能调整后两类路由信号，不能把内容降格为错误事实；新的成功证据、强作用域匹配、用户明确点选或索引导航仍可重新激活候选。所有反馈摘要和关系聚合必须有硬上限，防止历史无限增长。

Atom 的“层级上升或下降”统一解释为**动态激活层级**，而不是移动文件、频繁改写语义 `parentId`，也不是把所有 Atom 固定塞进三层或四层分类。动态激活层级应由连续、可衰减的 activation score 表达：在真实任务中被采用且确实产生验证价值的频率越高，Atom 越早进入候选窗口和高速缓存；长期未使用、反复无帮助、过期或被替代的 Atom 逐渐退到更冷的候选区，但仍保持持久、可发现和可恢复。单纯读取、召回或留在 Context 中不算“用到”，不得形成自增强循环。

必须保持四个概念正交：语义 `parentId` 表达事物归属和层级；D0-D3 表达渐进披露深度；缓存的最多三级压缩深度表达有界压缩链；动态激活层级表达本轮候选速度和资源驻留优先级。当前兼容字段 `InjectionTier.T0-T3` 只能作为强制策略或治理类别，不能被解释为 Atom 的动态热度。持久记忆 Atom 与语义缓存 Atom 可以共享同一套激活计算，但必须保留独立 namespace、生命周期、TTL 和删除规则，避免缓存内容混入长期记忆事实层。

activation score 只能作为任务相关度门后的排序先验，不能让一个与当前任务无关的高频 Atom 越过 scope、证据、认识状态或预算直接进入 Context。分数应基于有界聚合计数和时间戳惰性计算，不保存无界访问历史，也不依赖全库定时扫描；运行时可以按设备能力和 Context 预算动态划分热区，不把热区数量写成长期数据模型。

后端动态激活层级可以连续变化且不限制层数；前端若需要向用户呈现活跃程度，只映射为三层简化视图。三层是可丢弃、可重建的 UI projection，不写回 Atom，也不改变后端排序。映射应使用滞回区间和稳定过渡，避免分数位于边界时来回跳层；普通记忆文件页仍不暴露 Atom 结构，只有明确需要的概览或高级治理入口才显示这三层结果。

记忆运行时的核心闭环固定为：**沿层级缩小候选范围 → 计算当前任务相关度 → 结合 scope、权威、认识状态、时效、routing 和关系信号排序 → 按预算注入少量 Atom → 在 `KnownState` 登记采用与排除 → 执行中按需展开或释放 → 依据显式使用和验证证据分层反馈**。任何存储布局、索引实现或向量召回策略都只能服务这条闭环，不能绕过当前任务相关度、作用域、证据和预算直接决定注入。

关系不能只作为已经入池 Atom 的排序装饰，也不能变成无界图遍历。Runtime 可以从当前任务的高相关种子 Atom 出发，在同一 branch、scope、scopeKey 和已导航 subtree 内做一次有界关系扩展，以发现必要依赖、支持证据、替代项或冲突项；关系必须已生效、未过期、来源可追溯并通过 confidence、authority 和 relevance 门。`depends-on`、`supported-by`、`replaces`、`conflicts-with` 等按各自方向解释，`similar-to` 只帮助导航，不能自动注入。每个邻接 Atom 仍须独立通过 task relevance、认识状态和 Context 预算，不能因为“与种子有关”就进入模型请求。

“当前任务相关度”必须先回答本轮到底在做什么。当前输入已经自足时，不得为了显得连续而拼接旧历史；出现真实指代、延续或对 LS 先前方案的选择时，只能继承有界的最近目标。显式切换任务必须阻断旧话题。正向主题、硬排除对象和“某对象已被否决”这类负向约束属于不同语义：排除对象正文不能因词面相似被注入，方向一致的约束仍应保留。D1、FTS、向量候选必须使用同一结构化任务语义，不能在不同披露层各自猜测并互相推翻。检索结果数量只是上限，不是目标；出现清晰相关性断层时应停止，不能为了把列表填满而消费 Context。

长会话压缩后的版本化 Summary Memory 也只是任务语义的回退来源，不是新的权威事实层。只有当前请求确属指代、近期有界消息仍缺少任务锚点时，才可按预算提取目标、未完成事项、下一步、约束和决定；当前请求、近期明确用户目标、任务转向、排除条件和作用域始终优先。摘要文件位于哪里、是否刚生成、文本多长都不能直接提高 Atom 注入权重。弱相关候选应继续留在索引中供后续展开，而不是为了填满首轮 working set 自动进入 Context。

Atom 的完整性哈希与 Embedding 语义哈希必须分离。完整性哈希覆盖 Atom 的全部持久字段，用于检测文件被改写；Embedding 哈希只覆盖真正送入本地向量模型的标题、摘要、正文和检索键。层级、反馈、审计、可信度或其他治理元数据变化不得触发无意义的向量重算，只有语义输入变化才使向量进入重建队列。

LS 的记忆系统至少包含：

- Working Memory：当前 run 和最近会话；
- Summary Memory：长会话压缩后的可追溯摘要；
- Long-term Memory：稳定用户事实、偏好和长期约束；
- Project Memory：项目状态、决策和待办；
- Experience Memory：可复用的执行经验；
- Knowledge/RAG：外部知识与项目资料。

这些类型还必须按记忆主体区分，而不是混成一棵没有边界的树：

- **User Memory**：用户事实、偏好、习惯、目标、约束和用户确认的长期决策；用户拥有最高管理权，推断内容必须与用户明确陈述分开。
- **Agent Self Memory**：LS 的身份与使命、稳定行为约束、已注册能力、工具经验、失败教训和版本化运行认知。可学习经验不能覆盖更高权威的安全规则、产品原则或用户当前要求。
- **Task/Project/Session Memory**：当前任务、项目和会话的状态、摘要、证据与待办；作用域结束后按策略压缩、归档或提升，不能无条件污染长期用户记忆或 LS 自身记忆。
- **Knowledge Memory**：外部资料和受管资源的索引与证据，不因被检索就自动转化为用户事实或 Agent 经验。

所有 memory domain 使用同一个 Memory Repository、原子模型、索引导航、来源审计和权限协议，只通过 domain、scope、authority 与生命周期区分。不得为 UI、Prompt、用户画像或“自我认知”另建不可追溯的旁路记忆副本。

记忆系统必须明确区分三种视图，三者共享权威来源但不共享披露深度：

1. **用户文件视图**：GUI 的“记忆树”只展示应用数据根中的 `AGENTS.md`、`SOUL.md`、`USER.md`、`PHILOSOPHY.md`、`TOOLS.md` 和 `MEMORY.md`。当前仅 `SOUL.md` 可由用户直接编辑，其余文件只读；Atom、关系、向量、压缩投影和审计记录不进入普通前端。
2. **Runtime 记忆视图**：Runtime 使用完整的 Atom、层级、关系、来源、投影记录和本地向量目录执行写入、治理、恢复与检索。内部治理 API 可以保留，但不得因此把底层结构重新暴露为用户默认界面。
3. **LLM Context 视图**：模型先收到一段简短的记忆树说明和受限长度的根索引，知道有哪些分支、何时使用及如何继续展开；具体 Atom 只按 `root index -> branch index -> expand -> branch-scoped deep search` 渐进介入。模型拥有“完整记忆树可按需访问”的概念，不等于全树正文常驻 Context。

未来让 LS 介绍自己的能力、人格、记忆边界和当前状态时，应通过独立 Skill 组织用户可理解的说明；不能要求用户阅读 Atom、向量或审计结构来理解 LS。

记忆系统还必须显式表达“事物边界”和“关系”，避免把名称相近、路径相邻或经常共同出现的对象误合并为同一事物。Memory Repository 中的实体至少覆盖用户、项目、文件、目录、会话、任务、Skill、工具、规则、概念和外部来源；关系至少覆盖属于、依赖、引用、冲突、替代、派生、相似、影响和证据支持。每条关系必须保留方向、作用域、来源、证据、置信度、权威范围、相关度、有效时间、过期时间和冲突/解析状态。

实体相似度、向量距离、共现频率和路径邻近只用于导航与候选排序，不能自动证明两个实体相同、证明一条关系为事实，或触发记忆/Skill 合并。跨用户、跨项目、跨会话、跨插件所有者和跨安全作用域的关系默认保持边界；只有稳定标识、明确来源或经过验证的映射才能建立强关联。关系也遵循渐进式披露：D0 显示实体类型、边界和可发现入口，D1 显示摘要与最强相关关系，D2 展开当前任务需要的关系邻域，D3 才显示完整证据、版本、冲突和关系历史。

所有记忆信息都遵循统一的渐进式披露层级，且该层级与 T0-T3 介入优先级相互独立：

1. **D0 可发现层**：根索引、domain/branch、数量、状态和可继续展开的入口。
2. **D1 摘要层**：atom 标题、摘要、scope、tier、authority、confidence、importance、新鲜度和冲突提示。
3. **D2 内容层**：当前任务需要的原子正文与直接证据引用。
4. **D3 审计层**：来源全文、版本、更新事件、反馈、冲突处理和生命周期历史。

Runtime 与 LLM 检索默认从 D0/D1 开始，只在当前决策或验证确有需要时进入 D2/D3。普通用户 GUI 不直接映射 D0-D3 Atom 结构，而使用上面的记忆文件视图；高风险、冲突、低置信和待用户确认状态由 Agent 在相关任务或专门治理流程中明确披露，不能因内部结构隐藏而被静默忽略。

记忆注册表应能描述不同权威和用途的资源。运行时资源统一使用现有稳定名称，避免同义文件分裂：

- `AGENTS.md`：操作规则、行为边界和工程约定；
- `SOUL.md`：稳定人格、语气和身份；
- `USER.md`：用户称呼、偏好、习惯和长期约束；
- `PHILOSOPHY.md`：经用户确认的长期理念、价值判断和设计取舍原则；
- `TOOLS.md`：工具约定、风险和已知使用经验；
- `MEMORY.md` 与记忆树节点：兼容长期记忆来源和结构化记忆；
- `skills/<name>/SKILL.md`：可复用能力与专项工作流；
- 项目规范、UI 设计规范、任务书及其他正式文档：按 `documentKind`、scope、authority、privacy 和索引键注册，由 Agent 判断何时读取。

上述名称是资源类型与默认权威来源，不是要求每个层级或每个分支都复制一套文件。一个分支只注册它确实需要的资源；同一物理内容必须有唯一权威来源，其他作用域通过索引或受控投影引用，不能靠复制维持“记忆完整”。

Skill 属于 LS 应用数据和能力注册表的一部分，但不同来源拥有不同所有权。内置 Skill 随应用版本管理；用户和 LS 自动形成的 Skill 位于活动数据根的 `skills/`；插件 Skill 由对应插件拥有；外部 Skill 由外部路径拥有。治理时必须保留稳定 id、owner/source、版本、内容哈希、适用范围、依赖、使用证据和回滚位置。重复或高度相关的 Skill 只能先形成可审查的合并建议，经过语义、权限、依赖和回归验证后再生成新版本；相似度或调用次数不能直接触发覆盖。低收益、过期或无效 Skill 优先停用或归档，确认无引用、经过保留期且具备恢复证据后才允许删除。非 LS 所有的来源文件默认只能停用登记，不能由 LS 擅自删除。

长期、daily、项目和经验记忆采用四层数据模型。四层职责必须分开，不能再把内部恢复记录称为“原始数据”：

1. **对话原始来源（Conversation Source Records）**：原始数据只指用户发来的内容，以及用户能够在对话区域看到的 LS 回复、任务步骤、工具过程、验证结果和错误。它只证明“当时收到了或展示了什么”，不自动证明其中的技术主张为真。每条来源记录具有稳定 id、会话/run、发生时间、原始载荷和内容哈希；成功写入后不提供 update、merge、delete 或 prune API，纠正和补充只能形成新的来源记录。
2. **投影变更记录（Projection Mutation Records）**：保存一次 `MemoryUpdateEvent`、拟执行的结构化 mutation、期望 revision、捕获时间和内容哈希，并通过独立 commit receipt 证明提交边界。它只服务幂等、崩溃恢复和审计，不是用户对话原始数据，也不替事件内容作事实判断。
3. **Atom Projections**：从一个或多个对话原始来源、外部证据或兼容迁移基线提取的当前语义投影。一项 atom 表达一个可独立理解、检索和治理的事实主张、偏好、建议、决策、约束或方法，并保留 `statementKind`、`epistemicStatus`、`sourceRefs` 与 `evidenceRefs`。Atom 本来就是允许持续修订的当前投影，而不是不可变记录；它可以在 revision 前置条件和审计约束下去重、合并、调整父层级与关系、规范化、失效、恢复、重建或形成 tombstone。这些操作只演化投影，不改写对话原始来源。原子化按语义所有权切割，不按固定字符长度机械分块。
4. **Run Context Working Set**：当前 run 已实际介入模型请求的有界 atom 集合。它可以随任务推进加入、排除和重新激活 atom；排除只释放本轮 token 与去重预算，不改变对话原始来源或持久 atom。

Memory Repository 统一管理对话原始来源、投影变更记录、atom projections 和内置本地向量目录。对话原始来源是“用户与 LS 当时可见交互”的权威来源；投影变更记录是幂等与恢复依据；atom 文件保存可审计的当前语义投影与最小重建元数据；SQLite catalog 管理路径、父子关系、FTS、向量、状态、反馈、操作投影和审计。catalog 必须可从持久文件重建，不能成为不可恢复的唯一记忆副本；有界 recovery journal 只负责跨介质提交和重启恢复，不能冒充长期原始数据源。文件与数据库的跨介质更新使用可恢复 operation journal，不能假装普通 SQLite 事务可以同时原子提交文件系统。

记忆更新采用事件驱动而不是定期重写整棵树。用户新增或纠正信息、任务/工具/VERIFY 产生证据、项目和受管资源变化、能力与配置变化、冲突解决、权限决定，以及到期、衰减或重新验证时间到达，都生成版本化 `MemoryUpdateEvent`。事件必须带 idempotency key、subject/domain、scope、来源、发生时间、观察时间、目标 atom/parent、证据和期望版本。

为保证不失忆，V3 backend 激活后，Runner 必须在每轮结束时补齐该轮全部对话原始来源；EVOLVE/CAPTURE 若要据此写 Atom，必须先确认所引用来源已成功持久化，来源捕获失败时延期投影写入。正式 V2 路径在迁移前继续以会话 JSONL 保存可见对话，不提前创建 V3 来源文件。随后，每次 Atom 变化先形成带哈希的投影变更记录，再登记到有界 recovery journal，由幂等流程完成去重、Atom 更新、catalog 投影和审计。mutation 到达提交边界后另写 append-only commit receipt；若进程恰好在投影变更记录落盘后、journal 登记前中断，启动时必须从该记录自动补建恢复事件。含糊或冲突状态必须失败关闭，不能猜测覆盖。journal 可以按容量裁剪已提交记录，但投影变更记录与 commit receipts 不随之删除；catalog 删除重建时，历史记录依据 receipt 恢复审计投影，不能倒放旧 mutation 覆盖更高 revision 的当前 atom。应用运行时在安全边界近实时消费事件；应用关闭期间到期的时间事件和已登记资源变化，在下次启动时按 due index 与资源指纹补偿对账，不进行无授权的全系统监控。

“不失忆”在工程上表示：已确认需要保留的信息具有持久权威副本、稳定索引、版本来源、恢复路径和可验证备份，并能在相关时重新取回；不表示全部记忆永久注入每次请求。用户明确删除、依法清理或按已确认策略到期的信息仍可移除，但必须经过权限、引用检查、tombstone/审计和可恢复保留期。

Embedding 默认由应用内置的本地多语言引擎生成。Provider `/embeddings` 只能在用户明确启用后使用，不能因为配置了聊天模型就自动发送记忆正文或检索词。即使向量引擎不可用，层级索引与本地 FTS 仍必须工作。

记忆读取坚持索引优先：

```text
root index -> branch index -> node expansion -> branch-scoped deep search
```

向量召回只作为已导航分支或子树内的候选，不默认跨树搜索，也不能直接把召回结果塞入 Prompt。向量目录先返回 atom id、分数和命中原因，正文仍从原子文件按 Context 预算读取。

首次业务请求只能从 D1 索引元数据中选择一个很小、受预算约束的 D2 初始 working set；不得为了“更聪明”先做跨树向量搜索或加载整份近期记忆。默认仍只保留最强任务相关簇；只有已独立通过任务门、由高质量语义关系发现且 route strength 达到硬门槛的必要 Atom，才可跨越普通相关性断层与种子一同进入首次 working set。执行过程中，LLM 可以通过受控的记忆工具请求 branch index、expand、branch-scoped deep search，或把已经无助于当前目标的 atom 从本轮 working set 中 release。Runtime 负责校验导航前置条件、作用域、预算、去重和证据封套；release 后的 atom 仍保留在持久记忆中，并可在出现新证据或目标变化时重新介入。

随着使用增加，Atom 及其关系必须能依据真实结果持续演化，让有效数据更容易被精确取回，让当前无效或低收益数据退出默认介入。注入优先级应综合当前 scope/项目匹配、来源权威、任务相关性、confidence、importance、新鲜度、已验证的历史使用收益以及冲突、失效和过期惩罚；访问次数只能表示“经常被取用”，不能单独证明内容正确，也不能绕过层级导航、权限和预算。长期没有再次产生验证价值、使用收益持续下降或与当前任务弱相关的可选记忆，应通过可配置衰减降低候选优先级；衰减只影响注入策略，不自动降低事实 confidence，也不能淘汰 T0、安全规则、当前用户约束或其他强制信息。

Atom 的动态字段必须分工明确：`confidence` 表示陈述可靠性，只能由新的权威来源、用户在其权威范围内的确认或验证证据改变；`relevance` 与已验证 usefulness 表示某个 Atom 或关系对实际任务的帮助程度，可以随成功、无帮助、冲突和过期结果调整；`importance/basePriority` 表示治理优先级，不能由访问次数自动抬高。完全相同或近义 Atom 应在认识类别、作用域和权威边界内去重；合并必须保留全部 `sourceRefs`、`evidenceRefs`、来源 Atom tombstone 和变更历史，不能因为重复出现就覆盖正文或自动提高 confidence。层级变化必须保持稳定 id，并通过 parent revision、循环检查和同作用域约束完成。

记忆正文进入 LLM 请求时必须使用有界的 `MemoryEvidenceEnvelope`，至少携带 atom 引用、branch/scope、tier、statement kind、epistemic status、authority scope、asserted by、来源与证据引用、confidence、importance、验证/更新时间、新鲜度、命中理由、状态、冲突和截断信息。若 Atom 由关系发现，还必须记录独立的 `relation` 检索路径，以及种子 Atom、关系 id、类型、方向、confidence、relevance 和 route strength，不能伪装成 hierarchy、FTS 或 vector 命中。模型可以据此区分“事实”“用户陈述”“建议”“决策”和“假设”并判断证据权重，但不能直接修改这些元数据。内部缓存统计、完整访问历史和无助于当前决策的排序细节不得为“透明”之名全部塞进 Prompt。

记忆反馈必须防止错误自增强。只有用户在其权威范围内确认，或某次使用获得结构性 VERIFY、成功工具证据等可追溯结果时，才允许提高该 atom 的已验证 usefulness；是否同时提高 confidence 还取决于证据是否真的支持该陈述。单纯被读取、被模型引用或重复出现不构成强化证据。显式 `release` 可以记录为未验证的路由反馈，但不能据此断言 Atom 错误。错误、无帮助、冲突或过期的使用结果应形成可审计负反馈并降低候选优先级或关系相关度，但失效、删除和冲突解决仍须经过各自治理闸门。

目标分级扩展为 T0-T3：T0 是极小、稳定且必须常驻的身份/安全/根索引信息；T1 是被激活作用域的核心规则和摘要；T2 是当前任务相关片段；T3 是低频细节、对话原始来源、深层审计和分支内深搜候选。T0-T3 表示介入优先级、权威和预算语义，不等于磁盘目录只能有四层。现有 T1-T3 数据必须通过版本化迁移映射，不能直接改枚举导致旧数据失读；树的分支数量和子索引深度可以由 Agent 在预算、权限和可维护性约束内按需增长，但常驻 T0 预算必须固定。

项目记忆在逻辑上跟随项目，并采用“私有权威数据 + 可选项目内投影”的双层策略：完整、可审计的权威数据默认位于 LS 用户数据目录并以稳定 project id 关联；只有用户明确启用后，才在项目目录写入经过筛选的投影。运行时项目内投影默认仍属于私有 Agent 数据，不建议提交到线上仓库；创建前必须说明用途、包含内容、隐私边界、同步方向、建议的 Git 忽略方式和误提交风险。若用户确实需要共享项目背景，应使用单独的“可共享导出”动作和更严格的字段白名单，不能把运行时投影直接改名为公开文档。任何投影都不得包含密钥、私密用户画像、完整执行日志或其他不适合进入项目仓库的数据。

记忆写入必须沿层级和索引确定 domain、parent、scope、tier、statement kind、epistemic status、authority scope、对话来源、外部证据、置信度、重要性、时间语义和理由，并经过安全、去重、合并、预算和审计闸门。`sourceRefs` 只引用对话原始来源；工具、VERIFY、外部文档和其他佐证进入 `evidenceRefs`，两者不得混用。建议只能以 proposal/hypothesis 状态保存；事实主张必须保留验证状态；用户目标、偏好和决定按其权威范围保存，不能与客观技术事实混写。模型可以提出结构化记忆写入意图，也可以在当前 run 内请求加入或释放 atom；但它不能直接改写对话原始来源、提交持久 mutation、覆盖认识状态或解决冲突。运行时依据真实来源、`MemoryUpdateEvent`、工具证据和 VERIFY 结果决定是否更新 Atom 投影。默认 UI 不打扰用户；GUI 只开放记忆文件视图和 `SOUL.md` 编辑。完整 Atom 变更记录仍必须在内部可审计、可导出并能按治理规则失效、恢复或重建，后续若新增高级治理入口，也必须操作 Runtime 的同一份数据而不是展示副本。

EVOLVE/CAPTURE 中的模型只能描述 domain、statement kind、asserted source 和 topics，不能声明 verified、authority 或 resolution。Runtime 必须把 asserted source 与实际对话来源、成功工具结果或外部资源证据对账；对账失败时降级为 LS 自身的未验证陈述，并移除不可信主体标识。旧式 daily 原文追加到 `MEMORY.md` 的蒸馏路径不得存在；任何压缩、蒸馏或提升都只能产生结构化 Atom 提案，再经过同一套来源、认识状态、去重、审计与恢复闸门。

## 8. Tool Execution Service

LLM 可以提出结构化工具调用，但不直接持有工具对象或执行权限。统一的 Tool Execution Service 应负责完整生命周期：

```text
propose -> resolve -> validate -> authorize -> execute
        -> sanitize -> record -> retry/recover -> return evidence
```

所有工具，无论来自内置实现、技能、MCP 还是插件，都必须复用以下契约：

- 名称冲突与来源可追踪；
- 输入 schema 校验；
- 工作区和路径边界；
- 权限审批与风险说明；
- AbortSignal、超时和有限重试；
- 输出清洗、截断和敏感信息处理；
- 结构化结果、耗时和错误分类；
- 执行日志与 UI 流式事件。

同一模型响应中的工具调用可以并行，但必须由 Runtime 根据声明的资源访问、路径重叠、副作用、审批和依赖关系分波执行。缺少信息或工具类型未知时默认独占；并发度、队列和超时有硬上限；结果按模型原始调用顺序进入对话和证据，不能让完成时序随机改变语义。

当前阶段禁止 LS 通过内置写入、编辑或命令工具修改自身核心源码。核心源码可以被只读工具用于诊断，但源码根是审批之外的宿主级只读边界，完全访问模式也不能绕过。未来只有在主要能力与发布恢复链成熟后，才能单独设计受控自我修改：使用显式 feature flag、隔离分支或工作树、版本检查点、完整构建与回归、用户可见差异、失败自动回滚和人工最终批准；不得直接修改正在运行的活动版本。

Harness 负责“何时需要工具”和“工具结果如何进入步骤”，Tool Execution Service 负责“这次调用如何被安全执行”。两者不得重复实现权限、超时和结果规范化。

对可执行任务，真实操作、结构化结果和验证证据的优先级高于看似完整的文字说明；但工具不是目的。若现有上下文已经足以可靠回答，或工具成本与风险明显高于任务价值，就不应为了展示执行能力而调用工具。

工具的价值按它是否直接或间接提高任务兑现率衡量。除完成任务的直接工具外，能可靠降低等待、重复操作、上下文噪声、恢复成本或验证成本的索引、缓存、观测和恢复工具也属于合理能力。若一个新工具能够在代表性任务中稳定提高完成率或效率，并且权限、失败语义与维护成本可控，就应进入开发候选；但不能仅凭主观判断直接加入默认工具集。每个新工具都必须证明收益、权限边界、Context 成本、维护成本和可移除条件。

## 9. Workflow Engine

复杂任务的主流程属于代码，而不是 Prompt。Harness 必须掌握状态转移、重试上限、权限、验证和收尾。

目标形态采用“固定安全脊柱 + 可选择工作流策略”：

- 安全、授权、验证、恢复上限和 FINALIZE 是不可绕过的硬约束。
- Behavior Mode 可以选择已注册的工作流模板或阶段策略。
- LLM 可以决定阶段内部的语义内容，不能任意跳过阶段或创建未注册状态。
- 简单任务走轻量路径，复杂任务使用 TaskBook，避免“大炮打蚊子”。
- 合理超出用户预期可以提高结果价值，但额外范围或成本通常不得超过原请求的三倍。
- TaskBook 应显式表达步骤依赖、资源作用域和副作用。只有依赖已经满足、读写集合不冲突且权限允许的就绪步骤才可并行；同一路径写入、同一外部资源变更、需要顺序语义的验证以及共享审批必须串行。
- 并行调度必须有小而明确的默认并发度和不可突破的硬上限。每个分支独立记录开始、工具调用、结果、验证、取消和失败；归并时按 TaskBook 依赖与稳定顺序生成证据，不能让完成先后随机改变最终语义。
- 复杂 run 在安全决策边界接收用户追加消息和应用内相关事件。运行时重新理解目标并生成 TaskBook 差异，只修改受影响的未完成步骤，保留已完成证据；无关事件进入有界队列，不抢占当前动作。
- 暂停、用户中断、应用重启和可恢复故障都应写入版本化检查点。恢复必须从幂等边界继续，不能重复已成功的外部副作用。
- 所有验证、恢复和重规划循环都必须同时受尝试次数、总时长、成本/上下文预算和“无进展”检测限制；不能用“直到成功”为由形成死循环。

工作流可配置不等于允许任意图结构。只有在状态、迁移、失败语义、恢复语义和测试都明确后，才能增加新的工作流定义。

## 10. Plugin 与核心边界

插件赋予 LS 可扩展性，但不能成为核心运行条件。无插件时，本地 UI、Runner、Harness、内置工具、会话和记忆必须正常工作。

- 外部渠道是插件，只负责消息适配和回传。
- 插件能力通过版本化贡献接口注册，不直接修改 Runner/Harness 内部状态。
- 插件工具必须进入统一 Tool Execution Service，不能绕过权限和日志。
- 插件记忆、Provider、工作区或 UI 扩展必须先定义生命周期、权限、数据目录、错误隔离和卸载语义。
- 本地插件代码默认不信任；启用本地代码等同于用户明确接受其执行风险。
- Plugin SDK 与 Host 是否拆包，应在核心契约稳定后决定，不能为了目录整齐提前制造版本负担。

## 11. 数据与状态边界

- 源码仓库只保存产品源码、测试、正式文档和维护脚本。
- LS 的**应用数据根**是可整体迁移的活动目录，默认名称为 `.littlesheep`，实际位置由 `LITTLESHEEP_DATA_DIR`、外部 locator 或 branding 默认值解析；不能把默认目录名写死成唯一位置。
- 用户配置、API key 引用、会话、用户记忆、LS 自身记忆、执行日志、Skills、插件与插件数据、项目关联和 UI/工作区恢复状态都属于应用数据根。
- `<data-root>/workplace` 只是用户未选择项目或文件夹时的默认工作区，是应用数据根的一个子目录；它不是应用数据根的别名，也不承载应用的全部数据。
- 构建产物、缓存、日志和临时文件不进入 Git。
- 持久化协议必须版本化；修改前考虑旧数据读取、迁移、失败回退和回滚。
- 改写用户数据前必须先有只读诊断、备份/快照策略和用户授权。
- LS 应用数据与用户授权工作区采用不污染现有仓库的本地 shadow Git 或等价版本化存储。每轮完整对话至少形成一个关联检查点，写入前保留 preimage，正常结束保留 post-state，应用退出先冻结可恢复状态；数据域与工作区域版本必须由同一 manifest 关联，支持同步回退并保留部分失败诊断。
- 版本化不等于全盘收集。密钥、凭据、缓存、日志、SQLite/WAL、向量、构建物和其他可再生或敏感内容默认排除；回退只恢复受管文件，不删除无关未跟踪文件，也不接管用户已有 `.git`。
- 用户可以选择 LS 应用数据根目录。迁移对象是完整数据根，不只是 `workplace`；迁移必须暂停写入、创建快照、复制并校验全部受管数据、原子切换配置且保留失败回退。若必须重启才能完成切换，应在执行前明确告知用户。
- 数据根必须有可查询的受管资源清单，至少区分配置、会话、记忆树、项目关联、归档、执行日志、恢复检查点、附件缓存、默认 workplace、插件数据和 UI 恢复状态。目录名称可以演进，但每类数据的所有者、版本、迁移和清理策略必须明确。
- 上传/粘贴附件默认进入受管缓存或 workplace，并先注册附件清单；正文、图像和结构化内容只在任务确有需要时读取。缓存清理不得删除用户主动放入 workplace 的文件。
- Agent 应能通过有界索引了解自身 workplace 的目录和用户放入的文件，但不能把“知道存在”实现成每轮全量扫描或全文注入。用户文件始终归用户所有。

## 12. 模块与依赖规则

1. `@littlesheep/types` 只放稳定契约，不放文件系统、网络或 Electron 实现。
2. 核心包不得依赖 `packages/app/` 或具体 `packages/channels/*`。
3. 渠道和插件通过公开端口接入，不 import Runner、Harness 的内部文件。
4. Renderer 不直接读取用户数据文件、数据库或调用 Provider；统一经过 Local App API。
5. Local App API 只做输入校验、用例调用和协议转换，不持续吸收领域逻辑。
6. 新建 workspace 包之前，先证明其拥有独立职责、稳定接口、生命周期和测试；否则优先在现有包内建立子模块。
7. 公共协议从包入口导出，禁止跨包深层 import 私有文件。
8. 不允许循环依赖；依赖方向若需反转，应使用端口或事件，而不是互相 import。
9. 跨模块事件和持久化结构必须有明确版本、生产者、消费者和恢复策略。
10. 一个事实只能有一个真相来源；UI 展示模型、Prompt 文本和日志都应由该来源派生。

## 13. 目标、抽象与复杂度

功能、抽象、名称和目录结构都服务于用户目标与协作效率，不是独立目标。架构决策按以下顺序权衡：

1. 用户真实目标、时间与消费成本；
2. 安全、权限和用户数据边界；
3. 正确性、真实性和可验证证据；
4. 稳定性、可恢复性和运行成本；
5. 可维护性、可扩展性和团队理解成本；
6. 概念纯度、术语偏好和形式上的完整。

这不是允许含糊设计。命名和抽象本质上是认知接口，应按影响范围提高精度：

- 局部私有实现优先直观和低成本，只要作用域内含义一致即可；
- 跨模块共享概念必须有唯一含义、所有者和依赖方向；
- 公共 API、插件协议、权限语义和持久化格式必须精确定义、版本化并可迁移；
- 若历史名称已经被用户理解且不造成错误，可以保留；若它开始混淆安全边界、数据所有权或模块职责，就应提供兼容迁移，而不是继续积累语义债务。

LS 采用“最小充分架构”：先选择能够可靠解决当前问题、同时保留合理演进路径的最简单机制。只有当新抽象能够降低真实耦合或重复、建立稳定契约、隔离风险，或满足已经出现的复用需求时，才值得引入。不得因为流行术语、目录对称、形式完整或假设中的未来需求提前增加包、层级、配置和工作流。

简单可靠不等于拒绝演进。当前机制无法满足结果、可靠性或规模要求时，应依据证据重构；重构目标是消除已经发生的约束，而不是追求理论上的终局架构。

## 14. 生命周期与有界资源

所有长期运行的模块都必须明确创建、使用、取消、停止和卸载路径。一次性 UI、请求、连接和动画不能因为组件重挂载、页面切换、重试或应用关闭而继续持有资源。

对用户而言，下列动作必须保持独立语义：隐藏或切换对话、关闭最后一个窗口、暂停任务、中断当前 run、放弃任务、彻底退出应用。隐藏界面不能自动等同于取消任务；中断也不能自动等同于删除检查点。若用户选择让活动任务在后台继续，LS 必须提供可见状态、重新打开入口和明确的彻底退出动作。可恢复任务不设置“只能重启若干次”的业务限制；只要检查点仍在受支持版本和保留期内，重复关闭、重启或用户主动中断后都应能够继续。检查点数量、历史版本和磁盘占用仍必须有有界保留与淘汰策略，不能为了无限恢复造成资源泄漏。

- 异步请求必须绑定组件/任务生命周期，使用 `AbortSignal`、请求代次或 `mounted` 守卫，过期结果不能覆盖新状态。
- `setTimeout`、`setInterval`、`requestAnimationFrame`、`ResizeObserver`、DOM 事件、WebSocket、PTY 和子进程必须在对应生命周期结束时清理；重复启动前先清理旧资源。
- `AbortSignal`、EventTarget 和其他长期对象上的监听器必须在成功、失败、超时和取消四条路径都解绑，不能只依赖 `once` 等待未来可能永远不会发生的取消事件。重复轮询、重连和模型调用应复用经过测试的生命周期辅助函数。
- 内存中的历史、Map、Set、目录/响应缓存、授权记录和事件流水必须有明确上限、淘汰策略和重启语义；页面历史只保存有界的标量快照，不复制消息正文或文件内容。
- 服务停止必须统一中止活动请求、结算等待中的 Promise、移除监听、关闭连接和进程，并清空临时引用；不能只关闭最外层 HTTP 监听。
- 每个新增模块的验收清单必须包含卸载、重复打开/关闭、请求取消、异常路径和长时间运行下的资源增长检查。

## 15. 可观测性与验证

每次 run 应能回答：

- 用户目标和校准后的成功标准是什么；
- 使用了哪个 Behavior Mode、Permission Policy、模型和工作区；
- 实际装配了哪些上下文，为什么被选中或丢弃；
- 执行了哪些步骤和工具，权限结果是什么；
- 供应商 usage、错误、重试和中断来自哪里；
- 每个验收标准如何被证明；
- 哪些信息被写入记忆，依据是什么。

信息透明是双向的：Agent 只能接收与当前任务相关、由 LS 明确产生或用户授权观察的事件，不能以“同步”为名扫描无关隐私；用户则能看到 Agent 正在做什么、改了什么、为何等待、是否在后台运行以及从哪个检查点恢复。

可观测性数据必须服务于调试、恢复和用户控制，不能反过来成为大段默认注入 LLM 的上下文。

验证按风险分层：

- 纯函数和 schema：单元测试；
- 包间协议：契约测试；
- 状态机、上下文和工具生命周期：场景测试；
- Provider、渠道、PTY、持久化：真实集成测试；
- Electron 关键交互与重启恢复：端到端和可视验收。

## 16. 禁止的架构捷径

- 通过继续堆 System Prompt 修复本应由代码控制的问题。
- 让模型自行保证权限、安全、重试或状态一致性。
- 把整份历史、记忆树或工具输出无预算地注入上下文。
- 为 UI 单独维护一份与运行时不同步的状态真相。
- 为一个尚未稳定的概念立即创建新包或公开插件接口。
- 在 Runner、Local App API、`App.tsx` 或单个 stage 中继续堆积跨域逻辑。
- 用“已配置”“已有接口”冒充真实供应商或真实用户场景已验收。
- 为追求可配置性而放松安全状态、权限和验证硬约束。
- 为追求术语纯度、目录对称或形式完整而重构稳定模块。
- 把复杂工作流、额外工具调用或超出请求的产物当作能力展示，让用户承担与目标不相称的成本。

## 17. 架构变更门槛

涉及 Mode、Context、Memory、Tools、Workflow、持久化或插件公共接口的变更，实施前必须说明：

1. 当前问题、用户影响与可复现证据；
2. 为什么现有机制或更简单的修改不足以解决问题；
3. 责任应归属哪个模块；
4. 新旧契约、依赖方向和数据迁移影响；
5. 安全、权限、上下文预算和用户数据风险；
6. 回归测试、真实场景验收和失败回退方案；
7. 哪些正式文档需要同步更新。

若一次变更无法明确回答这些问题，应先做边界审查或特征测试，不直接进入大规模重构。

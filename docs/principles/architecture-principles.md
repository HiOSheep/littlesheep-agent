# LittleSheep 架构原则

本文只保留需要跨版本约束实现的职责和数据边界。当前实现与未完成项见[项目状态](../decision/project-status.md)；具体模块位置见[仓库指南](../reference/repository-guide.md)。

## 产品目标

LittleSheep 应替用户承担可重复的检索、规划、执行、验证和整理，让用户专注于目标、取舍和最终决定。系统内部概念只有在改善任务执行或记忆连续性时才值得保留。简单任务保持轻量，复杂任务才使用完整工具链和验收。

默认渐进披露：先给结论、当前状态和重要产物；细节按需展开。失败、权限拒绝、风险和待用户决定必须清楚可见。

## 模型与 Runtime 分工

LLM 负责语义理解、自然语言表达和提出工具请求。Runtime 独占权限判断、工具执行、状态转移、数据提交、证据判定和副作用结算。Prompt 是当前策略的模型投影，不是安全边界；模型说有权限不能代替 Runtime 授权。

对话中的回复、任务说明、步骤摘要、验证说明和交付表达必须来自真实 LLM 调用。发布前 Runtime 按 run 与规范化文案身份登记；同一结算在并发、重启和长会话中最多发布一次，且不能被换成另一份文案。按钮、状态、进度、路径、权限和工具事实由 Runtime 提供。

## 系统责任与依赖

UI、CLI 和渠道适配器负责交互及协议转换，不拥有业务真相。Application / Runner 负责一次运行的装配与生命周期；Harness 负责控制流；Context、Memory、Session、Tools 与安全模块各自拥有数据和策略；基础设施实现上层定义的契约。

依赖朝向稳定契约与领域能力，不朝向 Electron、具体 Provider、渠道或插件实现。跨包依赖走 package 公开入口；同一协议、类型和持久格式必须有唯一权威定义。

Harness 的当前执行路径为单一主循环。状态转移与旧检查点兼容由[Core Flow 状态契约](../reference/core-flow-state-contract.md)和[核心流程规范](core-agent-flow-guidelines.md)维护，本原则不复制阶段清单。

## 权限、容器与副作用

权限模式只改变授权，不改变模型行为或任务判断。研究模式、受限模式和完全访问的授权规则必须由 Runtime 强制执行；完全访问启用时需要明确危险确认，硬拒绝优先于模式与单次批准。

活动应用数据根是 LS 的逻辑容器边界，workplace 是默认工作区。用户选定的外部项目不会改变其数据所有权。当前 Main 的路径分类与审批不是 Docker 或 OS 进程沙箱；无法证明范围的路径和命令按外部或 unknown 处理。

每个工具调用都经过 schema 校验、边界复核、必要审批、执行、输出清洗和证据记录。提示词或 Renderer 不能绕过这些检查。不可逆或范围外操作应停下来请求用户决定；未结算副作用不得伪装成成功。

## Context 与 Memory

Context Engine 决定本轮模型需要看到的有限投影，不能默认注入整份长期记忆。候选需可追踪来源与预算；已经发送的上下文不能被悄悄重排或缩短。

Memory 的读取沿索引导航并受范围、预算和来源约束。名称、共现和向量相似只用于找到候选，不证明实体相同或事实等价。durable 写入和纠正必须通过受控工具，检查授权、来源和 revision；压缩只维护会话摘要，不得顺手学习为长期记忆。

## 持久化与恢复

持久格式、检查点、事件和摘要都要定义版本、所有权和失败恢复。提交既有文件前使用观察版本或内容校验；缺失、部分、截断或过期证据不能授权覆盖。迁移应能检查旧格式、在隔离数据上验证失败路径，并提供明确恢复边界。

后台资源、进程、监听器和存储连接必须有界，能取消并在生命周期结束时释放。普通请求不能因不相关的 Runner 恢复而失去已声明可用的只读能力。

## 插件、网络与不可信输入

插件和渠道默认按外部代码治理：明确声明能力、由宿主提供边界、失败隔离、停用后释放资源。未启用的插件不应加载。

网络检索由受控 Provider 和 Runtime 策略拥有。safe read 只适用于匿名公共 GET；每次连接和重定向都要检查目标及资源预算。外部页面和搜索结果始终是不可信证据，不能改写工具、权限、状态机或 Memory 策略。

## 证据与架构修改

验证结论只能覆盖实际观测到的事实。类型检查、单元测试、真实 Electron、真实 Provider、打包和长时负载是不同证据层；跳过、失败或不完整证据不能报告为通过。

只在职责、公开契约、持久格式、安全边界、所有权或生命周期真实变化时扩展模块或更新对应 owner 文档。评估抽象时要能指出它降低了哪一种用户负担或维护成本；否则简化或延后。
